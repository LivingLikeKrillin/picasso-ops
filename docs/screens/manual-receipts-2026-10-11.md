# 수동 작업의 영속 접수 통합

> 최신 구현: [상위 업무 중심 후속 7개 구현 및 검증](upstream-followups-2026-10-11.md). 아래 내용은 해당 단계의 기록이다.

2026-10-11. 운영 화면의 수동 작업 폼을 MES 주문과 같은 영속 접수·중복 방지·실행 관측·결과 스냅샷 계층에 연결했다. 실제 공장 인증이나 실물 로봇 검증이 아닌 로컬 PoC다.

## 구현 범위

- InspectAsset / PrepareSequencedRack 운영 폼은 POST /api/work-requests/manual을 사용한다.
- 최초 접수를 DB에 저장한 뒤 호스트에 제출한다. 같은 요청 ID와 요청자·입력은 원래 접수만 반환하며 재실행하지 않는다. 입력이나 요청자가 다르면 409다.
- 출처는 서버가 ops:manual로 고정하고 requestedBy를 실제 Ops 행위자 헤더에서 만든다. 외부 연계 출처 설정은 ':'를 허용하지 않아 로컬 출처를 사칭할 수 없다. 로컬 행위자 헤더는 기존 PoC 역할 구분이며 생산 환경 인증을 대체하지 않는다.
- 업무 입력 거절, 후보 없음, 호스트 응답 불명도 각각 REJECTED / UNASSIGNED / IN_DOUBT 접수로 남는다. RECEIVED·DISPATCHING·IN_DOUBT 재요청은 자동 재제출하지 않는다.
- 요청 목록에서 운영자 수동 출처를 구분하고 상세에 요청자를 표시한다. 제출 패널의 접수·실행 결과 보기는 같은 접수 상세로 연결된다. 폼 제출 뒤 목록도 즉시 다시 읽는다.
- 실행 완료 뒤 기존 결과 스냅샷 계층으로 결과를 저장한다. 로컬 작업은 MES ACK 대상이 아니므로 외부 수신 확인 대기로 표시하지 않는다. 외부 토큰으로 로컬 접수 결과에 접근하거나 ACK할 수 없다.

## API 계약

```
POST /api/work-requests/manual
X-Ops-Mode: operator
X-Ops-User: kim
Content-Type: application/json

{
  "requestId": "3342bd51-a170-45d9-827d-60a24a6b8e24",
  "form": {
    "workMasterId": "InspectAsset",
    "targets": [{ "id": "T1", "location": "bay-7" }]
  }
}
```

requestId는 정규 UUID 문자열이다. 본문은 requestId와 form 객체만 허용하며 64KiB 이하다. 최초 202 / 동일 접수 200 / 입력·요청자 충돌 409, 응답은 `{receipt, duplicate}`다. Location은 /api/work-requests/{receiptId}다. 202는 접수 저장을 뜻하며 배정·물리 완료를 뜻하지 않는다. 업무 검증 거절도 접수 후 REJECTED로 반환하고, 형식·역할 거절은 접수 전에 400/403이다.

내부 receiptId와 jobOrderId는 최초 접수 승자만 생성한다. 브라우저 requestId는 외부 요청 식별자로 보존된다. 조작 기록의 행위자는 실제 운영자이며 내부 접수 ID와 연결된다. 접수 커밋 전에 호스트를 호출하지 않도록 공통 접수 경로에서 상위 트랜잭션 진입을 거부한다.

## 사용자 흐름과 중복 방지

1. 작업 지시 내기를 누르면 브라우저가 UUID와 원본 폼을 sessionStorage에 먼저 보관한다. 보관 실패 시 서버에 제출하지 않는다.
2. 동일 입력의 재제출과 동일 요청 접수 확인은 보관된 ID·원본을 재사용한다. 응답 소실·프록시 오류·잘못된 접수 응답은 결과 불명으로 남는다.
3. 화면 이동·새로고침 후 보관된 요청을 읽어 확인 버튼과 원본 입력을 제공한다. 복원 시 자동 POST하지 않는다. 사용자 변경 시 해당 사용자와 모드의 보관 기록을 읽고, 이전 요청의 늦은 응답은 새 세션에 적용하지 않는다.
4. 보관된 요청과 현재 입력이 다르면 제출을 막는다. 확인 버튼은 수정된 화면 값이 아니라 보관된 원본을 사용한다.
5. ACCEPTED / REJECTED / UNASSIGNED를 확인한 뒤에만 새 작업 작성이 가능하다. 이 조작은 기존 요청과 별개의 실행 요청을 만들겠다는 의미다. 입력은 유지되므로 같은 작업을 명시적으로 반복할 수도 있다.
6. 처리 중·결과 불명은 새 작업 작성을 차단한다. 접수 상세에서 실행을 관측하고 동일 요청을 다시 확인하는 절차를 사용한다. 운영자 재개·자동 재배정은 아직 없다.

sessionStorage는 같은 탭의 이동·새로고침을 위한 보관이다. 탭 닫기·저장소 삭제·다른 브라우저를 넘어 요청 ID를 자동 복구하지 않는다. 이런 경우 통합 요청 목록의 요청자·접수·내부 작업 이력을 확인해야 하며, 불명 작업을 피하려고 새 요청 ID로 반복해서는 안 된다. 물리 동작의 exactly-once 보장을 주장하지 않는다.

## 호환성과 후속 범위

기존 POST /api/job-orders 직접 제출 API와 호출 계약의 /invoke는 기존 응답 계약을 유지한다. 새 운영 폼이 사용하는 경로는 영속 접수 경로이며, 위 두 레거시 경로에서 발생한 작업까지 목록에 소급 편입하지 않는다. 호출 계약의 로컬 실행 통합은 후속 작업이다.

전용 작업 메뉴·운영 개요, 중단 접수의 안전한 재개, callback 재전송·background 결과 수집, 배포 미션 버전 고정은 남아 있다.

## 검증

Ops 서비스 테스트 280개, UI 테스트 180개 통과. UI 빌드·lint, Ops 배포본 생성과 Core 의존성 경계 검사도 통과했다. DB 검증은 요청자 기록, 동시 중복, 요청자·입력 충돌, 업무 거절·미배정·전송 불명, 역할·UUID·본문 크기 검사와 DB 실패 시 호스트 미호출을 포함한다. UI 검증은 응답 소실 후 같은 ID 복원, 입력 변경 차단과 원본 재확인, 명시적 새 작업, 브라우저 보관 실패 시 미제출, 잘못된 성공 응답과 로컬 결과의 ACK 표시를 포함한다.

전체 스택 E2E는 실제 수동 접수 API, 동일 요청 확인, 새로고침 후 원래 접수 ID 복원, 한 실행 유지, 결과 상세와 로컬 ACK 비대상을 검증하고 기존 장애·재작업 시나리오를 유지한다.

전체 스택 Playwright E2E 1개 통과(시나리오 4.9분, 스택 기동·정리 포함 6.1분). 데스크톱과 390px 모바일 캡처를 직접 확인했으며 모바일 문서 가로 넘침 검사를 통과했다.
