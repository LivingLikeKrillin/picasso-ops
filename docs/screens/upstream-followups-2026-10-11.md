# 상위 업무 중심 후속 구현 및 검증 — 2026-10-11

이 문서는 상위 업무 접수 → 호출 계약·입력 매핑 → 실행 배포 → 로봇 실행 → 결과 수집·전달·수신 확인의 후속 구현을 기록한다. 실물 제조 현장 적용을 증명하는 문서는 아니다. 기존 단계별 문서는 당시 구현 범위를 설명하며, 현재 상태는 이 문서를 우선한다.

## 일곱 항목의 구현 범위

| 백그라운드 결과 수집 | 호스트 관측을 주기적으로 불변 결과 버전에 반영 | 전체 이벤트 스트림이나 모든 중간 응답 보존은 아님 |
| 결과 callback·재시도 | 로컬 Mock MES 수신기로 영속 큐·재시도·중복 키 전달 | 외부 인터넷·사내 원격 callback은 제외 |
| 실행 배포 버전 추적 | 계약·매핑·배포·실행 정의 버전을 접수와 결과에 보존 | 버전 계약 호출에 적용; 수동·기존 직접 호출 정책은 별도 |

## 화면과 사용자 여정

메뉴 순서는 운영 개요 / 작업 요청 / 운영 / 로봇 / 임무 / 현장 설정 / 이력 / 검증 도구다. 첫 진입 기본 화면은 로봇이며 URL hash가 있으면 해당 화면을 복원한다.

- 운영 개요: 전체 접수, 미배정, 제출 확인 필요, 업무 거절, 외부 결과 수신 미확인 카드를 해당 작업 요청 필터로 연결한다. 호스트의 실행 중·운영자 보류·불명 실행 및 인시던트를 별도로 표시한다.
- 작업 요청: `#requests?search=...&state=...&result=unacknowledged&receipt=...&offset=...`로 검색·필터·선택 접수·페이지를 보존한다. 새로고침 및 브라우저 뒤로 가기로 조회 맥락을 복원한다.
- 미션 호출 연결: 입력 매핑과 공개 상태를 확인하고 실행 배포를 변경한다. 운영자 호출 후 접수 상세로 이동한다.
- 접수 상세: 제출 관측, 사용한 배포, 결과 버전과 해시·ACK, 로컬 전달 이력, 미배정 재평가 이력을 연결한다.

조회 실패 시 직전 값을 유지하고 오래된 관측임을 표시한다. 미조회·불통을 0건으로 표현하지 않는다. 통신 불명은 작업 실패나 재실행 허가로 해석하지 않는다.

## 로컬 호출 API 변경

`POST /api/mission-interfaces/{id}/{version}/invoke`는 이제 아래 envelope를 받는다. 기존 bare input 호출자는 함께 변경해야 한다.

```json
{"requestId":"e513a6ba-f383-42ac-8c30-43eff582e88e","input":{"assets":["asset-1"]}}
```

`input`의 필드는 선택한 계약에 따른다. 위 예는 envelope 설명용이다. `requestId`는 정규 UUID이며 같은 행위자·계약·입력의 재확인에는 원래 값을 사용한다.

첫 접수는 HTTP 202, 동일 요청 재확인은 200과 `{receipt, duplicate}`를 반환한다. 다른 내용으로 같은 ID를 사용하면 충돌이다. 업무 거절은 영속 `REJECTED` 접수로 남을 수 있으므로 HTTP 202를 실행 수락이나 물리 완료로 해석하지 않는다. 이미 저장된 요청의 재확인은 이후 계약이 중지되어도 새 실행을 만들지 않는다.

브라우저는 전송 전에 요청 ID와 원본 입력을 sessionStorage에 보관한다. 응답 유실 후에는 같은 요청 확인을 제공하고, 불명 상태에서 새로운 ID로 다시 보내지 않는다. 저장 실패 시 전송을 막는다. 서버의 멱등 접수가 중복 방지의 최종 기준이다.

## 미배정 재평가와 불명 상태

`POST /api/work-requests/{id}/recover`는 `{requestId, reason, expectedUpdatedAt}`를 받는다. 서버가 receipt 행을 잠그고 최신 관측 시각·상태를 확인한다. 동일 판단 ID의 재확인은 기존 처리 결과만 반환한다.

재평가는 제출 응답이 없고 기존 실행 관측도 없으며 원래 정규화 입력이 있는 `UNASSIGNED`에 한정한다. 호스트 제출 전 배정 가능 판정에서 멈춘 요청만 대상이다. 실행 중·제출 중·전송 불명 또는 호스트가 이미 반환한 미배정은 이 경로로 보내지 않는다. 재평가 이력을 저장하고 기존 작업 ID·원래 배포를 보존한 뒤 제출한다. 새 배포가 생겨도 이전 접수를 새 정의로 바꾸지 않는다.

따라서 네 번째 항목은 제한된 안전 회복이다. 통신 불명 작업의 자동 재할당·자동 재송신 또는 임의 실행 재개까지 구현했다고 주장하지 않는다. 기존 실행 조회·현장 확인·운영자 판단 경계를 유지한다.

## 결과 자동 수집

수집기는 기본 5초마다 호스트 실행을 한 번 조회하고 대응하는 접수에 관측과 불변 결과 버전을 저장한다. 이 작업은 새 주문을 제출하지 않는다. `/api/work-requests/collector`에서 마지막 시도·성공·수집 건수·실패 상태를 확인한다.

상세 조회와 자동 수집이 겹칠 때 조회 시작 시각이 늦은 관측만 반영한다. 늦게 돌아온 과거 응답이 최신 상태나 결과를 덮어쓰지 않도록 한다. 호스트 불통 시 저장된 결과를 유지한다.

이는 polling이며 호스트가 현재 보유한 최신 응답을 수집한다. 두 조회 사이에 사라진 중간 응답까지 모두 수집하는 이벤트 로그는 아니다. 최종 결과의 운영 보장을 강화하려면 호스트 outbox 또는 이벤트 스트림·재처리 커서가 후속 과제다.

## 로컬 Mock MES callback

기본값은 비활성이다. 다음 환경 변수로 설정한다.

- `PICASSO_LOCAL_CALLBACK_URL`: 예 `http://127.0.0.1:8786/results`
- `PICASSO_LOCAL_CALLBACK_TOKEN`: 로컬 수신기 bearer token
- 기존 integration source 설정: 전달할 단일 Mock MES 출처

IP 리터럴 `127.0.0.1` 또는 `[::1]`의 HTTP만 허용한다. 호스트명·외부 주소·자격증명 포함 URL·리다이렉트는 허용하지 않는다. 자동 승인 검토에서 승인되지 않은 외부 목적지로의 결과 전송을 거부했기 때문에 외부 전송을 제외했다. 실제 원격 연계에는 구체적인 수신처·전송 데이터 승인과 별도 보안 설계가 필요하다.

V9 영속 전달 큐는 결과 버전마다 목적지와 상태를 기록한다. 기본 2초 간격으로 claim하고 30초 lease·claim token으로 경쟁 및 프로세스 중단을 처리한다. 실패는 지수 backoff 후 재시도한다. 안정적인 `Idempotency-Key: <receiptId>/v<version>`와 같은 snapshot·hash를 보내므로 수신기는 중복을 제거해야 한다. 설정 변경은 기존 큐의 목적지를 바꾸지 않는다.

HTTP 2xx는 전달 성공이며 업무 결과 수신 확인(ACK)은 아니다. 기존 결과 버전·해시 ACK API를 별도로 사용한다. E2E 수신기는 첫 전달에 503을 응답하고 다음 같은 키·본문을 204로 수락한다.

## 실행 배포와 버전

V10은 계약 버전별 불변 배포 이력을 추가한다. 기존 계약은 초기 배포 1 / `CODE`로 이행한다. 새 계약도 같은 초기 정책을 사용한다. 데이터 정의를 사용할 계약은 명시적으로 숫자 버전을 배포해야 한다.

`GET /api/mission-interfaces/{id}/{version}/deployments`로 이력을 읽고 `POST .../deploy`에 `{missionVersion, expectedDeploymentVersion, reason}`을 보낸다. 엔지니어 모드만 변경 가능하며 관측한 배포 버전과 다르면 충돌로 거절한다. 데이터 정의는 호스트의 이미 활성화 이력이 있는 불변 버전을 확인한다. 롤백도 새 배포 이력으로 만든다.

매핑은 불변 계약 버전에 속하므로 mappingVersion은 interfaceVersion과 같다. 접수 시 interfaceVersion / mappingVersion / deploymentVersion / missionVersion을 정규화 주문과 결과에 남긴다. 호스트는 지정된 정의로 배정 가능 판정과 실행을 수행하며 전역 활성 버전을 변경하지 않는다. 기존 실행·접수는 원래 버전을 유지한다.

`CODE`는 배포된 호스트 바이너리의 내장 정의를 가리킨다. 소프트웨어 업그레이드 사이의 동일 소스까지 보증하는 버전은 아니다. 수동 폼 및 기존 직접 API는 제출 시 활성 정의 정책을 유지한다. Ops와 mission-host를 함께 업그레이드해야 하며 구버전 호스트와의 혼합 배포는 검증하지 않았다.

## 검증

- Ops 서비스: 290개 통과. 멱등 접수, 동시 재평가 단일 제출, 관측 역전 차단, 자동 수집·불통 보존, 로컬 callback 재시도·중복 키·ACK 분리, 불변 배포·이전 접수 보존 포함.
- 실행 호스트: 80개 통과. 전역 활성 정의를 유지하면서 지정한 이전 버전으로 제출하는 검증 포함.
- UI: 18개 파일 186개 통과. 응답 유실 후 동일 요청 확인, URL 조회 맥락 복원, 개요 stale 관측, 재평가와 배포 변경 포함. 최종 보류 집계 수정 후 해당 5개 검사를 추가 통과.
- UI production build 및 lint, Ops 주 의존성 경계 검사 통과.
- 최종 전체 스택 E2E: 종합 시나리오 1개 통과(시나리오 5.3분, 스택 시작·종료 포함 6.7분). PostgreSQL·site/registry/Mimic·mission-host·Ops·UI·로컬 Mock MES 수신기를 함께 실행했다. 호출 계약 배포/영속 호출/중복 확인, 화면 조회 없이 자동 결과 생성, callback 첫 503 이후 재시도, ACK 분리, 개요 필터 이동·상세 URL 복원, 기존 미션 활성화·보류 후 재작업·registry 불통을 확인했다.
- 실제 Ops HTTP 운영 개요와 전용 작업 요청을 촬영·육안 확인했다. 1440px·390px 운영 개요에서 브라우저 오류 및 문서 가로 넘침 없음. 최근 접수 표의 주문 ID와 내부 작업 ID 구분을 보완했다.
