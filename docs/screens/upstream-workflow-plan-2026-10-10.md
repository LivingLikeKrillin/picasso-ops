# Picasso 상위 시스템 중심 운영 UX·연계 구현 계획

> 현재 구현과 제한: [후속 7개 항목 완료 기록](upstream-followups-2026-10-11.md). 본문 1~15절의 단계별 미구현 표시는 당시 기준이며 마지막 16절을 함께 읽는다.

작성: 2026-10-10 / 상태: 전체 계획. 미션 관리 1차 구현은 mission-refresh.md 참조

## 1. 목표와 설계 기준

Picasso가 제공하는 가치는 MES·WMS의 업무 요청을 로봇이 수행할 수 있는 작업으로 해석하고, 실행·예외·완료 근거를 관리하며, 상위 시스템이 사용할 결과로 돌려주는 것이다. Ops는 이 과정을 추적하고 운영자가 개입하는 창구로 재구성한다.

대표 사용자 여정:

**외부 업무 요청 → 접수·검증 → 임무 연결·배정 판정 → 로봇 실행 → 예외 대응 → 완료 근거 확인 → 결과 조회·반환 확인**

로봇·어댑터·프로파일 도입 흐름은 이 여정을 가능하게 하는 관리 기능으로 유지한다. 기존 파란색 디자인과 Pretendard 폰트 체계는 재사용하고 정보 구조를 바꾼다.

완료 기준은 “보기 좋은 대시보드”가 아니라 **외부 주문 하나를 기준으로 요청부터 결과까지 설명하고 추적할 수 있는가**이다.

## 2. 현재 구현과 공백

| 항목 | 현재 확인된 구현 | 보완 필요 |
|---|---|---|
| 작업 요청 | POST /api/job-orders, 두 임무의 수동 입력 폼 | 외부 시스템용 버전 계약·인증·원천 주문 식별 |
| 지원 임무 | InspectAsset, PrepareSequencedRack | 두 임무의 업무 의미와 입력 제약을 화면·명세에 설명 |
| 배정 판정 | POST /api/job-orders/eligibility, 로봇별 통과/거절 이유 | 요청 상세와 연결하고 사전 판정과 실제 접수 결과를 구분 |
| 요청 식별 | 운영 서비스가 호출마다 새 requestId/jobOrderId 생성 | 외부 주문 재시도를 동일 요청으로 처리하는 영속 식별·중복 방지 |
| 미배정 | 후보가 없으면 호스트를 호출하지 않고 조작 기록에도 남기지 않음 | 접수된 외부 요청의 미배정·거절도 조회 가능하게 보존 |
| 실행 추적 | GET /api/executions, jobOrderId·executionId·missionVersion | 외부 주문과 연결된 목록·상세 및 재기동 후 추적 |
| 예외 대응 | 인시던트 상세·판단·재작업 흐름 | 작업 상세 연결, 요약 우선 배치, 실패 시 사유 보존 |
| 결과 | GET /api/job-responses, 작업별 송신 기록·근거 | 실제 외부 시스템에 제공할 결과 계약·버전·조회 경로 |
| 수신 확인 | 현재 SENT 기록만으로 외부 MES 수신을 증명할 수 없음 | 실제 결과 제공과 업무 수신 확인을 분리 |
| 권한 | 현재 Ops의 사용자/모드 헤더와 로컬 호스트 구조 | 외부 호출 주체 인증 및 자기 요청만 조회하도록 범위 제한 |

따라서 기존 API만으로 “외부 MES 주문 통합 화면”을 완성했다고 표현하지 않는다. 현재 수동 폼은 운영자의 수동 요청이며, MES 연동 대체 입력이라고 명시할 수 있다.

## 3. 첫 구현 범위와 후속 범위

### 첫 구현(MVP)

- Mock MES 한 개가 실제 HTTP로 요청하고 결과를 조회한다. 대역임을 화면과 문서에 표시한다.
- 기존 두 임무만 지원한다. MES와 WMS라는 명칭만 바꾼 별도 대역을 늘리기보다 한 연결을 끝까지 검증한다.
- 외부 주문 식별, 접수 기록, 같은 주문의 중복 요청 처리, 결과 조회를 영속화한다.
- Ops의 기본 화면을 운영 개요로 변경하고 작업 요청 목록·상세를 중심으로 탐색한다.
- 미배정·거절·통신 결과 불명도 추적한다. 미배정 요청의 자동 재배정은 첫 범위에서 제외하며 상태와 조치 안내를 제공한다.
- 결과 반환은 우선 조회(polling) 방식으로 구현한다. 별도 업무 수신 확인 API로 확인 사실을 남긴다.
- 수동 작업 요청도 같은 접수 서비스와 작업 상세를 사용하도록 전환한다. 기존 클라이언트의 응답 계약은 호환성을 검토해 유지한다.

### 후속

- 외부 시스템별 필드 변환 설정, 실제 MES/WMS 연동, callback 재전송·전송 이력.
- 우선순위·대기열·자동 재배정, 취소·선점 정책은 별도 도메인 설계 후 추가한다.
- 범용 매핑 편집기, 범용 임무 그래프 편집기, 근거 없는 가동률·완료율 대시보드는 첫 범위에 포함하지 않는다.
- Narrator 연결은 작업 추적 ID와 결과 계약이 안정된 후 확장한다. 현 단계에서 연결된 기능처럼 표시하지 않는다.

## 4. 메뉴와 화면

| 메뉴 | 역할 | 핵심 화면 |
|---|---|---|
| 운영 개요 | 지금 개입할 업무 확인, 기본 진입점 | 판단 필요·접수 후 미배정·실행 중·결과 수신 확인 대기, 데이터 조회 상태 |
| 작업 요청 | 외부/수동 요청부터 결과까지 추적 | 목록, 작업 상세, 수동 요청 |
| 임무 관리 | 업무가 어떤 실행 정의로 연결되는지 관리 | 지원 업무와 입력 계약, 활성 버전, 편집·검증, 버전 비교 |
| 로봇 관리 | 실행 자원 도입·유지 | 기체, 도입 준비, 어댑터, 프로파일 |
| 현장 설정 | 운영 설정과 실제 적용 확인 | 저장 버전·호스트 적용 버전, 변경 전후·영향 |
| 이력 | 행위와 변경의 근거 확인 | 검색·필터·상세·관련 작업 링크 |
| 검증 도구 | 개발·PoC 재현 | Mock MES, 셀 대역, 장애 주입, 시나리오 실행 |

개요의 카드는 작업 목록 필터로 연결한다. 집계는 서버의 명시적 조회 범위에 근거하며, 최신 N건을 전체 건수로 표시하지 않는다. 로봇 목록은 작업 상세의 배정 기체에서 바로 접근한다.

### 4.1 작업 목록

주요 열: 요청 출처, 외부 주문 ID/내부 작업 ID, 업무 종류, 접수 시각, 접수·배정 상태, 실행 상태, 판단 필요, 결과 수신 확인 상태.

필터: 출처, 업무 종류, 상태, 기간. 외부 주문 ID 검색을 제공한다. 전체 기간 검색과 페이지 이동은 서버 조회 API와 함께 구현한다.

실행 ID가 없는 미배정·거절 요청도 행으로 나타난다. 기본 정렬은 운영 개입이 필요한 요청을 찾기 쉽게 제공하되, 접수 시각 정렬도 선택할 수 있게 한다.

### 4.2 작업 상세

상단에는 출처·외부 주문·내부 작업 ID, 업무 내용, 현재 멈춘 이유, 다음 가능한 조치를 표시한다.

1. **요청:** 원본 입력, 정규화된 업무 입력, 접수/검증 결과. 원본 JSON은 펼침 영역.
2. **임무·배정:** WorkMaster, 변환 규칙 버전, 실제 적용 임무 버전, 배정 기체, 판정 이유와 판정 시각. 아직 확정되지 않은 버전을 적용 버전으로 표시하지 않는다.
3. **실행:** 단위별 상태, 물리 상태, 요구/확보 근거, 조회 시각, 복원 여부.
4. **예외·판단:** 관련 인시던트 요약 → 근거 → 가능한 판단. 판단 사유는 반영 확인 전까지 유지한다.
5. **결과:** 결과 버전과 내용, 생성 시각, 외부 제공 방식, 업무 수신 확인 시각. 현행 송신 기록은 별도로 의미를 설명한다.
6. **이력:** 영속 이벤트가 있는 단계만 시간순 표시. 현재 스냅샷에서 과거 전이 시각을 추측하지 않는다.

기존 화면 단계에서는 외부 출처 정보를 만들어 넣지 않고 “수동 요청 / 외부 주문 정보 없음”으로 표시한다. 호스트 instanceId와 executionId를 함께 다뤄 이전 인스턴스에 잘못 판단하지 않게 한다.

### 4.3 수동 요청·임무 관리

수동 요청은 “업무 선택 → 입력 → 배정 사전 확인 → 제출 → 접수 상세” 순서로 제공한다. 제출 버튼은 로봇 명령 전송과 작업 완료를 의미하지 않는다.

임무 관리에는 업무 입력과 임무 단계의 관계를 읽기 전용으로 설명한다. 기존 JSON 편집은 고급 편집에 둔다. 활성화된 새 버전과 이미 실행 중인 작업의 적용 버전을 구분한다.

### 4.4 상위 시스템 연결 표시

첫 범위에서는 등록된 Mock MES의 식별자, 인증 설정 여부, 지원 계약 버전, 최근 실제 요청/조회 시각을 표시한다. 트래픽이 없다는 이유로 연결 장애로 판정하지 않는다. 등록 정보만으로 “연결 정상”을 표시하지 않는다.

## 5. 외부 인터페이스와 데이터 설계

아래 경로·필드는 **제안이며 현재 제공되는 API가 아니다.** OpenAPI와 상태 전이 명세를 먼저 확정한다.

| 제안 API | 역할 |
|---|---|
| POST /integration/v1/job-orders | 외부 주문 접수. 접수 식별자와 조회 주소 반환 |
| GET /integration/v1/job-orders/{receiptId} | 접수·배정·실행 상태 및 결과 조회 |
| POST /integration/v1/job-orders/{receiptId}/result-acknowledgements | 특정 결과 버전에 대한 외부 업무 수신 확인, 중복 확인은 멱등 처리 |
| GET /api/work-requests | Ops 작업 목록, 서버 검색·필터·페이지 이동 |
| GET /api/work-requests/{receiptId} | Ops 상세. 외부 요청·실행·인시던트·결과 연결 |

외부 요청 예시:

```json
{
  "externalOrderId": "MES-ORDER-204",
  "workMasterId": "PrepareSequencedRack",
  "input": {
    "slots": ["RACK-204.S01"],
    "material": "ENGINE-COVER-A",
    "presentation": "SEQ-IN-02.BIN-A"
  }
}
```

- sourceSystemId는 인증된 호출 주체에 연결한다. 클라이언트가 임의로 다른 출처를 주장할 수 없게 한다.
- 유일 키는 (sourceSystemId, externalOrderId)로 한다. 동일 키·동일 정규화 입력은 기존 접수 ID와 현재 상태를 반환한다. 동일 키·다른 입력은 409로 거절한다.
- receiptId와 내부 jobOrderId는 최초에 한 번 생성하고 재시도·재기동에서도 유지한다. 기존 호출별 새 ID 생성 경로를 그대로 외부 API에 노출하지 않는다.
- 접수 성공 응답은 저장 완료를 의미한다. 실행 수락·로봇 배정·작업 완료와 구분한다. 최초 저장 성공은 202, 중복 조회 반환 등 세부 코드는 명세와 테스트로 고정한다.
- JSON 형식 자체가 잘못되거나 인증되지 않은 요청은 접수하지 않는다. 식별 가능한 정상 형식의 업무 요청이 업무 검증에서 거절된 경우에는 거절 접수 기록을 보존한다. 인증 실패 로그에 민감한 원문을 남기지 않는다.
- 접수 기록에는 출처·외부 ID·계약 버전·정규화 입력/해시·변환 버전·내부 ID·검증/배정 결과·시각을 보존한다. 원문 보관 범위·크기는 명시적으로 제한한다.
- 결과에는 receiptId, externalOrderId, jobOrderId, executionId/instanceId, 실제 missionVersion, resultVersion, 물리 상태, 근거 충족, 미확인 단위, 사람 판단/보류, 생성 시각을 계약에 맞게 포함한다.
- 결과는 버전별 불변 스냅샷으로 보존한다. 최신 버전 변경 시 이전 버전의 수신 확인을 최신 버전 확인으로 취급하지 않는다.
- 변환은 기존 두 JobOrderDraft 생성 로직을 재사용한다. 첫 범위의 변환 규칙은 코드로 관리하고 버전을 기록한다. 로봇 벤더·프로토콜 선택은 상위 시스템 요청에 요구하지 않는다.

### 상태를 한 개의 성공/실패로 합치지 않는다

| 축 | 의미 |
|---|---|
| 접수·검증 | 저장됐는가, 업무 입력이 유효한가 |
| 실행 제출·배정 | 호스트 수락/거절/미배정/결과 불명인가 |
| 실행 | 물리적으로 어디까지 수행했는가 |
| 근거·판단 | 요구 근거를 충족했는가, 사람 판단 또는 잔여 보류가 있는가 |
| 결과 제공 | 어떤 결과 버전을 조회할 수 있는가, 외부가 그 버전 수신을 확인했는가 |

첫 범위의 결과 조회에는 네트워크 송신 완료 상태를 따로 만들 필요가 없다. 조회 가능과 업무 수신 확인을 표시한다. 후속 callback에는 전송 대기/시도/실패/HTTP 응답과 업무 수신 확인을 추가로 구분한다.

## 6. 구현 구조와 신뢰성 선행 조건

첫 범위는 새 마이크로서비스를 늘리지 않고 ops-service 안에 외부 계약·접수 저장소·변환·제출 조정·결과 조회 모듈을 둔다. 영속 데이터는 기존 PostgreSQL의 마이그레이션으로 추가한다. 실행과 로봇 제어는 mission-host/Picasso에 유지한다.

외부 접수 저장과 호스트 호출은 서로 다른 실패 경계이다. 접수 저장과 제출 대기 항목을 같은 DB 트랜잭션에 기록하고, 워커가 고정 jobOrderId로 제출한다. 호스트 응답을 받지 못해도 새 작업을 생성하지 않고 재조회·대조한다. 재전송은 호스트의 멱등·재기동 의미를 검증한 뒤 허용한다.

필수 선행 검증:

- 현재 MissionHost.submit은 미들웨어 수락 후 journal을 기록하며 JournalWriteFailed 때 실행이 메모리에 남는 경로가 있다. 기록 실패 후 pump가 명령을 내보낼 수 있는지 장애 테스트로 확인하고, 영속 기록 전 실행이 진행되지 않도록 경계를 보완한다.
- 호스트의 기존 멱등 처리와 재기동 복원은 외부 주문 중복 방지의 대체물이 아니다. 영속 접수 키와 제출 기록 양쪽을 검증한다.
- 재기동 후 동일 jobOrderId가 과거 실행과 연결되는지, 완료 근거·사람 판단·결과 버전을 다시 조회할 수 있는지 확인한다. 부족한 스냅샷/결과 보존은 본 범위에서 보완한다.
- DB 단절, 응답 소실, 복원 불확실 상태를 “미실행”으로 단정하지 않는다. 자동 재제출 대신 결과 불명·조정 필요를 표시할 수 있어야 한다.
- 물리 동작의 exactly-once를 주장하지 않는다. 명령 식별·중복 억제·관측 대조의 보장 범위를 명세에 적는다.

기존 mode/user 헤더는 외부 인증 수단으로 사용하지 않는다. PoC에서는 등록 주체별 자격 증명을 서버에서 검증하고 조회 범위를 제한한다. 실서비스에서는 TLS·자격 증명 관리·배포망 경계까지 별도 적용 검증이 필요하다.

## 7. 단계별 작업과 통과 조건

| 단계 | 구현 산출물 | 통과 조건 |
|---|---|---|
| 1. 작업 중심 화면 | 운영 개요, 기존 작업 상세, 인시던트·응답 연결, URL 탐색·입력 보존 | 기존 API로 작업 하나를 화면 간 ID 대조 없이 추적. 수동 요청·현행 송신 기록의 의미를 정확히 표시 |
| 2. 접수 계약·영속 기반 | OpenAPI, DB 마이그레이션, 외부 접수/조회, 공통 접수 서비스, 영속 제출 대기 | 동일 외부 주문의 중복 호출·응답 소실·재기동에도 한 접수/내부 작업 ID 유지. journal 실패 시 실행 진행 방지 확인 |
| 3. 상위 요청 운영 화면·결과 | 외부 주문 목록/상세, 미배정·거절, 결과 스냅샷·조회·수신 확인 | 실행 없는 요청도 조회. 결과 버전별 수신 확인. 재기동 후 근거와 결과 추적 |
| 4. 통합 데모·검증·문서 | Mock MES, 전체 스택 E2E, 대표 화면 캡처, 계약/운영 가이드 | 실제 HTTP 요청부터 예외 대응·결과 수신 확인까지 재현. 기존 로봇 도입/임무 관리 E2E 유지 |

1단계는 데이터가 없는 항목을 감추거나 미제공으로 표시하고, 2~3단계에서 실제 계약에 연결한다. 임시로 가짜 외부 ID나 ACK를 만들어 완성 화면처럼 보이게 하지 않는다.

기존 UX 검토의 판단 사유 보존·탐색 문제는 1단계에 포함한다. 임무 JSON 편집 개선과 현장 설정 비교는 핵심 여정 이후 진행하되, 적용 버전 표시처럼 작업 상세에 필요한 부분은 함께 반영한다.

## 8. 테스트 계획

단순 렌더링 반복보다 실패 경계와 사용자 여정을 중심으로 검증한다.

1. 정상: Mock MES 요청 → 접수 → 배정 → Mimic 실행 → 요구 근거 확인 → 결과 조회 → 해당 버전 수신 확인.
2. 중복: 같은 주문의 동시 요청·응답 소실 후 재요청에서도 한 접수/한 실행. 다른 입력의 같은 주문은 409.
3. 미배정/거절: 가용 로봇 없음, 스킬 불일치, 업무 입력 오류를 작업 목록·상세에서 추적. 거절을 성공으로 표시하지 않음.
4. 예외: GRASP_FAILED·통신 단절·판단 대기 → 관측 확인 → 재작업 → 완료. 사유 보존, instanceId 검증, 응답 불명 표시.
5. 영속 장애: 접수 DB 실패 시 접수 성공 응답 없음. 호스트 journal 실패·호스트 응답 소실·각 경계 재기동 후 중복 동작 없이 상태 대조.
6. 결과: 재조회는 같은 버전 내용 반환. 중복 수신 확인은 멱등. 이전 버전 확인으로 최신 결과가 확인됐다고 표시하지 않음.
7. 인증: 다른 출처의 주문 조회/수신 확인 차단. 브라우저 mode 헤더만으로 외부 쓰기 권한 획득 불가.
8. UX: 메뉴 왕복·뒤로가기·새로고침·늦은 응답, 좁은 화면·키보드 탐색, 불통/오래된 관측에서 완료나 0건으로 오인하지 않음.

기존 전체 스택 lifecycle E2E는 회귀 기준으로 유지한다. 새 외부 연계 E2E는 API 가로채기 없이 Mock MES·Ops·host·registry·Mimic·PostgreSQL을 실제로 연결한다. 실물 PLC·로봇 및 실제 MES 검증과는 구분해 보고한다.

## 9. 통합 흐름 대표 시연

1. Mock MES가 외부 주문 MES-ORDER-204를 실제 HTTP로 제출한다.
2. Ops의 작업 요청에서 업무 내용, 변환된 임무, 적용 버전과 배정 이유를 확인한다.
3. 로봇 실행 중 예외를 주입한다. 작업 상세에서 물리 상태와 요구 근거 부족을 구분해 설명한다.
4. 운영자가 근거를 보고 재작업을 판단한다. 실행이 재개되고 결과가 새 버전으로 제공된다.
5. Mock MES가 결과를 조회하고 버전 수신을 확인한다. 화면에서 해당 확인 사실을 검증한다.
6. 같은 주문을 다시 제출해 접수/작업이 늘지 않는 것을 보여준다.

이 시연은 가상 시스템에서 인터페이스 책임 경계와 실패 처리를 검증한다. 실제 MES·PLC·로봇의 현장 검증은 별도로 수행한다.

## 11. 미션 생성과 외부 호출 계약 연결 — 추가 UX 검토

### 현재 한계

현재 MissionsArea는 EDITABLE_WORK_MASTER 하나를 대상으로 초안 저장·검증·모의 실행·활성화를 제공한다. 서버 MissionOperations.EDITABLE도 PrepareSequencedRack만 허용한다. 이는 기존 업무의 실행 정의를 개정하는 기능이며, 임의의 새 업무 유형 생성·입력 스키마 등록·외부 API 공개 기능은 아니다.

JobOrderForm의 업무 입력 처리도 InspectAsset/PrepareSequencedRack 분기와 고정 근거 등급으로 구현되어 있다. 따라서 “새 미션 생성” 버튼이나 필드 매핑 화면만 추가해서 임의 업무를 실행할 수 있다고 표현해서는 안 된다. 새 업무 유형의 입력 검증·내부 작업 생성·런타임 지원까지 확장해야 한다.

### 권장 관리 모델

세 객체를 구분하고 화면에서 연결한다.

1. 미션 정의: 실행 단계, 요구 스킬, 실패/재작업 정책, 완료 근거, 정의 버전.
2. 호출 계약: 외부 업무 식별자, 입력·결과 스키마, 계약 버전, 허용 호출 주체.
3. 연결·배포: 호출 계약의 입력이 어떤 미션의 어떤 입력으로 변환되는지, 어느 배포 버전이 사용되는지.

미션 활성화와 외부 공개는 별도 상태다. 검증된 미션이 있어도 공개하지 않을 수 있고, 외부에 공개된 계약을 유지하며 검증된 새 미션으로 배포를 변경할 수 있다. 외부 계약 변경은 호환성을 별도로 검토한다.

### 화면 구성

미션 관리 안에 “미션 목록 / 호출 인터페이스 / 배포 이력”을 둔다.

- 미션 목록: 업무 이름, 설명, 지원 입력, 초안/활성 버전, 공개된 호출 계약, 검증 상태. 코드 정의와 편집 가능한 정의를 구분한다.
- 미션 상세: 개요 / 실행 정의 / 검증 / 호출 연결 / 버전. 생성은 지원 템플릿 복제로 시작한다. 임의 신규 업무 유형은 런타임 지원을 완료한 뒤 제공한다.
- 호출 인터페이스 상세: 외부 업무 식별자와 계약 버전, 공통 API 주소·호출 예제, 입력·결과 스키마, 연결 미션, 허용 호출 주체, 공개 상태.
- 입력 매핑: 외부 필드 → 내부 업무 입력, 자료형·필수 여부·기본값, 목록 요소 매핑, 허용 값. 필드별 오류와 변환 결과를 미리 본다. 초기에는 직접 필드 연결·제한된 상수만 허용하고 임의 스크립트 실행은 제공하지 않는다.
- 검증: 샘플 요청 → 스키마 검증 → 정규화된 업무 입력 → JobOrder 미리보기 → 배정 판정 → 명시적 모의 실행. 미리보기는 실제 로봇을 실행하지 않는다.
- 공개/배포 검토: 입력 호환성, 매핑 오류, 대상 미션 검증·모의 실행 결과, 버전 변경 영향, 공개 사유를 확인한다. 연결된 계약을 사용 중인 미션의 삭제/비공개 처리는 영향과 함께 제한한다.

결과 매핑도 필요하지만 물리 상태·요구 근거·미확인·사람 판단을 단일 success로 축약하지 못하도록 필수 의미를 보존한다. 첫 범위는 공통 결과 계약을 유지한다.

### API 구조와 버전 정책

미션별 HTTP 엔드포인트를 동적으로 생성하기보다 기존 계획의 공통 POST /integration/v1/job-orders와 버전이 있는 업무 식별자를 사용하도록 권장한다. 예: operationId=prepare-sequenced-rack, operationVersion=1. 외부 호출자는 로봇 벤더나 내부 미션 정의 버전을 선택할 필요가 없다.

이는 5절의 workMasterId 직접 지정 예제를 발전시킨 후속 계약 제안이다. 최종 OpenAPI에서 둘 중 하나로 확정하고, 처음에는 두 기본 업무에 대한 코드 기반 연결을 사용한다. 범용 UI 매핑을 첫 외부 요청 구현의 선행 조건으로 만들지 않는다.

외부 계약 버전, 변환 규칙 버전, 미션 정의 버전, 배포 버전을 각각 기록한다. 배포 시 연결 대상 미션 버전을 명시적으로 고정한다. 활성 버전을 매 실행 단계마다 다시 따라가지 않는다. 접수 당시 배포 정보를 보존하고, 실행 시 사용할 버전이 호스트에서 실제로 선택·검증되도록 서버 계약을 보완한다. 기존 호스트가 임의 버전 지정을 지원하는지는 구현 착수 시 확인하며, 지원되지 않으면 화면만으로 버전 고정을 주장하지 않는다.

기존 실행은 원래 버전을 유지한다. 새 배포와 롤백의 적용 대상은 이후 접수되는 새 요청으로 정하고, 대기 요청의 전환은 별도 명시적 정책으로 처리한다. 업무 입력 의미가 달라지는 변경은 새 계약 버전으로 공개한다.

### 단계별 반영

- 1단계: 미션 목록·상세 재구성. 기존 두 업무의 입력 계약·현재 코드 기반 연결을 읽기 전용으로 설명한다. PrepareSequencedRack의 기존 편집·검증·활성화를 유지한다.
- 2~3단계: 호출 계약 목록, 공통 API 호출 예제, 코드 기반 매핑 미리보기, 계약/매핑/미션/배포 버전 추적을 외부 접수와 함께 구현한다.
- 외부 연계 E2E 통과 후: 제한된 필드 매핑 편집·샘플 검증·공개/배포 흐름을 추가한다. 코드 분기에 묶인 신규 업무 생성과 일반화된 런타임 입력 지원은 별도 후속 범위로 수행한다.

추가 완료 기준: 엔지니어가 “상위 시스템이 어떤 입력으로 어떤 미션을 호출할 수 있는지”를 화면에서 확인하고, 샘플 요청의 변환 결과를 검증하며, 실제 작업 상세에서 사용된 네 가지 버전을 역추적할 수 있어야 한다.


## 12. 이번 로컬 PoC 구현 상태

미션 목록·실행 정의·호출 연결·버전 화면과 두 기존 업무의 계약을 반영했다. 제한된 JSON Pointer 매핑을 불변 계약 버전으로 저장하고, 로컬 공개·중지·운영자 호출 및 조작 기록 연결을 구현했다. 상세 API와 검증은 [호출 계약 저장·공개·실행 구현](mission-interface-implementation.md)에 기록한다.
