# 결과 전달 신뢰성 강화

상태: outbox·커서·현장 확인 기록 구현 완료, 서버·UI 회귀 및 장애 E2E 통과.

## 결과 outbox와 커서

호스트의 응답 송신 기록·outbox 삽입을 같은 트랜잭션에 묶고 커밋 이후에만 미들웨어의 pending 응답을 ACK한다. 재시작 중복 판정은 기존 정책을 유지한다. producer ID는 DB 수명 동안 유지한다. 증가 번호는 행 잠금을 잡는 트랜잭션 카운터로 배정해 커밋 순서 역전에 의한 커서 누락을 방지한다.

호스트 REST에서 커서 다음 결과를 순서대로 제공한다. Ops는 불변 결과 삽입·접수 연결·커서 이동을 하나의 트랜잭션에 묶는다. 오류 시 커서를 전진시키지 않는다. 결과 ID로 중복 제거하고, producer 변경·커서 역행·순서 누락·깨진 스냅샷은 수집 실패로 노출한다. 화면 상세 조회는 현재 실행을 관측하지만 outbox 결과 순서를 변경하지 않는다.

기존 설치에서 outbox 이전의 중간 응답을 새로 복원할 수 있다고 주장하지 않는다. 보관·삭제 정책 없이 우선 append-only로 두며 운영용 retention/압축은 별도 과제다.

## 검증 기준

- 기록/outbox 동시 롤백 및 커서/결과 동시 롤백.
- 같은 응답 재전달·동시 수집 시 결과 버전 중복 없음.
- Ops 재시작 후 이전 커서 재개, 호스트 재시작 후 producer와 기록 유지.
- 실제 HTTP 통신 단절 중 결과 발생 → 복구 후 중간·최종 결과 순서대로 수집.
- 기존 callback 재시도·멱등 키·결과 버전 ACK 분리 유지.

## 결과 불명 작업의 운영자 흐름

자동 재제출은 전송 전 미배정 증거가 있을 때만 허용한다. 결과 불명에는 내부 작업 ID, 마지막 관측, 호스트/수집 상태를 함께 표시하고 현장 확인 메모를 영속 기록한다. 메모는 물리 완료 판정이나 제출 허가로 해석하지 않는다. 확인자·시간·판단 근거와 관측한 버전을 남기고 낡은 화면에서의 변경을 차단한다.

## 구현 경로와 운영 계약

- Host V4: `mission.result_producer`, `mission.result_outbox`. `/host/result-events?after=0&limit=100`이 producer ID, highWatermark, sequence별 불변 snapshot을 제공한다. 최대 200개, 오름차순 페이지다. producer UUID는 호스트 프로세스 ID와 별개로 DB에 유지한다.
- Ops V12: `ops.result_cursor`. production은 durable outbox 수집만 사용하고 구형 최신 상태 polling으로 자동 전환하지 않는다. 5초 주기마다 최대 100개를 수집하며 결과 삽입과 커서를 함께 커밋한다. 화면 상세 조회는 현재 실행 관측만 갱신한다.
- Ops V13: `ops.work_request_review`. POST `/api/work-requests/{id}/reviews`에 `requestId`, `observation`, `reason`, `expectedUpdatedAt`을 보낸다. 운영자만 기록하며 동일 요청 재확인·내용 충돌·낡은 접수 상태를 검사한다. 확인 기록은 접수 상태를 바꾸지 않고 로봇 명령을 보내지 않는다.
- 운영 개요에서 영속 커서·확인한 마지막 번호·관측 시점 미수집량·최근 성공을 확인한다. 장애 중 highWatermark는 마지막 성공 시점의 값이므로 현재 호스트의 실시간 전체 누적량을 의미하지 않는다.
- 작업 요청 상세에서 현장 확인 기록과 당시 접수 상태·마지막 실행 관측·저장 결과를 함께 보존한다. 응답 유실 시 같은 확인 UUID로 재조회한다.

새 outbox는 V4 이후 기록한 응답만 포함한다. 기존 송신 로그를 역사 이벤트로 소급 변환하지 않는다. 이전 Ops 결과·ACK는 유지된다. 호스트 DB를 교체하여 producer가 바뀌면 자동 초기화하지 않고 수집을 중단한다. 운영자가 데이터 이관·정합성을 검토해야 하며 현재 자동 reset UI는 제공하지 않는다.

보장은 호스트 기록이 커밋된 이후의 at-least-once 수집과 Ops 결과 ID 중복 제거다. 로봇의 물리 실행 exactly-once 또는 호스트 기록 전에 발생한 실물 동작 복원을 주장하지 않는다. 이벤트 보관은 append-only이며 운영용 retention·용량 제한·오래된 커서 복구 정책은 후속 운영 과제다.

## 장애 주입 도구

`ui/e2e/host-link.mjs`는 루프백 HTTP 프록시이며 수락 응답을 끊고 연결을 차단/복구한다. E2E `run-dist.mjs --restartable`만 테스트용 로컬 재시작 제어를 연다. production Java 서비스에는 장애 주입이나 재시작 API가 추가되지 않는다.

## 회귀 검증 결과

Ops 299개·호스트 83개·UI 194개, 총 576개 테스트 통과. production 빌드·UI 린트·Ops 주 의존성 경계 검사 통과. 주요 검증은 outbox/커서 롤백, 동시 수집 중복 제거, 상세 조회와 결과 수집 순서 분리, producer 변경 차단, 확인 기록 멱등성·권한·낡은 화면 차단이다. 미션 전체 여정 및 아래 장애 E2E를 통과했다.

## 실제 전체 스택 장애 E2E

종합 시나리오 1개 통과(시나리오 6.1분, 기동·종료 포함 7.4분). PostgreSQL·site/registry/Mimic·mission-host·Ops·UI·로컬 Mock MES 수신기와 테스트용 HTTP 프록시를 함께 실행했다.

1. 기존 로봇 도입·설정·작업 접수·callback 첫 503 이후 재시도·버전 ACK·재작업 흐름 유지.
2. 사용자 정의 LineAssetCheck 등록 → 초안·검증·모의 실행·활성화 → 숫자 버전 배포 → 공개·호출 → 물리 완료.
3. 실제 호스트 수락 응답만 유실시키고 Ops↔호스트 HTTP 연결을 차단. 접수 IN_DOUBT와 수집 UNAVAILABLE 확인.
4. 현장 확인·인계 기록을 작성하고 단절 중 실제 작업이 물리 완료될 때까지 진행.
5. Ops를 강제 종료·재시작하고 커서 유지 및 동일 주문의 기존 접수 반환 확인. 호스트도 강제 종료·재시작하여 producer ID와 전체 outbox 페이지 동일성 확인.
6. 연결 복구 후 정확한 응답 ID의 불변 결과를 수집하고 접수를 ACCEPTED로 관측 확정. 현장 확인 이력 보존 및 HTTP 작업 제출 횟수가 1회만 증가했음을 확인.
