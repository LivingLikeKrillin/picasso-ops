# 제조 스테이션 통합 시나리오

2026-10-11. 상류 업무 계약, 이기종 로봇 배정, 완료 근거, 설비 대기와 운영자 재작업을 하나의 시나리오로 검증한다.

## 업무와 책임 경계

상류는 로봇 모델 대신 `interfaceId`, `interfaceVersion`, `input`으로 업무를 요청한다. Ops는 계약에 고정된 미션 버전으로 작업을 변환하고 시운전·연결·스킬·현재 실행 조건으로 후보를 제한한다. 실행 호스트와 미들웨어가 배정·실행·근거 판정을 담당한다. 설비 대역은 관측을 제공하고, 보류 해소는 사유를 남긴 운영자의 판단으로 수행한다.

로봇 모델마다 업무 정의를 복제하지 않는다. 미지원 기능을 지원하는 것처럼 처리하지 않으며, 검사 완료와 자재 배치의 물리 확인을 같은 근거로 간주하지 않는다.

## 재현되는 흐름

| 단계 | 실제 동작 | 검증하는 사실 |
|---|---|---|
| 준비 | 두 기체 선언, 프로파일 시험·활성화, 바인딩, 현장 명칭 티칭·기록 | 시운전 미완료를 능력 차이로 오인하지 않는다 |
| 공통 검사 | `StationInspection` 등록·검증·모의 실행·활성화, `station-inspection/v1`에 미션 v1 배포 | 기종별 분기 없는 공통 inspect 정의 |
| 두 요청 | 인증된 Mock MES가 같은 계약과 같은 입력을 서로 다른 주문 ID로 연속 호출 | 먼저 배정된 기체가 사용 중일 때 다른 기종에 배정; 두 실행의 계약·배포 동일 |
| 검사 결과 | 두 기체의 inspect 실행 완료와 저장 결과 수집 | 각각 PHYSICALLY_DONE / E0; E0를 품질 승인으로 해석하지 않는다 |
| 공급 후보 | `PrepareSequencedRack` 배정 가능 조회 | 시운전 완료 4족 기체도 pick_place 누락으로 제외 |
| 설비 누락 | 랙 대기 20초·OPERATOR_HOLD 정의를 검증·배포, rack_present=false에서 공급 호출 | SIGNAL_DEADLINE 인시던트와 운영자 보류 발생 |
| 재작업 | 운영자가 REWORK와 사유를 기록한 뒤 rack_present=true | 대기 재시작 후 자재 배치 관측으로 PHYSICALLY_DONE / E2 |
| 상류 재조회 | 동일 외부 주문 ID·계약·입력으로 재접수 | 기존 receiptId·jobOrderId·정규화 작업 유지, 새 작업 생성 없음 |

공통 검사는 이미 지정된 스테이션을 대상으로 하는 `inspect` 단위다. 이 정의에는 별도 `navigate_to` 단위가 없다. 이동을 포함하는 기본 업무 `InspectAsset`과 혼동하지 않는다. 공통 정의의 입력·표본·실행 정의는 [프로파일 예제](../examples/mission-profile-station-inspection.json)에 있다.

E0와 E2의 차이는 **검사 업무와 자재 공급 업무의 요구 근거 차이**다. 휴머노이드라서 E2, 4족이라서 E0인 것이 아니다. 동일 검사에서는 두 기종 모두 E0다. E2 공급 결과는 셀 대역의 관측에 근거하며 실물 PLC나 실제 제조 품질 시스템 검증을 의미하지 않는다.

## 자동 실행

기존 통합 시험과 동일하게 루트 `.env`, Java 21, 시험용 PostgreSQL을 준비하고 Ops 저장소 루트에서 실행한다.

```powershell
./gradlew.bat :e2e:test --tests dev.picasso.ops.e2e.ManufacturingScenarioTest
```

이 시험은 기존 `E2eStack`처럼 설정된 시험 DB의 public·ops·mission 스키마를 초기화한다. 개발 중인 운영 데이터가 있는 DB 대신 시험 전용 DB 설정을 사용한다. 참조 mimic, registry, 실행 호스트, Ops를 같은 JVM에서 실제 HTTP/gRPC로 연결하며, 외부 호출은 Bearer 인증을 거치는 `/integration/v1/job-orders`다. 예제 토큰은 시험 인스턴스 설정에만 주입된다.

성공 시 `build/reports/manufacturing-scenario.json`에 아래 실제 응답을 기록한다.

- `inspectionA`, `inspectionB`: 접수 상세, 적용 배포, 저장 결과와 배정 기체
- `supply`: 재작업 후 같은 접수의 저장 결과
- `reworkIncident`: 판단자·REWORK 결정이 남은 인시던트
- `reworkOperation`: 입력 사유와 처리 결과가 남은 조작 감사 기록
- `excludedManipulationCandidate`: pick_place 미지원 후보의 배제 근거

보고서는 시험 실행 당시의 기록이며, 종료된 시험 스택의 실시간 조회 화면은 아니다. 단순 선언이나 정적 성공 예시를 출력하는 방식이 아니다.

## 화면에서 확인

검증 도구의 **업무 계약과 실행 근거 비교**에서 주문을 검색하고 서로 다른 두 접수 ID를 선택한다. 접수 A/B ID는 직접 입력할 수도 있다. 최근 20건 이외의 주문은 전체 작업 요청에서 검색한다.

비교 표는 계약 ID·계약 버전·WorkMaster·고정 미션 버전·실행 배포 버전을 확인한다. 다섯 항목이 모두 존재하고 같을 때만 동일 계약·동일 실행 배포로 표시한다. 수동 요청처럼 계약 정보가 없으면 확인 불가이며, 업무 이름 하나가 같다고 동일 계약으로 판정하지 않는다. 입력 내용의 동등성이나 두 실행의 품질 승인까지 판정하는 기능은 아니다.

각 접수에는 저장 결과 버전·시각, 물리 상태, 요구/도달 근거, 배정 기체, 원문과 상세 링크를 표시한다. 현재 호스트 조회와 저장된 과거 결과를 구분한다. 결과 미수집은 완료로 표시하지 않으며 조회 실패나 접수 선택 변경 시 비교 판정을 지운다. 다시 비교할 때 최신 결과를 읽고, 이 화면 자체가 작업을 제출하거나 보류를 해소하지는 않는다.

일반 실행 스택에서 두 기종 비교를 하려면 둘 다 시운전 완료여야 한다. 기본 명부의 quadruped-01은 현장 명칭이 비어 있으므로 준비 없이 호출하면 배정되지 않는다. 참조 현장에서 티칭할 때는 런처를 내린 뒤 `site/robots.json`의 해당 기체 `site_names`를 `["dock-3", "bay-7"]`로 설정하고 다시 기동한 후 명칭 등록 기록까지 완료한다. 자동 시험은 `Site.teach`와 정식 등록 절차로 이 조건을 준비한다.

공통 검사 예제는 임무의 새 업무 등록에서 고급 JSON 입력으로 등록하고 실행 정의 검증·모의 실행·활성화를 거친다. 호출 계약은 `targets`를 `/assets`로 매핑하고 숫자 미션 버전을 배포한 뒤 공개한다. 두 요청은 첫 검사가 실행 중일 때 서로 다른 주문 ID로 호출해야 한다. 시간이 지나 첫 기체가 다시 가용해졌다면 같은 기체에 재배정될 수 있다. 기종 순환이나 균등 분배를 보장하는 스케줄러가 아니다.

Mock MES 요청 예시는 다음과 같다. 일반 실행에서는 서버의 `PICASSO_INTEGRATION_TOKEN`에 맞는 Bearer 토큰을 사용한다. 토큰이 비어 있으면 외부 API는 비활성 상태다. 두 번째 호출은 `externalOrderId`만 새 값으로 바꾸고 계약·입력을 유지한다.

```json
{
  "externalOrderId": "STATION-INSPECT-001",
  "interfaceId": "station-inspection",
  "interfaceVersion": 1,
  "input": { "assets": [{ "id": "T1", "location": "bay-7" }] }
}
```

공급 시나리오는 기존 `PrepareSequencedRack`의 랙 도착 대기·보류 템플릿과 운영 화면의 셀 신호·인시던트 판단을 사용한다. 비교 화면에는 그 흐름의 담당 화면으로 이동하는 안내가 있다.

## 검증 범위

- 제조 시나리오 통합 시험: 인증된 Mock MES → Ops → 호스트 → 참조 mimic/셀 대역 → 영속 결과 수집
- 비교 화면 단위 시험: 같은 배포/다른 배포/정보 누락/조회 실패/선택 변경/식별자 불일치
- 브라우저 전체 스택: 실제 서로 다른 계약의 접수 비교, 저장 결과 표시, 모바일 가로 넘침, 기존 단절·재기동 복구 흐름

브라우저 시험은 기존 기본 명부의 미시운전 4족 조건을 유지한다. **두 기종 공통 계약 실행은 Kotlin 통합 시험**, **실제 비교 화면은 Playwright 시험**으로 각각 검증한다.

실제 제조사 로봇, MES 제품, 실물 PLC, 안전 인증, 품질 승인, 대규모 플릿 성능과 자동 고장 복구는 이번 참조 시나리오의 검증 범위에 포함되지 않는다.
