# picasso-ops S3c: 미들웨어 시간값과 인시던트의 현장 설정 버전 설계

- 문서 상태: 설계 초안 (2026-10-09). 결정은 2026-10-09 사용자 결정(§2)
- 범위: picasso 선행 변경 P5 와 picasso-ops 의 S3c
- 요청·응답 JSON 의 정확한 모양과 스파이크가 정한 세부: S3c JSON 계약 `docs/superpowers/specs/2026-10-09-s3c-json-contract.md`(스파이크에서 정함). S2 스펙 §6 의 현장 설정 요청·응답 모양을 넓힙니다
- 근거 문서: 운영 관리 화면 설계 제안 `picasso/docs/superpowers/specs/2026-10-07-ops-console-lifecycle-design.md`(서브모듈) §8·§9·§10·§11, S2 스펙 `docs/superpowers/specs/2026-10-08-s2-site-settings-design.md`, S3b 스펙 `docs/superpowers/specs/2026-10-08-s3b-mission-versions-design.md` 와 그 JSON 계약

## 1. 목적과 범위

운영 관리 화면 설계 제안 §10 의 입증 항목 2 는 현장 값 한 세트를 화면에서 바꾸면 다음 tick 부터 적용되고, 인시던트 기록에 그 값과 버전 번호가 실리는 것입니다. S2 는 현장 설정의 저장·버전·변경 API 를 세우면서 미들웨어 시간값 셋과 인시던트의 버전 번호를 S3 로 넘겼고, S3a·S3b 스펙은 그것을 다시 S3c 로 넘겼습니다. S3c 는 picasso 선행 변경 P5 와 picasso-ops 변경을 합쳐 입증 항목 2 를 닫습니다.

입증하는 흐름은 다음과 같습니다. 엔지니어가 현장 설정 구역에서 시간값을 바꾸면 운영 서비스가 현장 설정의 새 버전을 저장합니다. 실행 호스트는 ops 스키마의 현재 버전 뷰를 1초마다 읽고, 다음 pump 부터 그 값으로 판정합니다. 설비 대기 단위가 기한을 넘겨 `SIGNAL_DEADLINE` 인시던트가 봉인되면 그 번들에 봉인하는 라운드의 설정 버전과 시간값이 실리고, 실행 호스트 REST 로 읽어 통합 시험이 확인합니다.

앞 문서와 달리 정한 것은 둘입니다. S2 스펙 §1 은 칸을 더하면 picasso 쪽 내보내기 버전과 인계 번들이 움직인다고 적었습니다. S3c 는 새 칸을 내보내기에 싣지 않고 해시에는 설정 버전이 있을 때만 줄을 더하므로, 내보내기 버전과 인계 번들이 움직이지 않습니다(T4). 제안 §11 결정 2 의 «허용 범위는 라이브러리가 쥔다» 는 지키되, 운영 서비스가 picasso 코드를 쓰지 못하므로 운영 서비스에는 범위 사본을 두고 통합 시험이 picasso 의 범위와 같은지 대조합니다(T6).

S3c 가 입증 범위에 넣지 않는 것은 다음 여섯입니다.

| 입증하지 않는 것 | 내용 |
|---|---|
| 임무별 시간값 | 사용자 결정 1. 현장 전체 한 값이며, 임무(WorkMaster)별 덮어쓰기는 나중에 키로 넓힙니다 |
| 인시던트 화면, 보류 해소, 장애 주입 | S4. 장애 주입 기능은 이 단계의 시험용 결함 주입과 별개입니다 |
| 새 칸의 내보내기 | 읽는 쪽이 생기면 내보내기 버전을 올립니다(ADR 9) |
| 모의 실행의 현장 시간값 | T10. 모의 실행은 케이퍼빌리티 기본값으로 돕니다 |
| 사용자 대기 기한(임무 정의의 `deadlineSeconds`)의 현장 설정화 | 임무 정의의 칸이며, 제안 §11 결정 2 대로 결과 판정 값과 다른 칸에 둡니다 |
| 연결 기준 시간의 picasso 이전 | 운영 서비스의 값이라 S2 그대로입니다 |

## 2. 결정 기록

### 2.1 사용자 결정 (2026-10-09)

세 건 모두 권장안을 택했습니다.

| 번호 | 물음 | 결정 | 내용 |
|---|---|---|---|
| 1 | 값의 단위 | 현장 전체 한 값 | 현장 설정 한 세트에 시간값 셋(앞·뒤 폭을 따로 세면 넷)을 두고 모든 임무에 같은 값을 적용합니다. 임무(WorkMaster)별 덮어쓰기는 나중에 키로 넓힙니다 |
| 2 | 인시던트의 설정 버전 | 기록과 실행 호스트 조회까지 | picasso 인시던트 번들에 설정 버전과 그때의 시간값을 싣고, 실행 호스트 REST 로 읽어 통합 시험이 확인합니다. 화면 표시는 S4 의 인시던트 화면에서 합니다 |
| 3 | 설정 전달 | 실행 호스트가 DB 를 읽기 전용으로 읽음 | 호스트가 ops 스키마의 현재 버전 뷰를 1초마다 읽고 다음 tick 부터 적용합니다. 쓰기는 S2 처럼 운영 서비스 혼자 합니다. 범위는 picasso 값의 사본을 운영 서비스에 두고 통합 시험이 picasso 와 같은지 대조합니다. 대가는 뷰 수준의 결합이며, 그래서 표가 아니라 뷰를 계약으로 둡니다 |

### 2.2 앞서 정해진 것

| 출처 | 내용 | S3c 에서의 자리 |
|---|---|---|
| 제안 §8 끝 | 설정 변경은 실행 진행의 단위 경계(tick)에서 적용합니다. ADR 41 의 단일 적용자 규칙과 같은 자리입니다 | T2 |
| 제안 §9 | 잘못된 값의 파급은 값마다 다릅니다. 범위는 라이브러리가 쥐고 화면은 범위 밖 값을 막습니다. 어느 버전의 설정에서 난 인시던트인지 되짚도록 버전 번호를 싣습니다 | T3, T4, §8 |
| 제안 §11 결정 2 (2026-10-07) | 현장 시간값은 데이터로 옮기되 엔지니어 권한으로만 바꿉니다. 결과 판정을 바꾸는 `evidenceWindow`·`inDoubtGrace` 는 사용자 대기 기한과 다른 칸에 둡니다. 범위 수치는 정하지 않았습니다 | T3, T6, §8 |
| S2 결정 2 | 버전 단위는 현장 설정 한 세트의 스냅숏입니다. 값 하나만 바꿔도 세트 전체가 새 버전이고, S3 에서 칸이 늘어도 같은 번호 체계입니다 | T5 |
| S2 결정 3 | ops 스키마의 덧붙이기 전용 표에 저장하고 조작 기록에도 남깁니다 | T5, T6 |
| S2 §6 | 연결 기준 시간의 범위는 운영 서비스 상수(60~3600초)입니다. 그 값의 주인이 운영 서비스이기 때문입니다 | 그대로 |
| S3b JSON 계약 | 임무 검증 결과의 `basisVersion` 은 S3b 에서 늘 null 이고 현장 설정 버전은 S3c 입니다 | 채울지와 모양은 스파이크에서 정함 |

### 2.3 기술 결정 (이 문서가 정함)

| 번호 | 주제 | 결정 | 이유 |
|---|---|---|---|
| T1 | 주입 | picasso 에 현장 시간값 한 세트 `SiteTimings`(설정 버전, 앞 폭, 뒤 폭, `inDoubtGrace`, `stallWindow`)와 그것을 주는 `SiteTimingsSource`(값이 없으면 null)를 더하고, `Middleware` 생성자에 기본값이 «없음» 인 인자로 받습니다. 값이 있으면 모든 케이퍼빌리티의 getter 를 덮고, 없으면 지금처럼 케이퍼빌리티 값을 씁니다. 기존 호출과 시험은 그대로입니다 | 사용자 결정 1. 기본값이 없음이라 picasso 의 다른 소비자가 바뀌지 않습니다 |
| T2 | 적용 시점 | `pump()` 가 시작할 때 한 번 읽어 그 라운드의 모든 판정에 같은 스냅숏을 씁니다. 바꾼 값은 다음 pump 부터입니다. 이미 단위에 저장된 근거 기한(완료 시각 + 뒤 폭)은 다시 계산하지 않습니다 | 제안 §8 의 단위 경계 적용. 한 라운드 안에서 값이 섞이지 않습니다 |
| T3 | 범위 | 허용 범위는 picasso 가 상수로 쥐고 검사 함수(`SiteTimings` 의 문제 목록)를 둡니다. 제안 수치는 앞 폭 5~120초, 뒤 폭 5~120초, `inDoubtGrace` 10~600초, `stallWindow` 30~3600초이며 스파이크에서 확정합니다. 값은 초 단위 정수입니다 | 제안 §9·§11 결정 2. 근거는 §5.1 |
| T4 | 인시던트 | `Intent` 에 `siteSettingsVersion: Long?` 과 `inDoubtGrace`·`stallWindow`(ISO-8601 문자열)를 기본값 null 로 더합니다. 셋은 현장 시간값이 있을 때만 채우고, 없으면 null 입니다. 앞·뒤 폭은 기존 두 칸에 그 라운드의 실제 값이 들어갑니다. 해시에는 설정 버전이 있을 때만 한 줄(버전과 값 넷)을 더합니다. 새 칸은 내보내기에 싣지 않습니다 | 사용자 결정 2. 설정 없이 도는 picasso 의 기존 인시던트(인계 번들 포함)의 요약과 내보내기 버전 6 이 그대로입니다. 내보내기에 안 싣는 것은 `missionVersion` 과 같은 처리입니다(읽는 쪽이 없음, ADR 9). 해시는 P3 와 다릅니다. P3 는 줄 끝에 칸을 늘 붙여 모든 요약을 바꿨고 인계 번들을 다시 산출하며 내보내기 버전을 5 에서 6 으로 올렸습니다 |
| T5 | 저장 | `ops.site_settings` 에 칸 넷(`evidence_before_seconds`, `evidence_after_seconds`, `in_doubt_grace_seconds`, `stall_window_seconds`)을 마이그레이션 V4 로 더합니다. 기존 행은 picasso 기본값(30, 15, 60, 300)으로 채웁니다 | S2 결정 2 의 스냅숏과 같은 번호 체계를 지킵니다 |
| T6 | 변경 API | `PUT /api/site-settings` 본문의 값 칸 다섯(연결 기준 시간과 시간값 넷)을 모두 선택으로 둡니다. 빠진 칸은 기준 버전의 값이고, 다섯이 다 빠지면 400 `SETTINGS_BAD_REQUEST` 입니다. 범위 밖은 기존 400 `SETTING_OUT_OF_RANGE` 이고 어느 칸인지 메시지에 적습니다. 범위는 운영 서비스의 사본 상수이고 `GET /api/site-settings` 의 `range` 에 실립니다. 조작 기록은 같은 `op` 와 기준 버전에 기준 버전으로 채운 값 다섯을 남깁니다 | 칸마다 규칙이 하나입니다. S2 의 운영 서비스 시험 일부(조작 기록 모양, 저장·변경 시그니처), 화면 시험의 PUT 본문, Playwright 의 이력 행이 바뀌며 계획이 함께 고칩니다(§10) |
| T7 | 읽기 뷰 | 운영 서비스 마이그레이션이 뷰 `ops.site_timings_current`(가장 큰 버전의 버전과 시간값 넷)를 만듭니다. 실행 호스트는 이 뷰만 읽고 표를 읽지 않습니다 | 사용자 결정 3. 뷰가 두 프로세스의 계약이고 JSON 계약 문서에 적습니다 |
| T8 | 호스트 읽기 | 호스트가 1초마다 호스트 잠금 밖에서 뷰를 읽고 picasso 범위로 검사한 뒤 통과한 값만 적용 스냅숏으로 바꿉니다. 첫 읽기가 성공할 때까지 호스트는 «미적용» 상태로 뜨고 작업 지시를 받지 않으며 배정 가능 판정의 이유에 그 사실을 보입니다(기동 순서상 호스트가 운영 서비스보다 먼저 뜨므로 기동 실패로 두지 않습니다). 그 뒤 읽기가 실패하면 마지막으로 적용한 버전을 계속 쓰고 실패를 기록합니다. 범위 밖 행은 적용하지 않고 마지막 버전을 유지하며 그 사실을 보입니다 | 사용자 결정 3. 재기동에 강합니다. 미적용 동안 작업 지시를 막는 것은 기본값으로 대신하지 않는다는 S2 스펙 §6.4 의 원칙을 지키기 위해서입니다. 통합 시험의 스택, Playwright, README 의 수동 순서가 모두 호스트를 운영 서비스보다 먼저 띄웁니다 |
| T9 | 호스트 REST | `GET /host/site-timings` 와 `GET /host/incidents` 를 더합니다. 둘 다 읽기만 합니다. 정확한 모양은 JSON 계약입니다 | 사용자 결정 2. 통합 시험이 호스트의 적용 상태와 인시던트를 밖에서 확인합니다 |
| T10 | 모의 실행 | S3b 의 모의 실행은 현장 시간값을 쓰지 않고 케이퍼빌리티 기본값으로 돕니다 | 모의 실행은 이상적 현장에서 정의가 끝까지 도는지만 봅니다. 한계로 적습니다 |

## 3. 단계와 완료 기준

| 단계 | 저장소 | 내용 | 완료 기준 |
|---|---|---|---|
| P5 | picasso | PR 하나. T1~T4, 변경 이력 §15.212, 한계 레지스터에 «현장 설정 버전 내보내기» 행, 시험 | 계약 버전과 내보내기 버전 그대로. 기존 시험이 그대로 통과하고 새 시험이 결함 주입을 잡습니다 |
| S3c | picasso-ops | PR 하나. 서브모듈을 P5 머지 커밋으로 올리고 운영 서비스·호스트·화면·통합 시험·Playwright·README 를 바꿉니다 | 통합 시험 `SiteTimingsTest` 의 다섯 단계와 Playwright 가 통과합니다 |

두 단계 모두 스크래치 스파이크에서 먼저 짓고, 계획에 기계로 옮기고, 결함 주입으로 시험을 확인합니다. 앞 단계들과 같은 방식입니다.

통합 시험 `SiteTimingsTest` 는 새 스택에서 순서대로 돕니다. 세부는 스파이크에서 정합니다.

| 순서 | 단계 | 확인 |
|---|---|---|
| 1 | 기동 직후 | 운영 서비스 현장 설정 버전 1 이 시간값 기본값(30, 15, 60, 300)을 보이고, 호스트가 버전 1 을 적용했다고 보입니다 |
| 2 | 엔지니어가 시간값을 바꿈(버전 2) | 수 초 안에 호스트 적용 버전이 2 가 됩니다 |
| 3 | `ARRIVAL_WAIT` 버전을 활성화하고(S3b 흐름) 작업 지시를 낸 뒤 신호를 켜지 않고 가상 시계를 기한 너머로 밈 | 호스트 인시던트 목록에 `SIGNAL_DEADLINE` 인시던트가 설정 버전 2 와 버전 2 의 값으로 보입니다 |
| 4 | 둘째 작업 지시가 대기 중일 때 설정을 버전 3 으로 바꾸고 호스트 적용을 기다린 뒤 기한을 넘김 | 그 인시던트는 버전 3 을 듭니다(다음 tick 적용) |
| 5 | 범위 밖 값 | 400 `SETTING_OUT_OF_RANGE` 가 돌아오고, 운영 서비스의 범위 사본이 picasso 의 범위와 같습니다(통합 시험 모듈이 picasso 를 시험 의존으로 둠) |

Playwright 는 엔지니어 모드에서 시간값 하나를 바꾸면 이력에 새 버전이 보이고 «실행 호스트 반영» 이 그 버전이 되는 것을 확인합니다.

| 항목 | 확인한 사실 |
|---|---|
| 시간값 셋의 자리 | picasso `LogicalCapability` 의 기본 getter 입니다. `evidenceWindow` 는 앞 30초, 뒤 15초이고 주석은 케이퍼빌리티 단위 설정 항목이며 현장별로 설정하는 값이고 여기는 기본값이라고 적습니다. `inDoubtGrace` 는 60초이며 `IN_DOUBT` 에서 아래 시스템에 물을 수 없을 때 물리 관측을 기다리는 유예입니다. `stallWindow` 는 5분이며 진행 정체를 사람에게 보이기까지의 유예이고 실패가 아니며 자동 조치가 없습니다 |
| 덮어쓰는 케이퍼빌리티 | main 코드에서 이 셋을 덮어쓰는 케이퍼빌리티는 없습니다. 시험 하나만 `stallWindow` 를 10초로 덮어씁니다 |
| 미들웨어가 읽는 자리 | `Middleware.kt` 의 정체 판정(`stallWindow`), `IN_DOUBT` 판정(`inDoubtGrace`, `evidenceWindow`), 단위 완료 뒤 근거 기한(`unit.evidenceDeadline = doneAt.plus(evidenceWindow.after)`, 단위에 저장됨), 근거 판정 두 곳, `IncidentLog.sealIncidents` 의 근거 윈도우 필터입니다. 모두 `execution.capability.<값>` 으로 읽습니다 |
| 인시던트 봉인 | `IncidentLog.sealIncidents` 가 라운드 끝에 번들을 봉인합니다. 의도 `Intent` 에 이미 `evidenceWindowBefore`·`evidenceWindowAfter`(ISO-8601 문자열)와 `missionVersion: Int?`(P3) 가 있습니다. `missionVersion` 은 해시에 들고 내보내기에는 실리지 않습니다(읽는 쪽이 없음, ADR 9). 내보내기 줄에는 해시 요약 `digest` 가 실립니다. 내보내기 버전은 `LedgerExport.SCHEMA_VERSION = "6"` 입니다 |
| 인시던트를 만드는 자리 | 설비 대기 단위(`pumpSignalUnit`)의 기한이 지나면 `failureClass = SIGNAL_DEADLINE` 으로 인시던트를 표시합니다. S3b 의 실행 호스트 템플릿 `ARRIVAL_WAIT`(`mission-host/src/main/resources/mission-templates/PrepareSequencedRack.arrival-wait.json`)가 신호 `rack_present` 를 기한 120초, 기한 뒤 `ABORTED` 로 기다립니다. 기한은 미들웨어 시계(호스트 시계 = site 가상 시계)로 잽니다 |
| 실행 호스트 | `MissionHost.kt` 가 `Middleware(robots, cell, now = clock::now, missions = catalog)` 를 만듭니다. 공정 잠금 하나와 250ms pump 입니다. 모의 실행(`MockRunner`)은 별도 `Middleware` 를 만듭니다. 호스트는 같은 Postgres 의 자기 스키마 `mission` 을 쓰고, 데이터 소스 값은 루트 `.env` 의 `PICASSO_DB_URL` 등입니다(운영 서비스와 같은 DB) |
| 운영 서비스 저장 | `ops.site_settings` 표에 버전, `connection_threshold_seconds`, 모드, 행위자, 사유, 기록 시각이 있고 덧붙이기 전용 트리거가 있습니다. 마이그레이션이 버전 1 = 90초를 넣습니다 |
| 운영 서비스 API | `GET /api/site-settings`(current, range, history), `PUT /api/site-settings`(본문 `baseVersion`, `connectionThresholdSeconds`, `reason`, 엔지니어 모드만). 범위 밖 400 `SETTING_OUT_OF_RANGE`, 사유 빈칸 400 `REASON_REQUIRED`, 못 읽는 본문 400 `SETTINGS_BAD_REQUEST`, 지난 기준 버전 `SETTINGS_VERSION_CONFLICT` 입니다 |
| 운영 서비스 격리 | 빌드 검사 `checkNoPicassoOnMain` 이 운영 서비스에서 picasso 코드 사용을 막습니다. 연결 기준 시간 범위는 `SiteSettingsRange`(60~3600초)입니다 |

## 5. picasso P5: 현장 시간값 주입과 인시던트의 설정 버전

### 5.1 시간값과 허용 범위

현장 시간값 한 세트 `SiteTimings` 는 설정 버전과 값 넷을 듭니다. 값은 초 단위 정수이며, 허용 범위는 picasso 가 상수로 쥐고 `SiteTimings` 의 검사 함수가 문제 목록을 돌려줍니다. 아래 범위는 제안 수치이고 스파이크에서 확정합니다.

| 값 | picasso 기본값 | 제안 범위(초) | 하한 근거 | 상한 근거 |
|---|---|---|---|---|
| `evidenceWindow` 앞 폭 | 30 | 5~120 | 셀이 슬롯을 보고 기체가 완료를 보고하는 순서가 뒤바뀌는 것을 받기 위함 | 옛 신호가 완료 근거로 들어오는 파급(제안 §9) |
| `evidenceWindow` 뒤 폭 | 15 | 5~120 | 호스트 pump 250ms 와 셀 폴링을 넘김 | 기본값의 수 배 |
| `inDoubtGrace` | 60 | 10~600 | 스파이크에서 정함 | 기본값의 수 배 |
| `stallWindow` | 300 | 30~3600 | 프로파일 보고 간격 30초 | 기본값의 수 배 |

상한들은 기본값의 4~12배 안에 둡니다. 결과 판정을 바꾸는 값은 앞·뒤 폭과 `inDoubtGrace` 이고, `stallWindow` 는 사람에게 보이는 시점만 바꿉니다. 제안 §9 의 파급대로 앞 폭을 늘리면 옛 신호가 완료 근거로 들어오고, 뒤 폭이나 `inDoubtGrace` 를 줄이면 `UNVERIFIED` 와 운영자 대기가 늡니다.

### 5.2 미들웨어 주입과 적용 시점

`SiteTimingsSource` 는 현재 값을 주거나 값이 없으면 null 을 줍니다. `Middleware` 생성자는 이것을 기본값이 «없음» 인 인자로 받습니다. 기존 호출과 시험은 바뀌지 않습니다.

`pump()` 가 시작할 때 소스를 한 번 읽어 그 라운드의 스냅숏으로 둡니다. 값이 있으면 아래 일곱 자리가 모두 케이퍼빌리티 getter 대신 스냅숏을 읽고, 없으면 지금처럼 케이퍼빌리티 값을 읽습니다. 바꾼 값은 다음 pump 부터 적용됩니다. 단위가 완료될 때 저장한 근거 기한(완료 시각 + 뒤 폭)은 그 단위가 완료된 순간의 값이며, 나중에 뒤 폭이 바뀌어도 다시 계산하지 않습니다.

| 자리(picasso `2ca7cd6`) | 값 |
|---|---|
| `Middleware.kt:794` 정체 판정 | `stallWindow` |
| `Middleware.kt:925` `IN_DOUBT` 판정의 근거 윈도우 | `evidenceWindow` |
| `Middleware.kt:931` `IN_DOUBT` 유예 | `inDoubtGrace` |
| `Middleware.kt:1284` 완료 뒤 근거 기한 | `evidenceWindow` 뒤 폭(단위에 저장) |
| `Middleware.kt:1300` 근거 판정 | `evidenceWindow` |
| `Middleware.kt:1365` 근거 판정 | `evidenceWindow` |
| `IncidentLog.kt:86` 봉인의 근거 윈도우 필터 | `evidenceWindow` |

일곱 자리 모두 pump 경로 안에 있습니다. 작업 지시 접수, 취소, 보류 해소, 반납, 재할당은 이 값을 읽지 않습니다. `IncidentLog` 는 미들웨어를 참조하지 않으므로 라운드 스냅숏을 `sealIncidents` 의 인자로 넘깁니다.

저장하는 값은 근거 기한 하나뿐입니다. 나머지는 라운드마다 그 라운드의 값을 씁니다. 그래서 바꾼 `inDoubtGrace` 는 이미 `IN_DOUBT` 인 단위에도 다음 라운드부터 미치고, 완료된 단위의 윈도우 판정은 저장된 근거 기한과 그 라운드의 앞·뒤 폭을 함께 씁니다. 이것을 의미로 정하고 시험으로 고정합니다(운영 관리 화면 설계 제안 §10 의 «다음 tick 부터 적용»).

스냅숏을 라운드 단위로 두는 것은 한 라운드 안에서 판정마다 다른 값을 읽는 일을 막기 위해서입니다. 이것은 제안 §8 의 단위 경계 적용과 같은 자리입니다.

### 5.3 인시던트

`Intent` 에 다음 칸을 더합니다.

| 칸 | 형 | 내용 |
|---|---|---|
| `siteSettingsVersion` | `Long?` | 봉인하는 라운드의 설정 버전. 설정 없이 돌면 null |
| `inDoubtGrace` | ISO-8601 문자열, 널 가능 | 봉인하는 라운드의 값 |
| `stallWindow` | ISO-8601 문자열, 널 가능 | 봉인하는 라운드의 값 |
| `evidenceWindowBefore`·`evidenceWindowAfter` | 기존 칸 | 봉인하는 라운드의 실제 값이 들어갑니다 |

새 칸 셋은 기본값이 null 이고 현장 시간값이 있을 때만 채웁니다. 기존 시험이 새 칸 없이 `Intent` 를 만들므로 기본값이 있어야 합니다. 해시에는 설정 버전이 있을 때만 한 줄(설정 버전, 앞 폭, 뒤 폭, `inDoubtGrace`, `stallWindow`)을 더합니다. 그래서 설정 없이 도는 picasso 의 기존 인시던트(인계 번들 포함)의 요약은 바뀌지 않고, 내보내기 버전 6 도 그대로입니다. 이것은 P3 와 다릅니다. P3 는 `missionVersion` 을 줄 끝에 늘 붙여 모든 요약을 바꿨습니다. 지금은 커밋된 인계 요약을 지금 인코더로 다시 계산해 대는 시험이 없으므로(두 구동을 서로 비교만 함), P5 가 `HandoffFixtureTest.bundle()` 이 만드는 번들의 `digest()` 를 `2ca7cd6` 에서 계산한 문자열로 박는 시험을 더합니다. 새 칸을 내보내기에 안 싣는 것은 `missionVersion` 과 같은 처리입니다(읽는 쪽이 없음, ADR 9).

## 6. 운영 서비스: 저장과 변경

### 6.1 표

마이그레이션 V4 가 `ops.site_settings` 에 칸 넷을 더합니다. 기존 행은 picasso 기본값으로 채웁니다.

| 칸 | 형 | 기존 행 값 |
|---|---|---|
| `evidence_before_seconds` | 정수 | 30 |
| `evidence_after_seconds` | 정수 | 15 |
| `in_doubt_grace_seconds` | 정수 | 60 |
| `stall_window_seconds` | 정수 | 300 |

칸은 `ADD COLUMN ... NOT NULL DEFAULT <기본값>` 으로 더해 기존 행을 채운 뒤 `DROP DEFAULT` 합니다. `UPDATE` 로 채우지 않습니다(덧붙이기 전용 트리거가 막음). 기본값을 지우는 것은 새 칸을 빠뜨린 `INSERT` 가 조용히 기본값으로 들어가지 않고 실패하게 하기 위해서입니다. DB 제약은 0 보다 큼만 두고 허용 범위는 넣지 않습니다(범위를 바꿀 때마다 마이그레이션이 필요해짐). 버전 체계는 S2 그대로입니다. 값 하나만 바꿔도 세트 전체가 새 버전이고, 덧붙이기 전용 트리거와 조작 기록도 그대로입니다.

### 6.2 변경 API

`PUT /api/site-settings` 본문에 정수 칸 넷을 선택으로 더하고, 규칙을 하나로 맞추려고 S2 에서 필수였던 `connectionThresholdSeconds` 도 선택으로 바꿉니다. 값 칸 다섯이 다 빠지면 400 `SETTINGS_BAD_REQUEST` 입니다.

| 본문 칸 | 필수 | 빠지면 |
|---|---|---|
| `baseVersion` | 필수(S2) | 400 `SETTINGS_BAD_REQUEST` |
| `connectionThresholdSeconds` | 선택(S2 에서는 필수) | 기준 버전의 값 |
| `reason` | 필수(S2) | 400 `REASON_REQUIRED` |
| `evidenceBeforeSeconds` | 선택 | 기준 버전의 값 |
| `evidenceAfterSeconds` | 선택 | 기준 버전의 값 |
| `inDoubtGraceSeconds` | 선택 | 기준 버전의 값 |
| `stallWindowSeconds` | 선택 | 기준 버전의 값 |

범위 밖은 기존 400 `SETTING_OUT_OF_RANGE` 이고, 메시지에 어느 칸인지 적습니다. 범위는 운영 서비스의 사본 상수이며 `GET /api/site-settings` 의 `range` 에 시간값 넷의 범위를 더해 싣습니다. 엔지니어 모드만 쓸 수 있고, 지난 기준 버전은 `SETTINGS_VERSION_CONFLICT` 입니다. 조작 기록은 같은 `op` 와 기준 버전, 그리고 기준 버전으로 채운 값 다섯을 남깁니다(S2 는 `op`·기준 버전·연결 기준 시간을 조립해 남겼습니다). 화면은 폼의 값 다섯을 늘 다 보냅니다. 본문 칸의 정확한 이름은 JSON 계약에서 정합니다.

### 6.3 읽기 뷰

운영 서비스 마이그레이션이 뷰 `ops.site_timings_current` 를 만듭니다. 가장 큰 버전 한 행의 버전과 시간값 넷을 보입니다. 실행 호스트는 이 뷰만 읽고 표를 직접 읽지 않습니다. 뷰의 칸 이름과 형이 두 프로세스의 계약이며 JSON 계약 문서에 적습니다. 운영 서비스가 뷰를 바꾸면 호스트도 바꿔야 합니다.

## 7. 실행 호스트: 읽기, 적용, 조회

### 7.1 읽기와 적용

호스트는 1초마다 호스트 잠금 밖에서 뷰를 읽습니다. 읽은 행을 picasso 의 `SiteTimings` 검사 함수로 확인하고, 통과한 값만 적용 스냅숏으로 바꿉니다. `Middleware` 는 `SiteTimingsSource` 로 그 스냅숏을 받아 다음 pump 부터 씁니다.

| 상황 | 처리 |
|---|---|
| 첫 읽기 성공 전 | «미적용». 배정 가능 판정은 기체마다 `passed=false` 에 이유 하나를 더하고, 작업 지시 제출은 새 결과 값 없이 `UNASSIGNED` 와 `excluded` 로 돌려줍니다(S3a JSON 계약 그대로). 임무 초안·검증·모의 실행·활성화·요청 조회, 셀 신호 조작과 조회, 실행 목록은 시간값을 쓰지 않으므로 미적용 동안에도 그대로 동작합니다. 호스트는 기동 안에서 첫 읽기를 한 번 동기로 시도하고, 실패하면 미적용으로 뜬 뒤 1초 주기로 다시 읽습니다. 기본값으로 대신하지 않습니다(S2 스펙 §6.4 와 같은 원칙). 도는 실행이 없으므로 미들웨어가 시간값으로 판정할 자리도 없습니다 |
| 기동 뒤 읽기 실패 | 마지막으로 적용한 버전을 계속 쓰고 실패를 기록합니다 |
| 범위 밖 행 | 적용하지 않고 마지막 버전을 유지하며, 적용 안 한 버전과 이유를 보입니다 |
| 같은 버전 | 바꾸지 않습니다 |

적용 버전은 읽기 주기가 받아들여 다음 pump 부터 쓰일 버전입니다. 모의 실행(`MockRunner`)의 별도 `Middleware` 에는 소스를 주지 않습니다(T10).

호스트 시험 세트(`HostBench`)에는 ops 스키마가 없습니다. 그래서 호스트의 읽기 코드가 main 에 뷰 이름과 칸(이름과 형) 목록을 상수로 두고, `HostBench` 는 초기화 때 `DROP SCHEMA IF EXISTS ops CASCADE` 뒤 그 상수로 대역 뷰(`VALUES` 로 만든 한 행)를 만듭니다. 범위 밖 행 시험은 그 뷰를 다시 만듭니다. 통합 시험은 `mission-host` 의 main 만 보므로 같은 상수를 읽어 실제 뷰(`information_schema`)의 칸과 대조합니다. 통합 시험의 스택은 호스트를 띄우기 전에 ops 스키마 마이그레이션을 먼저 돌립니다.

### 7.2 REST

| 엔드포인트 | 방식 | 내용 |
|---|---|---|
| `GET /host/site-timings` | 읽기 | 적용 버전, 값, 적용 시각, 마지막 읽기 시각, 읽기 실패, 적용 안 한 버전과 이유 |
| `GET /host/incidents` | 읽기 | 최신부터. 인시던트 id, 실행 id, 작업 지시 id, 단위 id, 시각, `failureClass`, `route`, 임무 버전, 설정 버전, 시간값 |

둘 다 읽기만 합니다. 정확한 모양과 목록의 상한은 JSON 계약에서 정합니다.

## 8. 화면

현장·자원 영역의 현장 설정 구역(S2)에 시간값 넷의 입력과 이력 칸을 더합니다.

| 요소 | 내용 |
|---|---|
| 입력 | 초 단위 정수 넷. 각 칸 옆에 허용 범위를 보이고 범위 밖 값은 화면이 막습니다 |
| 묶음 | 결과 판정을 바꾸는 값(`evidenceWindow` 앞·뒤 폭, `inDoubtGrace`)과 `stallWindow` 를 묶음 둘로 보입니다 |
| 문구 | 묶음마다 무엇이 바뀌는지 적습니다. 앞 폭을 늘리면 옛 신호가 완료 근거로 들어오고, 뒤 폭이나 `inDoubtGrace` 를 줄이면 `UNVERIFIED` 와 운영자 대기가 늘며, `stallWindow` 는 정체를 사람에게 보이는 시점만 바꿉니다(제안 §9) |
| 이력 | S2 의 이력 행 끝에 시간값 넷을 붙입니다(기존 칸 순서는 그대로). 변경 결과 문구는 바뀐 칸만 적고, 연결 기준 시간만 바꾼 경우는 S2 문구 그대로입니다 |
| 권한 | 엔지니어 모드만 바꿀 수 있습니다(S2 그대로) |
| 두 버전 | 운영 서비스의 최신 설정 버전과 실행 호스트의 적용 버전을 따로 보입니다 |
| 실행 호스트 반영 | 운영 서비스가 `GET /host/site-timings` 를 대신 읽어 «실행 호스트 반영: 버전 N» 을 보입니다. 호스트가 닿지 않으면 «모름» 입니다 |

인시던트 화면은 S4 입니다. 정확한 문구는 스파이크에서 정합니다.

## 11. 한계와 다음 단계

- 통합 시험의 설비 대기 기한 판정은 시간값을 쓰지 않습니다. 통합 시험이 증명하는 것은 봉인 라운드의 설정 버전과 값이 실리는 것까지이고, 시간값이 판정을 바꾸는 것은 picasso 시험이 맡습니다.
- 근거 기한은 단위가 완료된 순간의 값으로 정해지므로, 그 뒤에 바꾼 뒤 폭은 이미 완료된 단위에 미치지 않습니다(T2). 인시던트에 실리는 값은 봉인하는 라운드의 값이라, 같은 인시던트 안에서 근거 기한을 정한 값과 다를 수 있습니다.
- 완료된 단위의 윈도우 판정은 저장된 근거 기한과 그 라운드의 앞·뒤 폭을 함께 씁니다. 판정 도중 값을 바꾸면 두 버전의 값이 한 판정에 섞일 수 있습니다(§5.2 에서 의미로 정함).
- 호스트가 ops 스키마의 뷰에 결합합니다(T7). 운영 서비스가 뷰를 바꾸면 호스트도 바꿔야 합니다.
- 읽기 주기 1초 동안은 운영 서비스의 최신 버전과 호스트 적용 버전이 다를 수 있습니다. 화면이 둘을 따로 보입니다.
- 모의 실행은 현장 시간값을 쓰지 않습니다(T10).
- 새 칸은 내보내기에 싣지 않습니다. 읽는 쪽이 생기면 내보내기 버전을 올립니다(ADR 9).
- 시간값은 현장 전체 한 값입니다. 임무별 덮어쓰기는 나중에 키로 넓힙니다(사용자 결정 1).
- 허용 범위의 수치는 제안이며 스파이크에서 확정합니다(T3).
- S3b 에서 늘 null 인 임무 검증 결과의 `basisVersion` 을 S3c 에서 채울지와 그 모양은 스파이크에서 정합니다.
- 다음은 S4(장애 주입, 인시던트 화면, 보류 해소)입니다. 그 뒤 운반 임무(AMR 플릿 연동)는 별도 단계 후보입니다.
