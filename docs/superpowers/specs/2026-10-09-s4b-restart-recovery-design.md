# picasso-ops S4b: 호스트 재기동 뒤 실행 복원, 중복 명령·중복 작업 응답 막기 설계

- 범위: picasso-ops 의 S4b 와 그 선행 picasso PR P6(`Middleware.resume`). P6 은 picasso PR #86 으로 머지됐습니다(`74e4d3d`)
- 요청·응답 JSON 의 정확한 모양과 스파이크가 정한 세부: S4b JSON 계약 `docs/superpowers/specs/2026-10-09-s4b-json-contract.md`(스파이크에서 정함)
- 근거 문서: picasso 운영 관리 화면 설계 제안 `picasso/docs/superpowers/specs/2026-10-07-ops-console-lifecycle-design.md`(서브모듈) §10, S3a·S3b·S3c·S4a 스펙, picasso `docs/contract.md` §3(멱등 담보), `docs/orchestration.md` §8, picasso ADR 9·ADR 46·ADR 48, picasso-ops `8ed1b91`, picasso `195c1ee`

## 1. 목적과 범위

운영 관리 화면 설계 제안 §10 의 입증 항목 5 는 두 가지를 요구합니다. 지연, 단절, 묵은 값, 재시작을 넣으면 인시던트와 사람의 판단으로 이어져야 하고, 재시작 뒤에는 중복 명령과 중복 작업 응답을 막아야 합니다. S4a 가 앞의 셋을 입증했고 «재시작» 은 S4b 로 넘겼습니다(S4a 스펙 §1, 결정 3).

지금 실행 호스트는 미들웨어를 메모리에만 두므로, 호스트를 재기동하면 실행, 작업 응답 아웃박스, 인시던트, 운영자 판단이 모두 사라집니다. 이때 `instanceId` 가 바뀌고 `exec-N`·`resp-N`·`incident-N` 은 1부터 다시 셉니다(S3a 스펙 §12). 기체 쪽 태스크는 site 가 계속 돌리므로 끝까지 가고, 그래서 재기동 뒤에는 세 가지가 어긋납니다.

- 호스트가 도는 실행을 모르므로, 판정이 고아 태스크가 도는 기체를 비었다고 보고 새 작업 지시를 받습니다.
- 같은 작업 지시를 그대로 다시 내면 새 인스턴스가 이전 인스턴스가 이미 낸 작업 응답(보류, 미확정, 완료)을 같은 내용으로 다시 내고, 상위에서는 그것이 새 시도처럼 보입니다.
- 인시던트와 판단이 사라집니다. 판단의 행위자와 사유는 조작 기록에 남지만 인시던트 본문은 남지 않습니다.

S4b 는 이 셋을 picasso-ops 에서 막습니다. 실행 호스트는 받은 작업 지시를 자기 DB 에 실행 일지로 적고, 기동 때 정착하지 않은 것을 새 미들웨어에 다시 넣어 실행을 다시 짓습니다. 로봇 쪽은 계약의 멱등 덕에 새 명령 없이 기존 태스크에 다시 붙습니다(같은 `task_id`·`revision` 을 다시 보내면 같은 핸들, picasso `docs/contract.md` §3). 작업 응답은 호스트가 송신 기록을 남기고, 새 인스턴스가 이전 인스턴스의 마지막 송신과 같은 내용을 처음 내면 다시 내지 않습니다. 인시던트는 호스트 DB 에 사본을 두어 재기동 뒤에도 화면에 보입니다.

다시 짓기에는 picasso 쪽 빈칸이 셋 있어 선행 PR P6 으로 채웁니다. 미들웨어에는 이전 인스턴스의 실행을 넘겨받는 입구가 없습니다. `submit` 은 늘 지금 활성 임무 버전으로 계획하고, 배정 관문을 다시 걸며, 재작업 횟수(`attempt`)를 0 으로 시작합니다. 관문은 이미 집어 간 자재를 결품으로 읽어 거부할 수 있습니다. 재작업한 단위를 0 으로 다시 지으면 `@rN` 이 빠진 옛 태스크 id 로 가서 이미 끝난 첫 태스크에 붙고, 실제로 도는 재작업 태스크는 고아가 됩니다.

S4b 가 입증하지 않는 것은 아래 표와 같습니다.

| 입증하지 않는 것 | 자리 |
|---|---|
| 어댑터나 site 의 재기동 | picasso 한계 §1.3 B-1(어댑터 재시작은 범위 밖). site 의 mimic 태스크 장부도 메모리입니다 |
| 운영자 판단의 자동 재적용 | T8. 판단이 있었던 단위는 다시 짓기 뒤 판단이 다시 필요할 수 있고, 이전 판단은 인시던트 사본에 보입니다 |
| 제안·승인·소모 기록의 복원 | picasso ADR 46 이 영속을 담는 쪽 몫으로 두었고, S4b 화면은 그것을 쓰지 않습니다 |
| 작업 지시 리비전 뒤의 다시 짓기 | 운영 서비스가 리비전을 내지 않으므로 소비자가 없습니다(picasso ADR 9) |
| 실제 상위 시스템과 `ack` 왕복 | 상위 시스템 대역이 없어 송신 기록이 그 자리를 대신합니다 |
| Playwright 의 재기동 단계 | T11 |

## 2. 결정 기록

### 2.1 사용자 결정 (2026-10-09)

| 번호 | 물음 | 결정 | 비고 |
|---|---|---|---|
| 1 | 재기동 뒤 도는 실행을 어떻게 되살리는가 | 다시 제출해 다시 짓습니다. 호스트가 받은 작업 지시와 배정 기체를 자기 DB 에 적고, 기동 때 새 미들웨어에 다시 넣습니다. 로봇 쪽 멱등 덕에 새 명령이 나가지 않고, 다시 못 짓는 경우는 운영자에게 넘깁니다. picasso 선행 PR 은 작게 하나입니다 | 권장안 채택 |
| 2 | 작업 응답 중복을 어디까지 막는가 | 호스트 송신 기록까지입니다. 보낸 작업 응답을 내용 키로 적고, 재기동 뒤 같은 것은 다시 내보내지 않습니다. `ack` 를 배선하고 화면에 송신 기록을 보입니다 | 권장안 채택. 상위 시스템 대역은 만들지 않습니다 |
| 3 | 인시던트와 판단을 재기동 뒤에도 남기는가 | 호스트 DB 에 사본을 저장하고, 재기동 뒤에도 인시던트 화면에 이전 인스턴스 표시와 함께 보입니다 | 권장안 채택 |

### 2.3 기술 결정 (이 문서가 정함)

| 번호 | 주제 | 결정 | 이유 |
|---|---|---|---|
| T1 | picasso 입구 (P6) | `Middleware.resume(order, robotId, mission: ActiveMission): Submission` 을 더합니다. 같은 작업 지시 id 의 실행이 이미 있으면 `submit` 과 같이 `revise` 로 가고, 없으면 이 차례로 합니다. (가) 넘겨받은 정의의 WorkMaster 를 작업 지시와 대조해 다르면 거부합니다. (나) 기체 스냅숏(`RobotPort.snapshot`)을 한 번 읽고, 못 읽으면 실행을 만들지 않고 `RESUME_SNAPSHOT_UNREADABLE` 로 시작하는 사유로 거부합니다. (다) 근거 등급 검사만 거쳐 카탈로그 대신 넘겨받은 임무 정의와 버전으로 계획합니다. 배정 관문을 다시 걸지 않고 제안 기록도 남기지 않습니다. (라) 로봇 경로 단위마다 태스크 id `jobOrderId#unitId@rN` 의 가장 큰 N 을 `attempt` 로 맞춥니다. (마) 스냅숏에 태스크가 있는 마지막 로봇 단위보다 앞선 설비 대기 단위는 근거 등급 E0 인 채 끝난 것으로 둡니다. (바) 그 앞선 로봇 단위는 기체에서 다시 관측한 성공에 설비 근거를 다시 묻지 않고 E0 으로 닫고, 실패로 다시 관측되면 보통의 실패 경로를 탑니다. 복원의 흔적은 단위 메모가 아니라 실행 자취(`eventTrail`)에 `RESUME_ATTEMPT`, `RESUME_SIGNAL_PASSED`, `RESUME_PRIOR_ROBOT` 으로 남깁니다. 넘기는 작업 지시는 이전 인스턴스가 받은 마지막 버전이어야 합니다. 계약과 내보내기 형식은 바뀌지 않습니다 | 명령이 이미 나간 실행이라 관문은 다시 판정할 대상이 아닙니다. WorkMaster 대조를 스냅숏보다 먼저 해야 호스트가 영구 거부(GAVE_UP)와 일시 거부(DEFERRED)를 사유의 앞머리로 가릅니다. 재작업 횟수는 프로세스 안에만 있고 태스크 id 는 결정적이라 기체 스냅숏에서 되찾고(mimic 스냅숏은 종료한 태스크까지 싣습니다), N 은 태스크 id 접미사에서 읽습니다. 실행은 단위를 차례로 돌므로 뒤 로봇 단위가 기체에 있으면 앞 단위는 이미 지나간 것입니다. 지금 신호나 지금 셀 값으로 다시 판정하면 그 뒤 바뀐 값으로 보류, 중단, 미검증이 납니다. 스냅숏 없이 지으면 첫 pump 가 `@rN` 없는 id 로 가서 막으려던 고장이 다시 납니다 |
| T2 | 실행 일지 | 호스트 스키마에 `mission.execution_journal` 을 둡니다. 키는 작업 지시 id 이고, 기체 id, 작업 지시 JSON, WorkMaster, 임무 버전(`null` 은 코드 정의), 받은 인스턴스와 실행 id, 받은 시각을 둡니다. 이 표는 덧붙이기 전용이고, 이후의 일(복원, 정착, 포기)은 덧붙이기 전용 표 `mission.execution_journal_event` 에 행으로 적습니다. 제출이 새 실행으로 ACCEPTED 이면 같은 호스트 잠금 안에서 응답하기 전에 일지 행을 적고, `revise` 가 낸 Accepted 와 IDEMPOTENT 는 적지 않습니다 | 미들웨어는 제출에서 실행만 만들고, 로봇 명령은 pump 가 냅니다(`robots.start` 는 pump 경로와 `revise` 에만 있고, 운영 서비스는 리비전을 내지 않습니다). pump 도 같은 잠금을 잡으므로 «일지에 없는 실행은 명령을 낸 적이 없다» 가 성립하고, 일지가 다시 짓기의 완전한 목록이 됩니다. 덧붙이기 전용으로 두면 S3b 의 스키마 관례를 지키고, 무엇이 언제 일어났는지도 지워지지 않습니다 |
| T3 | 기동 복원 | `MissionHost.start()` 가 pump 를 켜기 전에 복원을 하며, 정착도 포기도 없는 일지 행을 받은 순서대로 `resume` 합니다. 임무 정의는 일지의 임무 버전으로 `mission.mission_version` 에서 읽습니다(`null` 이면 코드 정의). 결과는 RESTORED(새 실행 id), DEFERRED(기체 스냅숏을 못 읽음), GAVE_UP(그 밖의 거부와 정의를 못 읽음) 셋이고, 일지 이벤트로 남깁니다. DEFERRED 행은 pump 마다 다시 시도하고, RESTORED 가 되면 이벤트를 하나 더 적습니다. 이번 기동의 복원 보고는 `GET /host/executions` 에 실립니다 | 복원은 빈 생성 안에서 끝나므로, 웹 서버가 열리기 전에 복원이 끝나고 판정이 도는 실행을 압니다. 기동이 중간에 실패해 다시 떠도 같은 행에서 같은 결과가 나야 하므로, 결과는 행의 내용과 기체 스냅숏만으로 정해집니다 |
| T4 | 다시 짓지 못한 실행의 기체 | DEFERRED·GAVE_UP 행의 기체는 판정에서 «복원 못 한 실행이 있다» 로 뺍니다. GAVE_UP 행의 기체는 그 스냅숏에서 그 작업 지시의 종료되지 않은 태스크(id 가 `jobOrderId#` 로 시작하고 `@rN` 접미사를 포함)가 없어지면 판정에서 더 빼지 않습니다. 종료 상태는 용어집의 넷(`SUCCEEDED`, `FAILED`, `CANCELLED`, `CANCELLED_RECOVERY_FAILED`)뿐이며, 사람을 기다리는 `RETRIABLE`·`NEEDS_INTERVENTION` 태스크는 종료하지 않은 태스크라 남아 있는 동안 계속 뺍니다. 스냅숏은 그 판정 때만 읽고, 못 읽으면 계속 뺍니다 | 미들웨어가 모르는 고아 태스크가 도는 기체에 새 작업 지시가 들어가지 않게 하고, 고아 태스크가 끝나면 기체를 돌려받습니다 |
| T5 | 중복 명령 | 새 명령을 막는 장치를 호스트에 더하지 않습니다. 다시 지은 실행은 단위마다 같은 태스크 id·같은 리비전으로 `StartTask` 를 보내고, 그러면 기체가 기존 핸들을 돌려줍니다. 시험은 site 가 읽어 주는 mimic 태스크 갱신 로그(`Site.taskHistory`, 엔진 잠금 아래 읽기만 함)로 셋을 봅니다. 가상 시계를 밀기 전 재기동 앞뒤의 태스크 id 집합이 같고, 재기동 전 로그가 재기동 뒤 로그의 앞에 그대로 있고, 태스크 id 마다 `ACCEPTED` 가 한 번뿐입니다 | 계약이 이미 막고, 호스트가 따로 막으면 계약의 멱등이 실제로 동작하는지 시험하지 못합니다 |
| T6 | 송신 기록 | 호스트 스키마에 덧붙이기 전용 `mission.job_response_log` 를 둡니다. pump 뒤 같은 잠금 안에서 미들웨어 `pending()` 의 응답마다 내용 키를 만듭니다. 내용 키는 작업 지시 id, 버전, 물리 상태, 요구·도달 근거 등급, 완료·미검증 단위 id, 미완 단위 id 집합, 미확정 단위 id, 운영자 필요, 남은 파지 종류, 막은 것입니다. 새 인스턴스가 그 작업 지시에 대해 처음 내는 응답을 그 작업 지시의 가장 최근 송신 행(인스턴스 무관)과 견줍니다. 내용 키가 같으면 «재기동 중복» 으로 적고 송신하지 않으며, 그 밖에는 송신으로 적습니다. 어느 쪽이든 적은 뒤 `ack` 합니다 | 상위 시스템이 없으므로 송신 기록이 전선 자리를 대신합니다. 재기동이 만드는 중복은 «상위가 이미 가진 마지막 상태를 새 인스턴스가 다시 알리는 것» 이므로 첫 응답 하나만 보고, 그 뒤의 같은 내용(재작업 뒤 다시 보류 등)은 새로 일어난 일이라 거르지 않습니다. `version` 을 시도 구분에 빌려 쓰지 않으므로(ADR 48) 인스턴스로 가릅니다. 응답 id 와 `connection` 은 인스턴스마다 달라지고, 미완 단위의 사유는 실패 분류가 없으면 계속 쌓이는 단위 메모라 인스턴스마다 달라질 수 있어 키에서 뺍니다 |
| T7 | 인시던트 사본 | 호스트 스키마에 덧붙이기 전용 `mission.incident_copy` 와 `mission.incident_copy_resolution` 을 둡니다. 사본의 키는 (인스턴스, 인시던트 id)이고, 실행 id, 작업 지시 id, 단위 id, 봉인 때의 상세 본문 JSON 을 둡니다. pump 뒤 기록 트랜잭션에서 새로 봉인된 인시던트를 적습니다(인시던트 목록은 덧붙이기만 하므로 마지막으로 적은 색인 뒤의 것입니다). 번들에 `resolution` 이 있는데 판단 행이 없는 것은 판단 행을 적습니다. `GET /host/incidents` 는 이전 인스턴스의 사본을 `earlier` 로 더 싣습니다. 상세 `GET /host/incidents/{id}` 는 `instanceId` 질의가 이전 인스턴스면 사본을 돌려줍니다. 사본의 판단과 보류 여부는 읽을 때 판단 행으로 다시 계산하고, 이전 인스턴스 인시던트는 보류 중이 아닙니다 | `incident-N` 도 재기동하면 1부터 다시 세므로, 인스턴스와 짝을 지어야 겹치지 않습니다. 봉인 때의 판단 칸은 낡으므로 판단을 따로 적습니다. 판단 행은 pump 뒤에 적어야 미들웨어 판단과 DB 쓰기 사이에서 죽어도 다음 기록에서 빠지지 않습니다(그 사이에 프로세스가 죽으면 판단은 조작 기록에만 남습니다) |
| T8 | 판단의 인스턴스 | 판단 요청에 `instanceId` 를 싣고, 운영 서비스가 상세에서 받은 값을 넘깁니다. 호스트는 빠지면 400 `BAD_REQUEST` 로 거부하고(운영 서비스는 400 `RESOLVE_BAD_REQUEST`, 검사 순서는 결정, `instanceId`, 사유), 지금 인스턴스와 다르면 409 `INSTANCE_MISMATCH` 로 거부합니다. 운영자 판단, 설비 대기의 기한 시작 시각, 근거 윈도우의 요청 시각은 다시 짓기 뒤 새 인스턴스의 값입니다. 판단을 자동으로 다시 넣지 않습니다 | `exec-N` 은 인스턴스마다 다시 세므로, 이전 인시던트의 `exec-k` 가 새 인스턴스의 다른 실행을 가리킬 수 있습니다. 사람의 판단은 그때의 사실에 걸린 것이므로, 다시 본 사실로 사람이 정해야 합니다. 이전 판단은 사본과 조작 기록에 남습니다 |
| T9 | 운영 서비스 | `GET /api/incidents` 와 상세는 `earlier` 와 `instanceId` 질의를 중계합니다(호스트 클라이언트의 상세 조회에 질의 인자를 더합니다). 판단 요청은 `instanceId` 를 받아 넘기고, 409 `INSTANCE_MISMATCH` 는 조작 기록에 REJECTED 로 남깁니다. 판단의 재조회(S4a T6)는 목록의 `instanceId` 가 요청한 인스턴스와 같을 때만 `incidents` 를 보고, 다르면 `earlier` 에서 그 인스턴스의 사본과 판단을 봅니다. `GET /api/job-responses` 를 더해 송신 기록을 중계합니다. 빈 `instanceId` 질의는 400 `INCIDENT_BAD_REQUEST`, 송신 기록의 빈 `jobOrderId` 와 범위 밖 `limit` 은 400 `JOB_RESPONSE_BAD_REQUEST` 로 호스트를 부르지 않고 거부합니다. 작업 지시 재조회 규칙은 바꾸지 않습니다 | T2 덕에 재조회가 다시 지은 실행을 작업 지시 id 로 찾으므로 «명령이 나갔는데 반영 안 됨» 이 생기지 않습니다. 재조회 때 호스트가 아직 안 떠 있으면 기존대로 확인 행을 붙이지 않습니다. 판단 재조회는 재기동이 끼면 새 인스턴스의 같은 `exec-k` 를 잘못 맞출 수 있으므로 인스턴스로 가릅니다 |
| T10 | 화면 | 실행 목록 위에 이번 기동의 복원 보고를 보입니다(다시 지은 수, 미룬 것과 포기한 것의 사유). 다시 지은 실행에 이전 실행 id 를 표시합니다. 인시던트 구역에 이전 인스턴스 부분을 읽기 전용으로 둡니다. 운영 영역에 송신 기록 구역(작업 지시별 송신과 재기동 중복)을 둡니다 | 운영자가 재기동이 있었는지, 무엇을 다시 지었는지, 무엇이 거르기로 빠졌는지 화면에서 바로 봐야 합니다 |
| T11 | Playwright | 재기동 단계를 넣지 않고, 송신 기록 구역이 보이는지만 기존 흐름에 더합니다. 재기동은 e2e 가 `E2eStack.restartHost()` 로 입증합니다 | Playwright 는 프로세스마다 런처로 띄우고, 호스트만 끄고 켜는 도우미가 없습니다. e2e 는 같은 DB·site 를 두고 호스트만 다시 띄우며, 가상 시계로 결정적입니다 |

## 3. 단계와 완료 기준

| 단계 | 저장소 | 내용 | 완료 기준 |
|---|---|---|---|
| P6 | picasso | `Middleware.resume`, 한계 레지스터 행, 설계 문서 §15 변경 이력 | 미들웨어 시험이 다음을 보입니다. 넘겨받은 임무 버전으로 계획하고, 관문을 걸지 않으며, 태스크 id 접미사의 가장 큰 재작업 횟수를 맞춥니다. 앞선 설비 대기 단위를 근거 등급 E0 인 채 끝난 것으로 두고, 스냅숏을 못 읽으면 Rejected 이고 실행이 없습니다. 같은 작업 지시 id 면 revise 로 가고, 내보내기 형식 6 과 골든 다이제스트가 그대로입니다 |
| S4b | picasso-ops | 실행 일지, 기동 복원, 송신 기록, 인시던트 사본, 판단의 인스턴스, 운영 서비스 중계, 화면 | e2e 재기동 시험이 아래 여섯을 보입니다 |

e2e 재기동 시험의 여섯은 다음과 같습니다. 복원 직후 단위는 모두 대기에서 시작하므로, pump 가 기체를 다시 관측할 때까지 기다린 뒤 봅니다.

1. 도는 실행이 있을 때 호스트를 다시 띄우면, 같은 작업 지시 id 의 실행이 새 실행 id 로 다시 섭니다. 이미 끝난 단위는 끝난 대로, 도는 단위는 도는 대로 서고, 이어서 끝까지 갑니다. 앞서 통과한 설비 대기가 있으면 최종 응답의 도달 근거 등급은 E0 입니다.
2. 가상 시계를 밀기 전 재기동 앞뒤의 태스크 id 집합이 같고, 재기동 전 태스크 갱신 로그가 그대로 앞에 있으며, 태스크 id 마다 `ACCEPTED` 가 한 번뿐입니다.
3. 운영자 보류에 선 실행을 다시 띄우면, 기한이 다시 지난 뒤 새 인스턴스의 보류 응답이 재기동 중복으로 적히고 송신으로는 두 번 적히지 않습니다. 두 번 다시 띄워도 같습니다.
4. 설비 대기 보류를 재작업으로 판단한 뒤 다시 띄우면, 대기가 새 기한으로 다시 서고 옛 인시던트와 그 판단은 `earlier` 에만 있습니다. 로봇 단위의 `@rN` 맞추기는 P6 미들웨어 시험과 mission-host 시험이 입증합니다(e2e 에는 로봇 단위를 보류로 세울 수단이 없습니다).
5. 작업 지시를 받은 뒤 다른 임무 버전을 활성화하고 다시 띄우면, 받은 때의 임무 버전으로 다시 짓습니다.
6. 이전 인스턴스의 인시던트와 그 판단이 재기동 뒤 `earlier` 에 보이고, 이전 인스턴스를 실은 판단 요청은 409 `INSTANCE_MISMATCH` 입니다.

## 5. picasso P6: `Middleware.resume`

`resume` 은 담는 쪽이 재기동 뒤 자기 기록으로 실행을 다시 짓는 입구입니다. 받는 것은 작업 지시, 기체 id, 임무 정의와 버전(`ActiveMission`)이고, 넘기는 작업 지시는 이전 인스턴스가 받은 마지막 버전이어야 합니다. 같은 작업 지시 id 의 실행이 이미 있으면 `submit` 과 같이 `revise` 로 가고 같은 버전이면 Idempotent 입니다.

없으면 넘겨받은 정의의 WorkMaster 를 작업 지시와 대조하고, 기체 스냅숏을 한 번 읽고, 근거 등급 검사(`evidenceRefusal`)를 거친 뒤 넘겨받은 정의로 계획해 실행을 만듭니다. 스냅숏을 못 읽으면 실행을 만들지 않고 `RESUME_SNAPSHOT_UNREADABLE` 로 시작하는 사유로 거부합니다. 배정 관문은 걸지 않고 제안 기록도 남기지 않습니다.

실행을 만든 뒤 로봇 경로 단위마다 스냅숏 태스크 id 가운데 `jobOrderId#unitId` 이거나 `jobOrderId#unitId@rN`(N 은 `[1-9]\d*`)인 것을 찾아 가장 큰 N(접미사가 없으면 0)을 `attempt` 에 넣습니다. 스냅숏에 태스크가 있는 마지막 로봇 단위를 찾아, 그보다 앞선 설비 대기 단위는 근거 등급 E0 인 채 끝난 것으로 둡니다. 그보다 앞선 로봇 단위는 pump 가 기체에서 성공을 다시 관측하면 설비 근거를 다시 묻지 않고 E0 으로 닫습니다. 실패로 다시 관측되면 보통의 실패 경로를 탑니다. 이번 인스턴스가 관측하지 않은 근거를 주장하지 않으므로, 그런 실행의 작업 응답은 도달 근거 등급이 E0 이고 요구가 E2 인 작업 지시는 요구에 못 미친 채 정착합니다. 이 사실들은 실행 자취에 `RESUME_ATTEMPT`, `RESUME_SIGNAL_PASSED`, `RESUME_PRIOR_ROBOT` 으로 남깁니다.

KDoc 은 이것이 실행 상태를 되살리는 일이 아니라 같은 정체성으로 다시 짓는 일임을 밝힙니다. 운영자 판단, 감수한 결함, 승인 소모 기록, 근거 확인 결과, 근거 윈도우의 요청 시각, 설비 대기의 기한 시작 시각은 넘어오지 않습니다.

picasso 문서는 한계 레지스터에 내부 행 `§15.213 · 재기동 뒤 다시 짓기` 를 더하고 설계 문서 §15 에 변경 이력 213 을 더했습니다. 시험은 `ResumeTest` 17개이고 계약 proto 와 내보내기 형식은 바뀌지 않았습니다.

## 6. 실행 호스트

### 6.1 저장소

`V2` 마이그레이션이 덧붙이기 전용 표 다섯(`execution_journal`, `execution_journal_event`, `job_response_log`, `incident_copy`, `incident_copy_resolution`)을 더하고, V1 과 같은 트리거로 갱신과 삭제를 막습니다. `MissionStore` 에 임무 버전 하나를 읽는 함수를, 카탈로그에 (WorkMaster, 버전 또는 `null`)로 `ActiveMission` 을 만드는 함수를 더합니다. `MissionHost` 는 이 저장소를 생성자로 받습니다.

### 6.2 실행 일지

새 실행의 ACCEPTED 제출은 응답 전에 일지 행을 적고, 작업 지시 JSON 은 picasso `JobOrder` 의 칸 그대로입니다. 일지 쓰기가 실패하면 제출은 500 이고 이미 만든 실행은 남습니다. 이 경우는 한계(§11)입니다.

pump 뒤 같은 잠금 안에서 한 트랜잭션으로 송신 기록, 인시던트 사본, 정착 이벤트를 적습니다. 정착 이벤트는 물리 상태가 정착한 실행 가운데 아직 정착 이벤트가 없는 것만 적습니다. 트랜잭션이 실패하면 아무것도 `ack` 하지 않고, 다음 pump 에 다시 합니다.

### 6.3 기동 복원

복원은 `MissionHost.start()` 안에서 pump 를 켜기 전에 돕니다. 행마다 일지의 임무 버전으로 정의를 읽고 `resume` 을 부릅니다. Accepted 이면 RESTORED 이고, 기체 스냅숏을 못 읽은 Rejected 는 DEFERRED 이며, 그 밖의 Rejected 와 정의를 못 읽은 것은 GAVE_UP 으로 사유를 남깁니다. 새 미들웨어라 Idempotent 는 생기지 않습니다.

복원 보고는 이번 인스턴스, 복원 시각, 행마다 작업 지시 id, 기체 id, 이전 인스턴스와 실행 id, 결과, 새 실행 id 또는 사유이고, `GET /host/executions` 의 `restore` 칸에 실립니다. DEFERRED 가 나중에 RESTORED 가 되면 그 칸도 바뀝니다.

### 6.4 송신 기록

§2.3 T6 과 같습니다. `GET /host/job-responses` 는 작업 지시별 송신 행을 돌려주고, 행은 인스턴스, 응답 id, 내용 키의 칸, 적은 시각, 송신인지 재기동 중복인지입니다. 정확한 모양은 JSON 계약에 둡니다.

### 6.5 인시던트 사본과 판단

§2.3 T7·T8 과 같습니다. 사본의 상세 본문은 봉인 때 호스트가 만든 상세(S4a 의 `IncidentDetailView`)와 같은 모양입니다. 판단 REST 는 본문의 `instanceId` 가 지금 인스턴스일 때만 받습니다.

## 7. 운영 서비스

T9 와 같습니다. 새 쓰기 조작이 없으므로 조작 기록 op 를 더하지 않습니다. 판단 조작(`RESOLVE_OPERATOR_HOLD`)은 본문에 `instanceId` 가 필요합니다. 호스트 불통이면 기존과 같이 503 `HOST_SILENT` 입니다.

## 8. 화면

- 실행 목록: 복원 보고 띠를 두고, «재기동: 이전 인스턴스의 실행 n건을 다시 지었습니다» 와 미룬 것, 포기한 것의 사유를 보입니다. 다시 지은 실행 행에 «이전 exec-k» 를 표시합니다.
- 인시던트 구역: «이전 인스턴스» 부분을 둡니다. 목록과 상세는 읽기 전용이고 판단 양식이 없습니다. 지금 인스턴스의 판단 양식은 상세의 `instanceId` 를 같이 보냅니다.
- 송신 기록 구역: 작업 지시를 고르면 송신 행과 재기동 중복 행을 보입니다.

## 9. 오류 처리

| 상황 | 동작 |
|---|---|
| 일지 쓰기 실패 | 제출 500 `JOURNAL_WRITE_FAILED`. 실행은 남고 다시 짓기 목록에서 빠집니다(한계) |
| 복원 중 기체 스냅숏을 못 읽음 | DEFERRED. pump 마다 다시 시도하고, 그동안 그 기체를 판정에서 뺍니다 |
| 복원 중 임무 버전 행이 없음, 근거 등급 거부 | GAVE_UP 과 사유. 그 작업 지시의 종료되지 않은 태스크가 기체에 남아 있는 동안 그 기체를 판정에서 뺍니다 |
| pump 뒤 기록 트랜잭션 실패 | 경고 기록. `ack` 하지 않고 다음 pump 에 다시 합니다(인스턴스·id 키라 겹치지 않습니다) |
| 이전 인스턴스를 실은 판단 | 호스트 409 `INSTANCE_MISMATCH`. 운영 서비스는 조작 기록에 REJECTED 로 남깁니다 |

## 10. 시험

- picasso P6: 미들웨어 단위 시험입니다(§3 P6 완료 기준).
- mission-host: 일지 쓰기와 정착 이벤트, 복원 보고의 세 결과, DEFERRED 재시도, 판정 제외, 송신 기록의 첫 응답 거르기와 `ack`, 사본 쓰기와 판단 행, `earlier`·`instanceId` 상세, `INSTANCE_MISMATCH` 를 시험합니다.
- ops-service: 중계와 `instanceId` 전달, 인스턴스로 가르는 판단 재조회를 시험합니다.
- S4a 시험 수정: 호스트 `IncidentResolveTest` 와 e2e `FaultIncidentTest` 의 판단 요청이 `instanceId` 를 싣습니다. S4a Playwright 판단 단계는 화면의 판단 양식이 `instanceId` 를 실으므로 바꾸지 않습니다.
- ui: 복원 띠, 이전 인스턴스 부분, 송신 기록 구역을 시험합니다.
- site: 기체 태스크 갱신 로그 읽기(`Site.taskHistory`).
- e2e: `RestartRecoveryTest` 가 §3 의 여섯을 보입니다. 넷째부터 여섯째는 보류 실행 하나를 이어 쓰고, 같은 인스턴스에서 재작업 뒤 다시 선 보류는 송신, 그 뒤 재기동한 보류는 재기동 중복임을 함께 봅니다. 실제 시간 대기는 다시 관측 폴링(상한 10초)과 검증 확인뿐입니다.
- Playwright: 송신 기록 구역 확인 한 단계를 더합니다.
- 결함 주입은 스파이크에서 전체를 돌립니다. 계획의 워크트리에서는 모듈마다 대표 한 건을 돌립니다.

## 11. 한계와 다음 단계

- 일지 쓰기가 실패하면 그 실행은 다시 짓기에서 빠집니다.
- 판단은 자동으로 다시 넣지 않습니다(T8).
- 도는 설비 대기의 기한과 근거 윈도우는 다시 짓기 뒤 새로 시작합니다. 기한으로 선 보류는 재기동 뒤 기한만큼 늦게 다시 서고, 그동안 화면에는 도는 것으로 보입니다.
- 앞서 통과한 설비 대기는 근거 등급 E0 으로 다시 서므로, 다시 지은 실행의 작업 응답은 도달 근거 등급이 E0 입니다. 재기동 전의 E2 판독은 이번 인스턴스가 관측하지 않았습니다.
- 마지막 로봇 단위보다 뒤의 설비 대기는 다시 기다립니다. 대기를 통과한 직후 다음 로봇 단위가 시작되기 전에 재기동하면 바뀐 신호로 보류나 중단이 날 수 있습니다.
- 송신 기록은 새 인스턴스의 첫 응답만 가장 최근 송신과 견줍니다. 재기동 직후 다른 응답이 먼저 나면 그 뒤의 같은 내용은 송신됩니다.
- 어댑터나 site 가 같이 재기동하면 기체 쪽 장부가 사라지고, 같은 태스크 id 가 새 작업이 됩니다(picasso 한계 §1.3 B-1).
- 앞선 로봇 단위는 다시 관측한 성공을 설비 근거 없이 E0 으로 닫습니다. 재기동 전에 설비로 확인했더라도 그 결과는 넘어오지 않습니다.
- 계약의 `GetSnapshot` 은 종료한 태스크를 싣는다고 정하지 않으므로, 종료한 태스크를 빼는 발신자에서는 마지막 로봇 태스크 앞의 로봇 단위가 새 태스크로 다시 나갑니다(picasso 한계 §15.213). mimic 은 싣습니다.
- 플릿 단위는 마지막 로봇 단위를 정할 때 세지 않고 재작업 횟수도 되찾지 않습니다. S4b 는 플릿 WorkMaster 를 받지 않습니다.
- 판단 직후 다음 pump 의 기록 전에 재기동하면 판단은 사본에 남지 않고 조작 기록에만 남습니다. 그 판단의 재조회는 «반영 안 됨» 으로 남습니다.
- 일지, 송신 기록, 사본에 보존 기한이 없습니다.
- 실행 호스트가 `start()` 에서 복원과 pump 를 시작한 뒤 웹 포트를 열지 못하면(예: E2eStack 의 재시도), 한 번도 응답하지 않은 그 인스턴스가 다음 기동의 `previousInstanceId` 가 됩니다. 다시 지은 행이 있으면 복원이 그 인스턴스로 RESTORED 이벤트를 이미 적었기 때문입니다.
