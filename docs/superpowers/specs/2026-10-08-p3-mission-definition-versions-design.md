# picasso P3: 임무 정의 데이터와 임무 버전 설계

- 문서 상태: 설계 초안 (2026-10-08). 결정은 2026-10-08 사용자 결정(§2)
- 범위: picasso 선행 변경 P3(picasso PR 1개, 구현 묶음 둘: P3a·P3b). picasso-ops 의 S3(실행 호스트, 버전 저장, 편집 화면, 배정 가능)는 다음 설계 문서
- 근거 문서: picasso `docs/superpowers/specs/2026-10-07-ops-console-lifecycle-design.md`(이하 운영 관리 화면 설계 제안) §5·§6·§8.4·§9·§10·§11 · picasso `docs/adr/0032-safety-boundary.md`(ADR 32)·`0036`(ADR 36)·`0038`(ADR 38) · S1 스펙 §1 · S2 스펙 §10

## 1. 목적과 범위

S1 스펙 §1 의 덩어리 표에서 S3 는 «임무 버전» 입니다. 입증 항목 3·4 에 대응합니다. 운영 관리 화면 설계 제안 §10 은 항목 3 을 «임무 하나(`PrepareSequencedRack`)를 데이터 판으로: 모의 실행(mimic) → 활성화 → 도는 실행 중 새 판 전환 → 옛 실행은 옛 판으로 끝난다» 로 적었습니다. 같은 자리에 «이것이 핵심입니다» 라고 적었습니다. 항목 4 는 «잘못된 변경 하나(신호 사양에 없는 신호 참조)가 활성화에서 거절된다» 입니다.

2026-10-08 사용자 결정으로 S3 를 나눕니다. 임무 버전을 먼저 picasso 에 짓습니다. picasso 시험 위에서 입증합니다. picasso-ops 의 호스트와 화면은 그 위에 얹습니다. 이 문서는 picasso 쪽 P3a·P3b 만 다룹니다.

P3 가 입증하는 것은 4가지입니다. 모두 picasso 시험 위에서 입증합니다.

| 번호 | 입증하는 것 |
|---|---|
| 1 | 노드형 JSON 임무 정의를 읽어 실행 단위로 펼칩니다. 데이터로 옮긴 `PrepareSequencedRack` 이 코드와 같은 계획을 냅니다 |
| 2 | 설비 대기 노드가 신호를 기다립니다. 기한이 지나면 정해 둔 상태로 갑니다 |
| 3 | 검증기가 5가지 검사로 잘못된 정의를 활성화에서 거부합니다. 거부는 종류와 후속 행동으로 보입니다 |
| 4 | 버전 1 실행이 도는 중 버전 2 를 활성화하면 새 작업 지시는 버전 2 로 돕니다. 옛 실행은 버전 1 로 끝납니다. 인시던트 기록이 어느 버전에서 일어났는지 싣습니다 |

P3 가 입증하지 않는 것은 6가지입니다.

| 입증하지 않는 것 | 내용 |
|---|---|
| 화면에서의 편집·모의 실행·활성화 | S3(picasso-ops)의 일입니다 |
| 운영 실행 호스트 | S3 의 일입니다. 지금 미들웨어를 도는 호스트는 시험 소스의 `ScenarioHost` 뿐입니다(picasso 한계 레지스터 §15.176) |
| `DeliverContainer`·`InspectAsset` 의 데이터 이전 | 코드 정의로 남깁니다(결정 (가), §10) |
| 분기·병렬 | 운영 관리 화면 설계 제안 §6 이 5가지 의미를 먼저 정한 뒤 연다고 적었습니다 |
| 미들웨어 시간값 셋의 데이터화와 인시던트의 현장 설정 버전 | S3c 의 일입니다 |
| 실제 하드웨어 PLC 와의 신호 대조 | P3 에 없습니다 |

이 문서가 정한 것은 13가지입니다.

| 번호 | 정한 것 | 이유 |
|---|---|---|
| (가) | 데이터로 옮기는 정의는 `PrepareSequencedRack` 하나입니다. `DeliverContainer`·`InspectAsset` 은 코드 케이퍼빌리티로 남아 같은 카탈로그에 함께 섭니다. 스키마는 `PrepareSequencedRack` 과 설비 대기를 표현하는 만큼만 짓습니다 | 셋을 다 덮으려면 반복 한 번에 노드 여럿, 단위 id 접미사, 작업 지시 파라미터 값, 조건부 포함, 플릿 경로가 더 필요합니다 |
| (나) | 코드의 `PrepareSequencedRack` 클래스는 지우지 않습니다. 실패 분류 상수(`NO_SOURCE_FOR_MATERIAL` 등)도 그대로 둡니다 | 동등성 시험의 기준이고 기본 케이퍼빌리티 목록에 남습니다. `docs/diagrams/mission.svg` 와 `DocumentClaimsTest` 가 `LogicalCapability.kt` 본문에서 그 이름을 찾습니다 |
| (다) | 설비 대기의 «기한 뒤 갈 상태» 는 `OPERATOR_HOLD` 와 `ABORTED` 둘입니다. `OPERATOR_HOLD` 면 대기 단위가 `OPERATOR_HOLD` 가 되어 라인이 멈추고 운영자 판단을 기다립니다. `ABORTED` 면 대기 단위는 `FAILED`(실패 분류 `SIGNAL_DEADLINE`)로 남고, 남은 `PENDING` 단위를 먼저 `ABORTED` 로 바꾼 뒤 기존 중단 경로(`abort`)로 가고, 같은 라운드에서 멈추는 가드를 둡니다. 실행의 결과는 `ABORTED` 로 확정됩니다. 이 중단은 취소 요청이 아니므로 취소 보고(`CancelReport`, `lastCancel`)는 남기지 않습니다 | 엔진은 `FAILED` 단위 뒤에도 다음 단위를 그대로 내보냅니다. 진행 루프는 도는 단위가 끝난 뒤 취소 여부만 보고(614-626), 그 뒤 첫 `PENDING` 을 골라 출발시키며 `startUnit` 이 `physicalState` 를 `RUNNING` 으로 덮습니다(640-662, 1047). `abort` 는 `physicalState=ABORTED` 와 통보만 하고 라운드를 끝내지 않습니다(1455-1476). 그래서 남은 `PENDING` 을 먼저 `ABORTED` 로 바꾸고 같은 라운드에서 멈춰야 합니다. 다음 라운드부터 진행 루프는 종료된 실행을 건너뛰고(580), 리비전은 종료된 실행이라 거부됩니다(402). 라인을 멈추는 것은 `OPERATOR_HOLD` 뿐입니다. 신호를 못 본 채 다음 로봇 단계를 하면 대기를 둔 뜻이 없습니다. 정산을 기존 규칙에 맡기면 `[FAILED, ABORTED…]` 가 부분 완료(`PARTIAL`, `Middleware.kt:1102-1105`)가 되어 완료 단위가 없는데 부분 완료로 알리고, 리비전으로 다시 열립니다 |
| (라) | 설비 대기의 신호는 이름으로 읽습니다. 셀 신호 포트에 메서드 하나를 기본 구현(없음)으로 더합니다 | 지금 셀 신호 포트(`CellSignals`)는 자리 이름으로 슬롯 점유를 볼 뿐 이름 있는 신호가 없습니다. 기본 구현을 두면 기존 구현체가 깨지지 않습니다 |
| (마) | 안전 검사는 «안전 신호를 기다리는 대기 노드를 거부» 입니다 | 안전 기능은 이 소프트웨어 계약을 거치지 않습니다(ADR 32, picasso 한계 레지스터의 의도적 제외) |
| (바) | 자원 검사는 정의에 고정으로 적힌 자리(대기 신호의 자리)의 바닥 소유를 관문과 같은 규칙으로 봅니다. 바닥 소유는 3값(`Declared`·`Unowned`·`NotDeclared`, `FloorOwnership.kt:19-36`)이고 관문은 `Unowned` 만 막습니다(`AdmissionGate.kt:103`). 자원 검사도 `Unowned` 면 거부, `Declared`·`NotDeclared` 면 통과입니다. 신호에 자리가 없으면 자원 검사는 그 노드를 건너뜁니다 | 작업 지시에서 오는 자리(슬롯·제시 자리)는 실행 때 기존 관문(`unownedFloor`)이 봅니다. 기본값(`FloorOwnership.None`)에서는 모든 자리가 `NotDeclared` 이므로, 선언 없음을 거부로 읽으면 자리가 적힌 신호를 쓰는 정의가 모두 활성화에서 거부됩니다 |
| (사) | 스킬 검사는 두 가지입니다. 계약 카탈로그(`SkillCatalog`)에 있는 스킬인가, 활성화 때 주어진 현장 기체가 제공하는 스킬 집합에 있는가 | 계약에 있는 스킬과 현장이 제공하는 스킬은 다른 물음입니다 |
| (아) | 작업 지시 리비전(`revise`)은 실행이 쥔 버전으로 계획합니다. 이미 있는 실행이면 카탈로그 대신 그 실행이 쥔 케이퍼빌리티를 쓰도록 `submit` 의 순서를 바꿉니다 | 지금 `submit` 은 리비전으로 가기 전에 카탈로그에서 케이퍼빌리티를 찾고 최고 근거 등급을 검사합니다 |
| (자) | 계약(로봇 계약·작업 응답 `JobResponse`)에는 임무 버전 칸을 더하지 않습니다. 인시던트 번들(의도 `Intent`)에만 싣고 해시(`digest`)에도 넣습니다. 내보내기(`LedgerExport`)의 줄에는 싣지 않습니다 | 계약 쪽은 읽는 쪽이 없습니다(ADR 9). 인시던트 번들은 근거 문서 §9 가 요구하고, 읽는 쪽은 미들웨어를 띄운 호스트(S3 의 picasso-ops 실행 호스트)입니다. 내보내기를 읽는 쪽(narrator)이 `missionVersion` 을 읽을 자리는 확인되지 않았습니다. ADR 9 대로 내보내기 칸은 읽는 쪽이 있을 때 짓습니다(근거 문서 §11 도 «소비자가 붙을 때 ADR 9 에 따라 짓습니다» 라고 적었습니다). 선례는 `decidedBy`(picasso §15.202)입니다. 해시에 넣는 것은 해시의 원칙(«새 칸은 전부 든다 … 그중 어느 하나가 달라진 사건은 다른 사건이다», `Incident.kt:248-256`) 때문입니다. 버전 1 실행의 인시던트와 버전 2 실행의 인시던트는 다른 인시던트입니다. `review`·`resolution` 이 해시에서 빠지는 이유는 나중의 사람 단계가 그 인시던트를 다른 인시던트로 만들지 않기 때문이고(`Incident.kt:221-242`), 내보내기 여부와는 상관이 없습니다 |
| (차) | JSON 을 읽는 데 새 의존을 더하지 않습니다. 이미 있는 `protobuf-java-util` 의 JSON 파서로 읽습니다. 모르는 키 거부와 틀린 것을 모두 모아 한 번에 알리는 엄격 매핑은 손으로 씁니다 | picasso 모듈(main)에는 Jackson 도 kotlinx 도 없습니다. 의존이 계약과 계약 소비자뿐입니다. profile-model 의 `RequirementSet` 은 Jackson 을 씁니다. «같은 방식» 은 엄격성(모르는 키 거부, 틀린 것을 모아 한 번에)에 한합니다. `JsonFormat` 으로 `Struct` 를 읽으면 숫자가 double 로 오므로 정수 검사가 필요합니다. 중복 키 처리는 계획이 정합니다 |
| (카) | 임무 정의 버전 칸은 `missionVersion` 입니다. 포트 이름은 `MissionCatalog` 입니다. 작업 지시의 버전(`JobOrder.version`, 단위의 `revision`)과 섞지 않습니다 | «카탈로그» 는 이미 세 뜻(계약 `SkillCatalog`, registry `GET /catalog`, 용어집의 사이트 카탈로그)으로 쓰여 혼동이 생길 수 있습니다. 그래서 이름에 «Mission» 을 붙여 `MissionCatalog` 로 가릅니다 |
| (타) | P3a·P3b 를 picasso PR 하나(P3)로 합칩니다. 구현 계획에서는 묶음 둘(P3a: 정의 데이터, P3b: 버전)로 나눕니다 | `SIGNAL` 이 들어오는 PR 과 내보내기 버전을 올리는 PR 이 같아야 합니다. P3a 가 들이는 경로 `SIGNAL` 은 인시던트 줄의 `route` 로 나가므로(`IncidentLog.kt:117`) 내보내기 버전 4 의 선례(«분기하는 칸에 하위 범주가 늘면 버전을 봐야 한다», `LedgerExport.kt:39-41`)대로 버전을 올려야 합니다. P3b 의 `missionVersion` 은 내보내기에 싣지 않으므로 버전과 무관합니다(결정 (자)). 5→6 은 한 번이고, 인계 번들 네 세트 재산출과 바깥 소비자 알림도 한 번입니다 |
| (파) | 임무 쪽을 별도 저장소나 별도 모듈(예: `picasso-mission`)로 떼지 않습니다. picasso 모듈 안에 패키지(`dev.picasso.middleware.mission`)로 경계를 둡니다. 포트 `MissionCatalog` 인터페이스는 미들웨어 패키지(`Ports.kt` 의 다른 포트처럼)에 두고, 스키마·파서·검증기·해석기·메모리 구현만 `mission` 패키지에 둡니다. 의존은 `mission` → 미들웨어 한 방향입니다. 엔진 쪽 변경(대기 단위, 버전 고정, 인시던트 칸)은 기존 자리에 둡니다 | P3 변경의 절반이 엔진 안쪽(`Middleware` 의 경로·진행·중단, `Execution`, 번들·내보내기)이라 떼면 한 변경이 저장소 둘로 갈라집니다. ADR 38 과 `LogicalCapability` KDoc(«조합은 미션 계층의 일이고 그것은 이 모듈 안이다»), 근거 문서 §5 ③(검증기는 라이브러리)과도 맞습니다. 인터페이스를 `mission` 에 두면 엔진이 `mission` 을 가져오고 `mission` 은 `FloorOwnership`·`LogicalCapability`·`ExecutionUnit` 을 가져와 패키지가 서로 돕니다. 다시 볼 조건: 엔진 없이 스키마·검증기만 필요한 둘째 소비자가 생길 때(예: picasso-ops 운영 서비스가 저장 전에 검증). 그때도 picasso 안의 가벼운 모듈이 먼저이고, 검증기가 쓰는 `FloorOwnership` 같은 미들웨어 타입의 자리를 함께 정합니다 |

## 3. 단계와 완료 기준

## 5. P3a: 임무 정의 데이터

### 5.1 스키마

문서 하나가 WorkMaster 하나의 정의입니다. 최상위 칸은 5개입니다.

| 칸 | 내용 |
|---|---|
| `schemaVersion` | 1 |
| `workMasterId` | 정의가 속한 WorkMaster |
| `maxEvidence` | 최고 근거 등급(E0~E2) |
| `preferredOptionals` | 선택 파라미터(문자열 맵) |
| `steps` | 직선 노드 목록(1개 이상) |

노드는 `kind` 로 가릅니다. 단위 노드(`kind: "unit"`)의 칸은 다음과 같습니다.

| 칸 | 내용 |
|---|---|
| `id` | 노드 id |
| `skill` | 계약 스킬 이름 |
| `forEach` | 반복할 작업 지시 설비의 `equipmentUse`(예 `destination`) |
| `unitId` | 단위 id 의 값 출처 |
| `parameters` | 파라미터 이름 → 값 출처 |
| `expectedIdentity` | 기대 식별의 값 출처(선택) |
| `source` | 제시 자리의 값 출처(선택) |
| `destination` | 목적지의 값 출처(선택) |
| `pairWith` | 짝 지을 설비의 `equipmentUse` 와 맞출 속성(예 `source` 를 `material` 로) |
| `whenUnpaired` | 짝이 없을 때 계획 시점 실패 분류(예 `NO_SOURCE_FOR_MATERIAL`) |

값 출처는 3가지입니다. 반복 중인 설비의 id, 그 설비의 속성, 짝지은 설비의 id 입니다. 값 출처마다 대체값을 적을 칸을 둡니다(짝이 없을 때의 파라미터 값, 예 빈 문자열). 속성 값 출처에서 속성이 없으면 값은 없음(null)입니다(코드의 `expectedIdentity` 는 material 이 없으면 null, `LogicalCapability.kt:119`). 정확한 JSON 표기는 구현 계획이 스파이크에서 정합니다.

짝 규칙은 다음과 같습니다. 짝 후보는 `pairWith` 의 `equipmentUse` 를 가진 설비 중 맞출 속성이 있는 것입니다. 같은 속성 값의 후보가 여럿이면 목록에서 뒤에 오는 것을 씁니다(코드의 `associateBy` 와 같습니다, `LogicalCapability.kt:104`). 반복 중인 설비에 그 속성이 없으면 짝이 없습니다(110).

짝이 없을 때는 다음과 같습니다. 파라미터 값은 값 출처에 적은 대체값(예 빈 문자열)입니다. `source` 칸은 없음(null)입니다. 단위 상태는 `FAILED` 이고 실패 분류는 `whenUnpaired` 입니다.

설비 확인 칸(`evidence`)은 두지 않습니다. 설비 확인은 엔진이 언제나 단위의 `destination` 으로 하고(`observeCell` 1084-1086), 관문도 `destination`·`source` 를 봅니다. P3 에서 확인 없음(`none`)을 쓰는 곳이 없습니다.

설비 대기 노드(`kind: "wait"`)의 칸은 다음과 같습니다.

| 칸 | 내용 |
|---|---|
| `id` | 노드 id |
| `signal` | 신호 사양의 이름 |
| `expect` | 기대 값(문자열) |
| `deadlineSeconds` | 기한(양의 정수) |
| `onDeadline` | `OPERATOR_HOLD` 또는 `ABORTED` |

파서는 모양과 형만 봅니다. 모르는 키, 빠진 필수 칸, 형이 틀린 값은 모두 모아 한 번에 알립니다. 기한이 양수인지, 기한 뒤 상태가 허용된 값인지는 검증기의 기한 검사가 봅니다(§5.5).

예를 들어 버전 2 의 `PrepareSequencedRack` 은 맨 앞에 «랙 도착 신호 `rack_present` 가 `true` 가 될 때까지 120초 대기, 기한 뒤 `OPERATOR_HOLD`» 노드를 둡니다. 그 뒤에 슬롯마다 `pick_place` 단위 노드를 둡니다.

### 5.2 신호 사양

신호 사양은 현장 데이터입니다. 신호마다 4개 칸을 둡니다.

| 칸 | 내용 |
|---|---|
| `name` | 신호 이름 |
| `location` | 그 신호를 내는 자리(선택) |
| `kind` | `BOOLEAN` 또는 `TEXT` |
| `safety` | 참/거짓 |

근거 문서 §5 는 «설비 신호 사양과 «어느 주소가 어느 신호인가» 의 매핑» 을 데이터로 두라 했습니다. P3 는 이름과 성질까지입니다. 주소 매핑은 드라이버의 일로 남깁니다.

### 5.3 설비 대기 단위

`Route` 에 셋째 값(`SIGNAL`)을 더합니다. 진행 루프의 «로봇이 아니면 플릿» 분기를 경로마다 나눕니다.

| 항목 | 동작 |
|---|---|
| 경로 분기 | 컴파일러가 빠짐을 알려 주는 곳은 `when (unit.route)`(882) 하나입니다. 나머지는 «로봇이 아니면 플릿» 의 if/else 라 `SIGNAL` 이 조용히 플릿으로 갑니다. 진행 루프(607-612), `resolveDoubt`(828), `autoResolvesInDoubt`(1505), 리비전의 도는 단위 분기(435)입니다. 모두 경로별로 나눕니다. `blockingFaults`(666)·`judgeEffectMismatch`(1063)·관문의 연쇄 검사(127)·출발 결품(175)은 로봇만 보므로 이미 맞게 빠집니다 |
| 대기 칸의 자리 | 신호 이름·기대 값·기한·기한 뒤 상태는 `ExecutionUnit` 의 새 칸 하나(대기 사양)에 둡니다. 같은 넷을 단위 파라미터에도 실어 인시던트 의도의 `unitParameters` 로 나가게 합니다(번들 칸이 늘지 않습니다. `IncidentLog.kt:118-132` 는 `skillType`·`unitParameters`·`source`·`destination`·`expectedIdentity` 를 옮깁니다). `skillType` 은 계약 스킬 이름과 겹치지 않는 값으로 둡니다. 노드 id 는 정의 안에서 겹치면 안 됩니다(리비전이 단위 id 로 접습니다, 418). 반복 단위의 id 는 작업 지시 설비 id 라 대기 노드 id 와 겹칠 수 있습니다. 설비 id 는 작업 지시가 와야 알 수 있어 활성화 때 검증기가 볼 수 없으므로, 이 겹침은 한계 레지스터에 둡니다(구현 계획이 스파이크에서 확인해 정정한 문장입니다). |
| 읽기 | 대기 단위는 시작 시각부터 이름 있는 신호를 당겨 읽습니다 |
| 완료 | 읽은 값이 기대 값이면 `DONE` 입니다. 설비가 관측한 사실이라 근거 등급은 E2 입니다 |
| 낡은 신호 | 대기는 신호의 지금 값으로 판정합니다. 이름으로 읽은 값에 관측 시각이 있으면 자취에만 남깁니다. 시작 전 관측을 버리는 규칙은 두지 않습니다. `rack_present` 같은 상태 신호는 대기 시작 전에 이미 참일 수 있고, 그 관측 시각은 랙이 도착한 순간이라 시작 전 관측을 버리면 영원히 끝나지 않습니다. 설비가 시각을 주는지에 따라 같은 정의가 달리 도는 것도 막습니다. P3 의 신호는 상태 신호만입니다. 이벤트형 신호(순간에만 참인 펄스)는 한계입니다(§10) |
| 자취 | 신호 읽기는 값이 바뀔 때만 자취에 남깁니다(`observeCell` 1092 처럼 남겨야 인시던트 근거 윈도우에 실립니다. 진행마다 남기면 자취가 넘칩니다). 기한에 다다르면 마지막으로 읽은 값(없으면 «신호 없음»)을 자취에 한 번 남깁니다. 그래야 인시던트 근거 윈도우에 실립니다 |
| 기한 기준 | 단위의 시작 시각(`startUnit` 이 찍는 `requestedAt`, 1026)입니다. 재작업하면 다시 시작합니다 |
| 기한 | 기한(시작 시각 + `deadlineSeconds`)이 지나면 `onDeadline` 으로 갑니다 |
| `OPERATOR_HOLD` | 대기 단위가 `OPERATOR_HOLD` 가 되어 라인이 멈춥니다. 운영자 판단을 기다립니다 |
| `ABORTED` | 대기 단위는 `FAILED`(실패 분류 `SIGNAL_DEADLINE`)로 남습니다. 남은 `PENDING` 단위를 먼저 `ABORTED` 로 바꾸고, 기존 중단 경로(`abort`)로 간 뒤, 같은 라운드에서 멈추는 가드를 둡니다. 실행의 결과는 `ABORTED` 로 확정됩니다(다음 라운드부터 진행 루프가 종료된 실행을 건너뛰고(580), 리비전은 종료된 실행이라 거부됩니다(402)). 이 중단은 취소 요청이 아니므로 취소 보고(`CancelReport`, `lastCancel`)는 남기지 않습니다(결정 (다)). 지금 `abort` 는 언제나 취소 보고를 만들므로(1458-1473), `abort` 에 취소 보고를 남길지 가르는 인자를 둡니다 |
| 인시던트 | 두 경우 모두 인시던트를 남깁니다(실패 분류 `SIGNAL_DEADLINE`). P3b 의 인시던트 `missionVersion` 시험이 이 인시던트로 섭니다 |
| 작업 응답 | 대기 노드 id 는 다른 단위처럼 `completedUnits`·`incompleteUnits` 에 오릅니다(`InspectAsset` 의 `.travel` 이 선례입니다) |
| 관문 | 대기 단위는 `destination` 이 없어 관문의 바닥·구역·점유 검사를 건너뜁니다. 로봇 단위가 아니라 연쇄 검사와 결함 차단에서 빠집니다 |
| 시각 | 미들웨어의 시계(`now`)입니다 |
| 운영자 판단 | 운영자 판단(`OperatorDecision`)은 `CONFIRM_DONE`·`REWORK` 둘입니다(`Model.kt:91`, `resolve` 1245-1260). 대기 단위의 `OPERATOR_HOLD` 는 확인(`CONFIRM_DONE`, 진행)과 재작업(`REWORK`, 다시 기다림. 시도 횟수가 오르고 기한이 다시 시작합니다)으로 풉니다. 중단은 실행 취소(`cancel`)입니다. 지금 취소는 하위 핸들이 없으면 `cancelRequested` 만 세우고, 진행 루프는 도는 단위가 있으면 취소 분기에 닿지 않습니다(605-626). 그래서 대기 단위의 진행이 `cancelRequested` 를 보면 대기를 끝내고 기존 중단 경로(`abort`, 정리 «해당 없음»)로 갑니다. 취소 때 대기 단위는 `ABORTED` 입니다(취소 보고의 진행 중 단위가 대기 노드 id 가 됩니다) |
| 사람 확인 | 대기 단위를 `CONFIRM_DONE` 하면 도달 근거가 E0 로 남고(1248), 작업 응답의 근거 등급은 완료 단위의 최솟값이라(1489) E0 로 내려갑니다. 사람이 신호 대신 확인했다는 뜻이므로 그대로 둡니다 |
| 재할당 | 대기 중에는 도는 단위가 있어 재할당이 막힙니다(366) |

정확한 동작은 계획이 스파이크에서 정합니다. 기한 뒤 `ABORTED` 의 정산 결과(`physicalState`)는 `ABORTED` 로 확정됩니다. 다음 라운드부터 진행 루프가 종료된 실행을 건너뛰고(580), 리비전은 종료된 실행이라 거부됩니다(402).

셀 신호 포트에 이름으로 읽는 메서드를 기본 구현(없음, null)으로 더합니다. 시험의 `CellMimic` 이 그것을 구현합니다.

### 5.4 해석기와 동등성

해석기는 정의를 `LogicalCapability` 로 바꿉니다. 그래서 실행·리비전·인시던트는 지금 경로를 그대로 탑니다.

동등성은 다음과 같이 봅니다. 작업 지시 모양들에 대해 해석기의 계획과 코드 `PrepareSequencedRack.plan()` 이 단위마다 같은 칸을 냅니다. 기존 `SequencingRackTest` 의 작업 지시 도우미는 제시 자리를 material 로 묶은 맵으로 만들어 «같은 material 이 둘» 모양이 없습니다. 그래서 동등성 시험은 작업 지시 모양을 새로 만듭니다. 제시 자리 있음, 없음, 같은 material 둘, material 없는 슬롯, material 없는 제시 자리, 목적지 0개, 무관한 `equipmentUse` 입니다.

### 5.5 검증기

검증기는 정의, 신호 사양, 바닥 소유(`FloorOwnership`), 현장 기체가 제공하는 스킬 집합을 받아 거부 목록을 냅니다. 거부는 근거 문서 §8.4 의 모양을 따릅니다. 근거 문서 §8.4 는 6칸(부족한 조건, 관측값과 기대값, 마지막 확인 시각, 근거 버전, 해결 담당, 바로 갈 작업)입니다. 활성화 거부에서 마지막 확인 시각은 활성화를 시도한 시각이고, 근거 버전은 «해당 없음»(현장 설정 버전과 무관한 판정)입니다. 여기에 대상 노드 id 를 더합니다.

| 검사 | 묻는 것 | 거부 종류 예 | 후속 행동 |
|---|---|---|---|
| 기한 | 대기 노드마다 양의 기한과 허용된 기한 뒤 상태가 있는가. 파서가 아니라 검증기가 봅니다. 그래야 기한 검사를 빼는 결함 주입이 검증기 시험에 잡힙니다 | 기한 없음 또는 기한 뒤 상태 허용 밖 | 대기 노드의 기한 칸을 고칩니다 |
| 신호 | 참조한 신호가 신호 사양에 있는가 | 신호 사양에 없는 신호 | 신호 이름을 고치거나 신호 사양에 더합니다 |
| 자원 | 정의에 고정으로 적힌 자리(대기 신호의 자리)의 바닥 소유가 `Unowned` 인가. `Declared`·`NotDeclared` 는 통과입니다. 신호에 자리가 없으면 그 노드를 건너뜁니다(결정 (바)) | 바닥 소유 `Unowned` | 바닥 소유를 선언합니다 |
| 스킬 | 단위 노드의 스킬이 계약 카탈로그에 있고 현장 기체가 제공하는가 | 계약에 없는 스킬 또는 현장 기체가 제공하지 않는 스킬 | 스킬 이름을 고치거나 제공 기체를 둡니다 |
| 안전 | 안전 신호를 기다리는 대기 노드가 없는가 | 안전 신호 대기 | 대기 노드를 안전 신호가 아닌 신호로 바꿉니다 |

스킬 이름은 계약 카탈로그 기술자의 `skillTypeName` 으로 구합니다(`capability/HoldEffects.kt:20-24`). 파라미터 이름은 검사하지 않습니다. 오타는 실행 때 `PARAMETER_INVALID` 로 드러납니다(§10).

검증기 함수 이름은 관문의 함수 이름(`unownedFloor` 등)과 겹치지 않게 둡니다(`SeamPlacementTest` 가 이름으로 자리를 찾습니다).

거부 종류 이름은 계획이 정합니다. 읽을 수 없는 정의(파싱 실패)도 같은 모양의 거부로 냅니다.

## 6. P3b: 임무 버전

### 6.1 카탈로그와 활성화

새 포트 `MissionCatalog` 를 둡니다. WorkMaster 마다 지금 활성인 정의와 그 버전을 줍니다.

| 항목 | 내용 |
|---|---|
| 생성자 | 미들웨어 생성자에 이 포트(`missions`)를 맨 뒤 인자로 더합니다. `capabilities` 와 `missions` 는 둘 다 기본값을 null 로 둡니다(Kotlin 은 기본값이 있는 인자가 명시됐는지 알 수 없기 때문입니다). 둘 다 주면 생성 때 실패합니다(조용히 하나를 버리지 않습니다). 둘 다 없으면 지금의 기본 케이퍼빌리티 셋(버전 없음)이고, `capabilities` 만 주면 그 목록(버전 없음)입니다. 기본값 경로(`missions` 를 안 줌)는 그대로입니다. 그래서 생성 자리 28곳(어댑터 모듈의 종단 시험 포함)이 그대로 컴파일됩니다. `ProgressStallTest` 가 `capabilities` 를 덮어쓰는 것은 그대로 동작합니다 |
| 메모리 구현 | 하나를 main 에 둡니다. 시험과 picasso-ops 호스트가 씁니다. picasso-ops 는 저장을 S3 에서 붙입니다. 활성화와 조회가 다른 스레드에서 올 수 있으므로 스스로 스레드 안전하게 둡니다 |
| 활성화 관문 | 활성화는 검증기를 통과해야 합니다. 통과하면 그 WorkMaster 의 다음 버전 번호(1부터 오름)가 활성이 됩니다. 검증기 입력(신호 사양, 바닥 소유, 현장 기체가 제공하는 스킬 집합)은 활성화 호출의 인자로 받습니다. 미들웨어는 바닥 소유를 필드로 쥐지 않고 관문에만 넘깁니다(105) |
| 거부 | 거부되면 활성 버전은 그대로입니다 |
| 적용 시점 | 활성화는 다음 작업 지시부터 적용됩니다. 미들웨어에는 잠금이 없습니다(KDoc «스레드가 없다»). 잠금은 호스트가 쥡니다(`ScenarioHost`·`ApprovalHost` 의 `synchronized`) |
| `adopt` | `adopt`(314-317)는 카탈로그를 한 번 읽은 (케이퍼빌리티, 버전) 쌍을 이어지는 제출 계획까지 넘깁니다. 따로 두 번 읽으면 그 사이 활성화가 끼어 두 계획의 버전이 갈릴 수 있습니다 |

### 6.2 실행의 버전 고정

실행이 생성 때 `missionVersion` 을 쥡니다. 코드 케이퍼빌리티면 없습니다. 리비전은 실행이 쥔 케이퍼빌리티와 버전으로 계획합니다(결정 (아)). 리비전은 실행이 쥔 케이퍼빌리티의 최고 근거 등급으로 요구 등급을 검사합니다. 리비전에서 `workMasterId` 가 바뀌면 거부합니다. `adopt`(314-317)도 케이퍼빌리티 맵을 직접 읽으므로 카탈로그로 바꿉니다(§6.1). 그래서 활성 버전이 바뀌어도 도는 실행은 **옛 버전으로 끝납니다**.

### 6.3 인시던트 기록과 내보내기 버전

| 항목 | 내용 |
|---|---|
| 의도 칸 | 인시던트 번들의 의도(`Intent`)에 `missionVersion` 을 더합니다. 해시(`digest`)에 넣습니다(결정 (자)). 해시가 바뀌므로 인계 번들 네 세트의 해시 값도 재산출로 함께 바뀝니다. 내보내기 줄에는 싣지 않습니다. 미들웨어를 띄운 호스트(S3 의 picasso-ops 실행 호스트)가 번들을 읽어 «어느 버전에서 일어났는가» 를 보입니다. 근거 문서 §9 의 요구는 이것으로 채웁니다 |
| 단위 파라미터 | 대기 단위의 신호 이름·기대 값·기한·기한 뒤 상태는 단위 파라미터에 실려 의도의 `unitParameters` 로 나갑니다(§5.3). 번들 칸은 늘지 않습니다 |
| 내보내기 칸 | 내보내기(`LedgerExport`)에는 `missionVersion` 을 싣지 않습니다. 내보내기를 읽는 쪽(narrator)이 읽을 자리는 확인되지 않았고, ADR 9 대로 내보내기 칸은 읽는 쪽이 있을 때 짓습니다. 선례는 `decidedBy`(picasso §15.202)입니다. narrator 가 요청하면 그때 짓습니다(§10) |
| `route` 하위 범주 | 인시던트 줄의 `route` 에 하위 범주 `SIGNAL` 이 늘어납니다(`IncidentLog.kt:117`). 내보내기 버전 4 의 선례대로 버전을 올립니다(결정 (타)) |

| 문서 | `docs/orchestration.md` §6 적재 규약 표와 버전 행을 고칩니다. `docs/orchestration.md:213` 은 경로를 «`ROBOT` 또는 `FLEET`» 이라 적으므로 그 행도 고칩니다 |
| 인계 번들 네 세트 | 네 세트(`handoff/narrator/run-1..4`)는 manifest 의 `schemaVersion` 이 바뀌므로 `ExportFixtureTest` 로 다시 산출해 커밋합니다. 네 세트는 코드 케이퍼빌리티로 돌고 `SIGNAL` 단위가 없어 인시던트 줄의 키 집합은 그대로입니다. 데이터 정의로 도는 세트를 더하지 않습니다(값의 뜻은 시나리오 시험이 봅니다) |
| 인계 번들 세트 대조 | `HandoffFixtureTest` 는 인시던트 줄의 최상위 키와 `schemaVersion` 을 대조합니다(43, 45-52). 더하는 내보내기 칸이 없으므로 시험은 넓히지 않습니다 |
| 알림 | 로컬 `INDEX.txt` 의 버전 이력을 갱신합니다. narrator 와 «보강» 세션에 커밋 해시와 새 문장을 알립니다(picasso 의 재개 규약). 새 문장은 둘입니다. `route` 의 하위 범주 `SIGNAL` 이 생겼고, 해시에 임무 버전이 들어가 임무 버전이 없는 줄까지 모든 digest 가 바뀌었습니다(판 4 로 고정해 둔 요약의 digest 도 바뀝니다). 인계 번들 네 세트는 코드 케이퍼빌리티로 돌아 `SIGNAL` 값이 어디에도 나오지 않는다는 것도 알림에 적습니다 |

| `docs/limits.md` | 새 오픈 항목(나머지 두 정의의 데이터 이전, 분기·병렬, 주소 매핑, 정의 JSON 스키마 파일)과 수. §15.176(호스트)은 그대로입니다(S3) |

## 8. 오류 처리

| 상황 | 처리 |
|---|---|
| 읽을 수 없는 정의 | 활성화 거부(틀린 곳 모두). 활성 버전은 그대로입니다 |
| 검증 실패 | 활성화 거부(거부 목록). 활성 버전은 그대로입니다 |
| 대기 신호를 못 읽음(포트가 null) | 기다림을 계속합니다. 기한이 지나면 `onDeadline` 입니다. 못 읽은 것을 «값이 아님» 으로 접지 않습니다 |
| 활성 정의가 없는 WorkMaster | 지금처럼 «모르는 논리적 능력» 으로 작업 지시를 거부합니다 |
| 대기 기한 뒤 `OPERATOR_HOLD` | 대기 단위가 `OPERATOR_HOLD` 가 되어 라인이 멈춥니다. 운영자 판단(확인·재작업) 또는 실행 취소로 풉니다(§5.3) |
| 대기 기한 뒤 `ABORTED` | 대기 단위는 `FAILED`(`SIGNAL_DEADLINE`)로 남습니다. 남은 `PENDING` 단위를 먼저 `ABORTED` 로 바꾸고 기존 중단 경로(`abort`)로 간 뒤 같은 라운드에서 멈춥니다. 실행의 결과는 `ABORTED` 로 확정됩니다. 취소 보고는 남기지 않습니다(§5.3) |

## 9. 시험

| 단계 | 시험 |
|---|---|
| P3a 파서 | 모르는 키·빠진 칸·형이 틀린 값을 모두 모읍니다. 기한의 값 검사는 검증기 시험이 봅니다 |
| P3a 동등성 | 작업 지시 모양 여럿(§5.4)에 대해 칸마다 대조합니다 |
| P3a 설비 대기 | 신호 봄 → `DONE`(시작 전부터 참이던 상태 신호 포함). 기한 뒤 `OPERATOR_HOLD`. 기한 뒤 `ABORTED`(대기 단위 `FAILED`, 남은 `PENDING` 단위 `ABORTED`, 내보내지 않음, 실행 결과 `ABORTED`, 취소 보고 없음). 신호 못 읽음. 기한 때 마지막 값의 자취 |
| P3a 검증기 | 5검사 각각과 통과 정의. 기한 검사는 파서가 아니라 검증기 시험이 봅니다 |
| P3a 기존 시험 | 고치지 않고 통과합니다 |
| P3b 시나리오 | 새 시험 클래스입니다. `SequencingRackTest` 와 같은 대역(in-process 하네스, `ClientRobotPort`, `CellMimic`)입니다. 버전 1 실행 중 버전 2 활성화 → 새 작업 지시는 버전 2(대기 거침), 옛 실행은 버전 1 로 끝남, 옛 실행 리비전은 버전 1, 버전 3(없는 신호) 거부와 활성 버전 2 유지, 인시던트 `missionVersion`. 버전 2 활성화 뒤 버전 1 실행에서도 인시던트를 하나 내고(예: 셀 대역의 식별 불일치) 그 번들의 `missionVersion` 이 1 임을 단언합니다. 버전 2 실행의 인시던트는 2 입니다. 버전 2 실행에서만 보면 «활성 버전을 실음» 결함과 «실행 버전을 실음» 이 같은 값을 냅니다. 같은 기체에 두 실행을 겹치지 않습니다. 버전 2 의 작업 지시는 다른 기체와 다른 슬롯으로 보내 슬롯 점유가 겹치지 않게 합니다(정확한 구성은 계획) |
| P3b 인계 번들 세트 | 재산출한 세트와 대조합니다. 인시던트 줄의 최상위 키와 `schemaVersion` 을 봅니다(§6.3) |

결함 주입은 앞 단계들처럼 합니다. 코드를 바꿔 넣고 지정 시험이 이름으로 잡는지 봅니다.

| 주입하는 결함 | 잡아야 하는 시험 |
|---|---|
| 동등성의 짝 짓기 규칙 | 동등성 |
| 대기 기한 비교 | 설비 대기 |
| 기한 뒤 `ABORTED` 의 중단 경로 | 설비 대기 |
| 검사 5가지 각각 빼기 | 검증기 |
| 리비전이 카탈로그를 다시 봄 | P3b 시나리오 |
| 실행이 버전을 안 쥠 | P3b 시나리오 |
| 번들에 버전을 안 실음 | P3b 시나리오 |
| 번들이 활성 버전을 실음 | P3b 시나리오 |

| 한계 | 내용 |
|---|---|
