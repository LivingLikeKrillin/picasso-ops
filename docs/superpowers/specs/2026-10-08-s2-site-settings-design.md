# picasso-ops S2: 현장 설정 버전과 연결 기준 시간 설계

- 문서 상태: 설계 초안 (2026-10-08). 결정은 2026-10-08 사용자 결정(§2)
- 범위: picasso-ops 의 S2. picasso 변경 없음
- 근거 문서: S1 스펙(`docs/superpowers/specs/2026-10-07-s1-skeleton-robot-lifecycle-design.md`) §7.3·§7.4 · P2·S1d 스펙(`docs/superpowers/specs/2026-10-08-p2-s1d-runner-binding-commissioning-design.md`) · picasso `docs/superpowers/specs/2026-10-07-ops-console-lifecycle-design.md`(이하 운영 관리 화면 설계 제안) §5·§8.4·§9·§10·§11

## 1. 목적과 범위

S1 스펙 §1 의 덩어리 표에서 S2 는 «현장 값 데이터화» 입니다. 운영 관리 화면 설계 제안 §10 의 입증 항목 2 에 대응합니다. S1 스펙 §7.3 은 연결 기준 시간을 «S1 에서 운영 서비스 설정에 두고, S2 에서 데이터로 옮깁니다» 라고 적었습니다. §7.4 는 운영 관리 화면 설계 제안 §8.4 의 «근거 판» 칸을 «S1 에 버전이 없어서 빼며 S2 에서 더합니다» 라고 적었습니다. 이 문서는 그 칸을 «근거 버전» 이라 부릅니다. 이 문서가 그 두 자리를 채우는 설계 문서입니다.

입증 항목 2 의 원문 요지는 다음과 같습니다. 현장 값 한 세트를 화면에서 바꾸면 다음 tick 부터 적용됩니다. 인시던트 기록에 그 값과 버전 번호가 실립니다.

S2 가 입증하는 것은 한 흐름입니다. 엔지니어가 화면에서 연결 기준 시간을 바꾸면 현장 설정의 새 버전이 생깁니다. 코드 수정과 재기동 없이 다음 기체 목록 읽기부터 그 값으로 연결과 막힘을 판정합니다. 막힘 카드는 어느 버전으로 판정했는지(근거 버전)를 보입니다. 바꾼 사람·사유·시각이 버전 이력과 조작 기록에 남습니다. 잘못된 변경은 막힙니다. 허용 범위 밖 값, 남이 먼저 올린 버전을 모르고 덮어쓰기, 운영자 모드가 그것입니다.

S2 가 입증하지 않는 것은 2가지입니다.

| 입증하지 않는 것 | 내용 |
|---|---|
| 미들웨어 시간값 셋의 데이터화 | `evidenceWindow`·`inDoubtGrace`·`stallWindow` 는 지금 picasso 의 `LogicalCapability` 기본 getter 입니다. picasso-ops 는 미들웨어를 돌리지 않습니다. ops-service 빌드 검사 `checkNoPicassoOnMain` 이 ops-service 에서 picasso 코드 사용을 막습니다. 읽는 곳(미들웨어 실행 호스트)이 없는 값을 저장만 하면 소비자가 없습니다(ADR 9). 호스트를 세우는 S3 에서 같은 버전 체계에 칸을 더합니다(결정 1). |
| 인시던트 기록에 버전 번호 싣기 | 미들웨어가 인시던트를 만드는 자리이므로 S3 입니다. picasso 의 인시던트 번들은 지금 `evidenceWindow` 만 싣고 설정 버전 칸이 없습니다. 칸을 더하면 picasso 쪽 내보내기 버전과 인계 번들이 움직입니다. 그래서 S3 에서 picasso PR 로 다룹니다. |

그래서 입증 항목 2 중 S2 가 닫는 것은 «화면에서 바꾸면 다음 판정부터 적용, 버전과 근거 버전, 행위자·사유 기록, 잘못된 변경 차단» 입니다. «미들웨어 tick 적용과 인시던트 기록의 버전 번호» 는 S3 에서 닫습니다.

## 2. 결정 기록

2026-10-08 사용자 결정 3건입니다.

| 번호 | 결정 | 내용 |
|---|---|---|
| 결정 1 | 범위 | 지금 읽는 곳이 있는 값만 옮깁니다. 연결 기준 시간 하나와 버전 체계, 근거 버전 칸입니다. 미들웨어 시간값 셋은 S3 입니다. |
| 결정 2 | 버전 단위 | 사이트 설정 한 세트의 스냅샷입니다. 값을 하나만 바꿔도 세트 전체가 새 버전 번호를 받습니다. 근거 버전 번호 하나로 그 판정에 쓴 값이 전부 특정됩니다. S3 에서 칸이 늘어도 같은 번호 체계를 씁니다. |
| 결정 3 | 저장과 기록 | ops 스키마의 덧붙이기 전용 표에 저장합니다. 변경 조작은 조작 기록(`operation_log`)에도 남깁니다. |

앞서 정해진 것이 하나 있습니다. 운영 관리 화면 설계 제안 §11 결정 2(2026-10-07)입니다. 현장 값은 데이터로 옮기되 엔지니어 권한으로만 바꿉니다. 화면은 범위 밖 값을 막습니다. 허용 범위 수치는 그 문서가 정하지 않았습니다. 이 문서가 연결 기준 시간의 범위를 정합니다(§5).

그 문서는 «허용 범위는 라이브러리가 쥐고 화면은 범위 밖 값을 막습니다» 라고 적었습니다(§11 결정 2). 그것은 picasso 미들웨어 값에 대한 말입니다. 연결 기준 시간은 picasso 가 아니라 ops-service 의 값입니다. 그래서 범위도 ops-service 코드의 상수로 둡니다.

## 3. 완료 기준

통합 시험(e2e `SiteSettingsTest`)이 다음 7단계를 통과해야 합니다. 그 사이에 코드 수정과 재기동이 없습니다.

| 단계 | 조작 | 기대 결과 |
|---|---|---|
| (1) | 기동 직후 현장 설정을 읽습니다. | 버전 1 이 90초로 보입니다. |
| (2) | 기체를 선언하고 첫 보고를 보낸 뒤 보고를 멈춥니다. | 기체가 `CONFIRMED` 가 됩니다. |
| (3) | 엔지니어가 기준 버전 1 위에서 60초로 바꿉니다. | 버전 2 가 됩니다. 조작 기록에 `SUCCEEDED` 행이 남습니다. |
| (4) | 마지막 보고가 60초보다 오래될 때까지 기다립니다. | 그 기체에 `REPORT_STALE` 이 근거 버전 2, 기대값 «60초 안의 보고» 로 보입니다. |
| (5) | 기준 버전 2 위에서 3600초로 바꿉니다. | 버전 3 이 됩니다. 다음 읽기에서 `REPORT_STALE` 이 사라지고 연결이 신선으로 보입니다. 바인딩하지 않은 기체에는 `UNBOUND` 가 남습니다(S1d). |
| (6) | 이미 지난 기준 버전 1 로 바꾸려 합니다. | `SETTINGS_VERSION_CONFLICT` 로 거부됩니다. 조작 기록에 `REJECTED` 행이 남습니다. |
| (7) | 범위 밖 값(30초)을 보냅니다. 사유를 비워 보냅니다. JSON 으로 못 읽는 본문을 보냅니다. 운영자 모드로 보냅니다. | 범위 밖은 400 `SETTING_OUT_OF_RANGE` 로 막힙니다. 사유 빈칸은 400 `REASON_REQUIRED` 로 막힙니다. 못 읽는 본문은 400 `SETTINGS_BAD_REQUEST` 로 막힙니다. 운영자 모드는 403 으로 막힙니다. 넷 다 조작 기록에 남지 않습니다. |

Playwright 는 다음을 확인합니다. 단계는 기존 흐름 끝의 런처 종료(registry 정지) 바로 앞에 넣습니다. 값은 120초로 바꿉니다. 런처가 30초마다 보고하므로 기체는 계속 신선합니다. 엔지니어 모드에서 현장·자원 영역의 현장 설정 구역에서 값을 바꾸면 «연결 기준 시간 120초로 변경: 반영됨» 알림과 이력 행(버전 2)이 보입니다. 운영자 모드에서는 수정 폼 대신 «현장 설정 변경은 엔지니어 모드에서 합니다» 가 보입니다. 기체 상세의 «연결 판정 기준» 칸이 «기준 120초, 현장 설정 버전 2» 로 보입니다.

오래됨은 실제 시간으로만 생깁니다(§4). 그래서 통합 시험 (4) 는 마감 90초의 폴링으로 기다립니다. 실측은 약 61초였습니다. 기존 e2e 를 합친 CI gradle job 의 시간 안에 듭니다. 시험 전용 시계 이음새를 두지 않습니다. 앞 스펙들과 같은 원칙입니다.

## 4. 확인한 사실

picasso-ops main `7254521`, picasso `41beedb` 기준입니다.

| 항목 | 확인한 사실 |
|---|---|
| 연결 기준 시간의 자리 | `ops-service/src/main/resources/ops-service.properties` 의 `ops.connection.threshold=90s` 입니다. `OpsApplication.kt` 가 `@Value` 로 `RobotListService` 생성자에 넣습니다. 생성자의 고정 값이라 바꾸려면 재기동이 필요합니다. |
| 판정식 | `Blockers.connection` 입니다. 마지막 보고가 기준보다 오래면 오래됨입니다. 정확히 기준이면 신선입니다. `REPORT_STALE` 의 기대값은 «N초 안의 보고» 입니다. |
| 스냅샷 규칙 | `RobotListService` 는 기체·바인딩·소프트웨어 대조 셋을 모두 읽혀야 스냅샷을 바꿉니다. 하나라도 못 읽으면 직전 스냅샷을 보입니다(«다 읽히거나 직전 값»). 판정 시각은 읽기를 시작한 시각입니다. |
| 막힘과 거부의 모양 | `Finding` 으로 나갑니다. 칸은 종류, 관측값, 기대값, 마지막 확인 시각, 해결 담당, 화면 안/밖, 후속 행동, 바로 가기 대상입니다. 화면 `FindingCard` 가 그립니다. 운영 관리 화면 설계 제안 §8.4 의 6칸 중 «근거 판» 만 없습니다. |
| 보고 간격 | 기체 생존 보고는 실제 약 30초 간격입니다. 프로파일 `humanoid-a`·`quadruped-b` 의 `publish_interval.max_seconds` 가 30 입니다. `site/` 런처가 실제 1초마다 가상 1초를 밉니다(1:1). 기준 90초는 그 3배입니다(S1 스펙 §6). |
| 시계 | registry 는 생존 보고 시각을 자기 실제 시계로 찍습니다. ops-service 의 시계도 실제 시계입니다. mimic 의 가상 시계를 밀어도 보고가 늙지 않습니다. 그래서 오래됨은 실제 시간이 흘러야 생깁니다. 통합 시험 하네스에는 시간을 미는 반복 작업이 없습니다. `advance` 를 부르지 않으면 보고가 멈춥니다. |
| ops 스키마 | 표는 지금 `operation_log` 하나입니다(마이그레이션 `V1__operation_log.sql`). 고치기·지우기·통째로 비우기를 트리거로 막습니다(«코드의 약속이 아니라 스키마가 막는다»). 칸 9개 중 `registry_response` 는 NULL 을 받습니다. 결과는 5값입니다(`SUCCEEDED`·`REJECTED`·`NO_RESPONSE`·`CONFIRMED_APPLIED`·`CONFIRMED_NOT_APPLIED`). |
| 조작 경로 | 기존 조작은 전부 `OperationRunner` 를 거쳐 registry 를 부릅니다. 응답 없음이면 재조회로 반영 여부를 맞춥니다. registry 를 부르지 않는 조작은 이 장치를 쓸 이유가 없습니다. |
| 모드 관문 | `Guard` 는 헤더가 없으면 400 `ACTOR_REQUIRED` 로 막습니다. 모드가 다르면 403 `MODE_NOT_ALLOWED` 로 막습니다. 이 사전 거부는 조작 기록에 남지 않습니다. |
| 화면 읽기 | 화면은 API 4개(기체 목록·어댑터·프로파일·조작 기록)를 5초마다 한꺼번에 읽습니다. 하나라도 실패하면 아무것도 바꾸지 않습니다. 상단 영역 5개 중 현장·자원 영역은 지금 «다음 단계» 로 비어 있습니다. |

## 5. 저장: 현장 설정 버전

새 마이그레이션 `V2__site_settings.sql` 로 ops 스키마에 `site_settings` 표를 만듭니다.

| 칸 | 형 | 내용 |
|---|---|---|
| `version` | `BIGINT` | 버전 번호입니다. 기본 키입니다. |
| `connection_threshold_seconds` | `INTEGER` | 연결 기준 시간(초)입니다. 0보다 큽니다. |
| `mode` | `TEXT` | 변경한 모드입니다. `ENGINEER` 만 받습니다. |
| `actor_user` | `TEXT` | 변경한 사용자입니다. 빈 글자는 받지 않습니다. |
| `reason` | `TEXT` | 변경 사유입니다. 빈 글자는 받지 않습니다. |
| `recorded_at` | `TIMESTAMPTZ` | 기록 시각입니다. DB 가 찍습니다. |

행은 덧붙이기만 합니다. `operation_log` 와 같이 고치기·지우기·통째로 비우기를 트리거로 막습니다. 현재 버전은 가장 큰 `version` 행입니다.

마이그레이션이 넣는 첫 버전은 다음과 같습니다.

| 버전 | 연결 기준 시간 | 모드 | 사용자 | 사유 |
|---|---|---|---|---|
| 1 | 90초 | `ENGINEER` | `system` | S1 설정값 이전 |

그 뒤로 `ops.connection.threshold` 속성은 지웁니다.

표에 사이트 칸은 두지 않습니다. ops 스키마 하나는 ops-service 하나의 것입니다. ops-service 하나는 사이트 하나(`SITE_ID`)를 맡습니다.

연결 기준 시간의 허용 범위는 다음과 같습니다.

| 항목 | 값과 근거 |
|---|---|
| 하한 | 60초입니다. 보고 간격 상한 30초의 2배입니다. 보고를 한 번 놓쳐도 오래됨이 되지 않게 하는 값입니다. 하한을 보고 간격 가까이 두면 정상 기체가 신선과 오래됨을 오갑니다. |
| 상한 | 3600초입니다. 1시간보다 길면 연결 칸이 뜻을 잃는다는 판단입니다. |
| 기본값 | 90초입니다. 허용 범위 안입니다. |
| registry 신선도와의 관계 | registry 의 보고 신선도 기본값 24시간은 케이퍼빌리티 축소 판정용입니다. 이 범위와 관계없습니다(S1 스펙 §7.3). |
| 범위 관리 | ops-service 의 상수로 둡니다. 화면은 응답으로 받은 범위를 보입니다. |

기본 키 때문에 같은 버전 번호를 두 번 쓸 수 없습니다. 같은 기준 버전 위에서 두 변경이 동시에 오면 하나만 들어갑니다. 다른 하나는 기본 키 충돌로 거부됩니다.

## 6. 운영 서비스

### 6.1 읽기

`GET /api/site-settings` 는 다음을 냅니다. 모드와 관계없이 읽힙니다.

| 부분 | 칸 | 내용 |
|---|---|---|
| 현재 버전 | `current` | `version`(버전), `connectionThresholdSeconds`(연결 기준 시간 초), `mode`(모드), `user`(사용자), `reason`(사유), `recordedAt`(기록 시각) |
| 허용 범위 | `range` | `minConnectionThresholdSeconds`·`maxConnectionThresholdSeconds` |
| 버전 이력 | `history` | 최신부터, 최대 200행. 첫 행이 `current` 입니다. |

### 6.2 변경 조작

`PUT /api/site-settings` 입니다. 엔지니어 모드만 허용합니다.

| 본문 칸 | 뜻 |
|---|---|
| `baseVersion` | 기준 버전 |
| `connectionThresholdSeconds` | 새 연결 기준 시간 초 |
| `reason` | 사유 |

응답은 기존 조작 결과 `OperationOutcome` 그대로입니다. 새 버전 번호를 싣는 칸은 더하지 않습니다. 새 버전은 화면이 조작 뒤 다시 읽을 때 보입니다. 기존 조작과 같이 조작이 끝나면 다시 읽습니다.

성공은 200 이고 결과 `SUCCEEDED` 입니다. 상태 거부(버전 충돌)도 200 이고 결과 `REJECTED` 입니다. 거부 칸에 `Finding` 이 실리고 `registryStatus` 는 null, `unauthorized` 는 false 입니다. 409 는 쓰지 않습니다. 화면은 2xx 와 400/403 만 읽고 그 밖의 코드는 «결과 모름» 으로 보이기 때문입니다.

본문은 바이트로 받습니다. 관문(모드·사용자 헤더)을 지난 뒤 컨트롤러가 직접 읽습니다. 스프링에 맡기면 두 가지가 어긋납니다. 못 읽는 본문의 400 이 사전 거부 모양이 아닙니다. 관문보다 먼저 읽혀 운영자 모드의 깨진 본문이 403 이 아니라 400 이 됩니다. 칸은 널 가능으로 읽습니다. 빈 칸을 0 으로 읽으면 누락이 버전 충돌이나 범위 밖으로 갈립니다. 쓰기 본문은 `application/json` 만 받습니다. 다른 출처 방어이며 기존 조작과 같습니다. 그래서 JSON 이 아닌 형식으로 보낸 요청은 관문보다 먼저 415 로 막힙니다. 운영자 모드여도 403 이 아니라 415 입니다.

본문 검사 순서는 셋입니다. 먼저 본문을 JSON 으로 읽고 `baseVersion`·`connectionThresholdSeconds` 가 정수로 있는지 봅니다(없거나 정수가 아니면 `SETTINGS_BAD_REQUEST`). 다음으로 범위를 봅니다(`SETTING_OUT_OF_RANGE`). 마지막으로 앞뒤 빈칸을 뺀 사유가 비었는지 봅니다(`reason` 이 없거나 비면 `REASON_REQUIRED`).

같은 값으로 바꿔도 새 버전이 생깁니다. 버전은 값이 아니라 변경의 기록입니다.

트랜잭션은 다음과 같습니다. 기준 버전이 지금 버전과 같은지 비교합니다. 같으면 다음 번호 행과 조작 기록 `SUCCEEDED` 행을 한 트랜잭션에 넣습니다. 비교가 필요한 이유는 아직 없는 버전을 기준으로 보내는 경우입니다(예: 지금 1 인데 5). 비교가 없으면 번호가 건너뛴 행이 들어갑니다. 지난 버전 위의 변경은 비교에서 막힙니다. 비교와 넣기 사이에 다른 변경이 같은 번호를 먼저 커밋하면 기본 키가 막습니다. Postgres 는 기본 키 위반 뒤 그 트랜잭션을 더 쓸 수 없습니다. 그래서 되돌린 뒤 지금 버전을 다시 읽어 조작 기록에 `REJECTED` 행을 따로 넣습니다. 그 밖의 DB 오류는 아무것도 남기지 않습니다(500).

registry 를 부르지 않으므로 `OperationRunner` 를 거치지 않습니다. 조작 기록을 직접 씁니다. 조작 기록의 `target` 은 `site-settings` 입니다. `request` 는 기존 조작처럼 조작 이름과 값을 담은 JSON(`{"op":"CHANGE_SITE_SETTINGS","baseVersion":…,"connectionThresholdSeconds":…}`)이고, 사유는 `reason` 칸에 둡니다. `registry_response` 는 NULL 입니다. 응답 없음과 재조회는 없습니다. DB 오류면 트랜잭션이 되돌려지고 아무것도 남지 않습니다(500). 화면은 기존 조작의 500 과 같이 «결과 모름» 을 보이고, 반영 여부는 현장 설정 구역을 다시 읽어 확인합니다.

기존 조작의 결과 5값을 그대로 씁니다(`SUCCEEDED`·`REJECTED`). 새 값을 더하지 않습니다.

조작 기록의 기준을 다시 적습니다. S1 은 «registry 에 닿지 않은 요청은 조작이 아니다» 라고 적었습니다. S2 부터는 상태를 바꾸는 쪽(registry, 또는 현장 설정)에 닿은 요청을 조작으로 기록합니다. 관문에서 막힌 사전 거부는 여전히 기록하지 않습니다. 코드의 해당 주석(`Guard.kt`)도 이렇게 고칩니다.

### 6.3 거부 대응

| 구분 | 종류 | 조건 | 관측값·기대값 | 해결 담당 | 화면 | 후속 행동 | 조작 기록 |
|---|---|---|---|---|---|---|---|
| 사전 거부(400) | `SETTING_OUT_OF_RANGE` | 범위 밖 값 | - (응답의 `detail` 문장) | - | - | - (응답의 `detail` 문장) | 안 남음 |
| 사전 거부(400) | `REASON_REQUIRED` | 사유 없음 또는 빈칸 | - (응답의 `detail` 문장) | - | - | - (응답의 `detail` 문장) | 안 남음 |
| 사전 거부(400) | `SETTINGS_BAD_REQUEST` | 본문을 못 읽음, `baseVersion`·`connectionThresholdSeconds` 누락이나 정수 아님 | - (응답의 `detail` 문장) | - | - | - (응답의 `detail` 문장) | 안 남음 |
| 상태 거부 | `SETTINGS_VERSION_CONFLICT` | 기준 버전이 현재 버전이 아님, 또는 같은 번호를 다른 변경이 먼저 씀 | 관측값 «현재 버전 N», 기대값 «기준 버전 M» | 엔지니어 | 안 | «현재 값을 다시 읽고 다시» | `REJECTED` 행 |
| 모드 거부(403) | `MODE_NOT_ALLOWED` | 운영자 모드 | - (응답의 `detail` 문장) | - | - | - (응답의 `detail` 문장) | 안 남음 |

사전 거부 응답은 기존 `PreRejection(error, detail)` 모양입니다. 화면은 `detail` 문장만 보입니다. 범위 밖이면 `detail` 에 보낸 값과 범위가 들어갑니다(예: «연결 기준 시간 30초는 범위 밖이다. 60~3600초여야 한다»).

사전 거부는 기존 `ACTOR_REQUIRED`·`PROFILE_REQUIRED` 와 같은 길입니다. 상태 거부는 기존 거부처럼 조작 결과의 거부 칸으로 나갑니다. 운영자 모드는 기존 관문의 403 `MODE_NOT_ALLOWED` 입니다.

### 6.4 판정과 근거 버전

`RobotListService` 는 읽을 때마다 현재 현장 설정 버전도 함께 읽습니다. 기체 목록 읽기는 현장 설정을 먼저 읽습니다. 못 읽으면 예외가 그대로 나가 `GET /api/robots` 가 실패(500)합니다. 스냅샷은 바뀌지 않습니다. 기본값으로 대신 판정하지 않습니다. 어느 버전으로 판정했는지 말할 수 없게 되기 때문입니다. registry 상태 칸(`OK`·`REGISTRY_SILENT`·`REGISTRY_UNAUTHORIZED`)에 ops DB 실패 값을 더하지 않습니다. ops DB 를 못 읽으면 조작 기록 읽기도 같이 실패하므로 화면은 운영 서비스 실패로 보이고 다섯 읽기를 모두 직전 값으로 둡니다(§7). 현장 설정이 읽힌 뒤 기체·바인딩·소프트웨어 대조 셋이 다 읽혀야 스냅샷을 바꿉니다. 그래서 연결 칸과 막힘은 늘 그 스냅샷이 쥔 버전 하나로 판정됩니다. registry 가 답하지 않아 직전 스냅샷을 보일 때는 버전도 그 스냅샷의 것입니다.

기체 목록 응답에 그 스냅샷의 현장 설정 버전과 연결 기준 시간을 싣습니다. 칸 이름은 `settingsVersion`·`connectionThresholdSeconds` 입니다. 스냅샷이 없으면 null 입니다.

`Finding` 에 근거 버전 칸 `basisVersion` 을 더합니다. 기본값은 null 입니다. 끝에 더해 기존 생성 자리가 그대로 컴파일됩니다. `Blockers.of` 에 근거 버전 인자를 기본값 null 로 더합니다.

`RobotListService` 생성자의 기준 시간 인자(`Duration`)를 현장 설정 출처(`SettingsSource`)로 바꿉니다. 지금 값을 돌려주는 함수형 인터페이스입니다. 기존 시험 2곳(`RobotListServiceTest`, `RobotCommissioningListTest`)의 생성 인자를 고칩니다.

| 막힘·거부 | 근거 버전 |
|---|---|
| `REPORT_STALE` | 값을 갖습니다. 현장 설정에 기대는 판정입니다. |
| `AWAITING_FIRST_REPORT`, `REPORTING_AFTER_RETIREMENT`, `UNREGISTERED_ROW`, 시운전 막힘들 | 비어 있습니다(«해당 없음»). registry 상태에서 나온 막힘입니다. |
| 조작 거부 | 비어 있습니다(«해당 없음»). |

새 버전은 다음 읽기부터 적용됩니다. 화면은 5초마다 읽으므로 늦어도 다음 읽기에 반영됩니다. 이미 낸 판정은 바뀌지 않습니다.

## 7. 화면

현장·자원 영역을 엽니다. 그 안에 «현장 설정» 구역 하나를 둡니다.

| 자리 | 보이는 것 |
|---|---|
| 현장 설정 구역 | 현재 버전과 연결 기준 시간, 허용 범위, 버전 이력 표(버전, 값, 사용자, 모드, 사유, 기록 시각) |
| 현장 설정 구역(엔지니어 모드) | 수정 폼(값, 사유). 기준 버전은 고치기 시작한 순간의 버전으로 고정하고 폼에 «기준 버전 N» 으로 보입니다. 범위 밖 값과 빈 사유는 화면이 보내기 전에 막고 폼 안에 이유를 보입니다. 서버도 막습니다. 보낸 뒤에는 폼을 비우고 다음 변경은 새 기준에서 시작합니다. |
| 현장 설정 구역(운영자 모드) | 폼 대신 «현장 설정 변경은 엔지니어 모드에서 합니다» |
| 막힘 카드(`FindingCard`) | «근거 버전» 줄을 더합니다. 값은 «현장 설정 버전 N» 또는 «해당 없음» 입니다. |
| 기체 상세의 «연결 판정 기준» 칸 | «연결» 칸에 붙이지 않고 따로 둡니다. 값은 «기준 N초, 현장 설정 버전 M» 입니다. 목록 수준 값이라 로봇·연결 영역이 상세에 내려 줍니다. |
| 조작 알림 | 변경 결과는 기존 조작 알림으로 보입니다. 거부는 기존 거부 카드입니다. |
| 조작 기록 화면(이력 영역) | `site-settings` 대상 행이 기존 행과 같이 보입니다. |

기준 버전을 «보낼 때 화면이 읽은 현재 버전» 으로 하지 않는 이유가 있습니다. 화면은 5초마다 다시 읽습니다. 보낼 때의 버전을 실으면 고치는 사이 다른 사람이 올린 버전을 모르고 덮어쓰게 되어 충돌 탐지가 화면에서 무력해집니다.

화면이 한꺼번에 읽는 API 가 5개가 됩니다(현장 설정 더함). 하나라도 못 읽으면 다섯 다 직전 값입니다.

화면 시험 대역은 모르는 GET 에 빈 배열을 줍니다. 현장 설정 구역은 모양이 맞지 않으면 «모름: 현장 설정을 아직 읽지 못했습니다» 를 보입니다. 메뉴 시험의 기대값(현장·자원 «다음 단계»)은 바뀝니다.

## 8. 오류 처리

| 상황 | 대응 |
|---|---|
| ops DB 를 못 읽음 | 기체 목록 읽기가 실패(500)하고 스냅샷은 바뀌지 않습니다(§6.4). 조작 기록 읽기도 같이 실패하므로 화면은 운영 서비스 실패로 보이고 다섯 읽기를 모두 직전 값으로 둡니다. 현장 설정 구역도 직전 값을 보입니다. |
| 변경 중 DB 오류 | 트랜잭션을 되돌립니다. 기록이 없습니다(500). 화면은 «결과 모름» 을 보입니다. 재조회 장치는 따로 두지 않습니다. 커밋 도중 연결이 끊기면 반영 여부를 모를 수 있으므로 현장 설정 구역을 다시 읽어 확인합니다. |
| 동시 변경 | 기본 키가 하나만 받습니다. 진 쪽은 `SETTINGS_VERSION_CONFLICT` 입니다. |
