# picasso-ops 권위 경계와 다중 인스턴스 설계 기록

- 문서 상태: 설계 기록(2026-10-14). 결정은 2026-10-13 소유자 결정이고, 구현은 이 문서 범위가 아닙니다.
- 범위: picasso-ops 의 운영 서비스(ops-service)·실행 호스트(mission-host)·결과 수집과 전달. 라이브러리 쪽 경계·용어·자동 이양 규칙은 picasso ADR 51(`picasso/docs/adr/0051-three-authority-boundaries.md`)을 가리킵니다.
- 근거 문서: picasso ADR 51, picasso `docs/contract.md` §7(재기동과 넘겨받기의 전제), `docs/guarantees.md` «배포 전제»·«여러 인스턴스»·«부분 완료·잔여 파지 기체의 배정 제외»·«잔여 파지 표시의 범위», S4b 스펙(재기동 복원). 기준 커밋 picasso-ops `283af4e`(서브모듈 picasso `79e074d`).

## 1. 목적과 범위

### 1.1 현재 배포 전제와 한계

지금 picasso-ops 배포 전제는 «같은 DB 에 활성 운영 서비스는 하나여야 합니다» 입니다. `StationCoordinator` 의 `tick` 이 `RETRYING`·`REWORKING` 상태를 만나면 이전 프로세스가 비정상 종료했다고 읽고 `REVIEW_REQUIRED` 로 넘깁니다. 이 판단은 상태를 변경하는 조정기가 단 하나일 때만 성립합니다(`guarantees.md`). 현재 시스템은 여러 인스턴스를 지원하지도 않고 검증하지도 않았습니다(`guarantees.md`).

실행 호스트(mission-host) 역시 둘 이상 띄우면 안 됩니다.
- 공정 `ReentrantLock` 하나로 동시성을 제어합니다(`MissionHost.kt`).
- 기동 복원(`MissionHost.restore()`)은 정착도 포기도 없는 일지 행 전부를 소유 조건 없이 다시 짓습니다(`HostRecords.openJournal()`). 일지를 읽을 때 인스턴스 조건이 없습니다.
- 유휴 기체 배정 판정(`judge`)은 자기 JVM 메모리에 적재된 실행 목록만 확인합니다.
- 임무의 실행 중 버전(`MissionVersions.inFlight`)은 프로세스 메모리 안에 유지되며(`MissionVersions.kt`), 임무 카탈로그는 기동 시점에만 DB 에서 읽어 메모리에 캐시합니다(`StoredMissionCatalog.kt`).

운영 서비스는 단일 실행 호스트 주소(`ops-service.properties` 의 `ops.host.url`)만 바라봅니다. 호출 뒤 «응답 없음» 이 발생했을 때의 재조회 경로도 동일한 단일 호스트만 조회하도록 작성되어 있습니다(`JobOrderOperations.kt` KDoc).

인스턴스 식별자, 소유 세대(epoch), 옛 발행 경로 차단(펜싱) 토큰은 운영 서비스 및 스테이션 조정기 쪽에 전혀 없습니다. 실행 호스트 일지 테이블(`V2__execution_journal.sql`)에는 `instance_id` 열이 있고 미들웨어의 `instanceId` 값을 기록하지만, 심장박동이나 만료 확인 절차는 없습니다.

### 1.2 목적

이 문서는 단일 활성(단계 0)에서 활성·대기(단계 1), 분할 배포(단계 2)로 점진적 확장할 때 각 역할의 권위 단위가 무엇이고 무엇이 차단을 맡는지 정합니다. 아울러 단계 0 단계에서 지금 당장 코드에 마련해 두어야 할 최소한의 자리를 규정합니다.

### 1.3 입증하지 않는 것

다음 항목은 이 설계 기록에서 다루지 않으며, 구현이나 실측을 통해 별도로 확인해야 합니다.

| 리스 행 | §4, §8 |
| 세대 비교 | §6, §8 |
| DB failover 자동화 | §9 |
| 분할 배포 | §3.3, §11 |

| 리스 행 DDL 및 마이그레이션 | 실제 DB 스키마 생성 및 Flyway 마이그레이션은 구현 시점에 작성합니다 | §8 |

| 부하 측정 결과 | 인스턴스 경합 및 지연 시간 실측 하네스 결과는 추후 측정합니다 | §11 |

## 2. 결정 기록

picasso-ops 에는 `docs/adr/` 디렉터리가 없습니다. 소유자 결정 1 의 «picasso-ops ADR» 은 이 설계 기록으로 갈음합니다.

### 2.1 소유자 결정 (2026-10-13 저녁)

| 번호 | 질문 | 결정 |
|---|---|---|
| 1 | ADR 을 어디에 둘 것인가 | picasso 와 picasso-ops 둘로 나눕니다. picasso 는 경계, 용어, 호출 계약 조건, 자동 이양 규칙을 다루고, picasso-ops 는 리더 단위, 프로세스 권위 리스(첫 등장 «리스(lease)») 행, 펜싱, 인수 순서, failover 를 다룹니다. picasso-ops 가 picasso 를 단방향으로 참조합니다. |
| 2 | 강제가 없는 기종(G1 류)의 자동 제어권 이양 | 기본적으로 금지합니다. 증거는 이전 인스턴스의 자기 차단 기록 또는 독립 확인(프로세스 종료 확인, 네트워크 격리) 중 하나가 필수입니다. 리스 만료 단독은 인정하지 않습니다. |
| 3 | DB failover | 발행 중지와 전체 재대조가 기본입니다. 코드가 관측한 최대 세대로 후퇴를 감지합니다. 자동 failover 를 원하는 현장은 승격 시 generation 증가가 요구 사양이며, 그렇지 않으면 수동 복구합니다. |
| 4 | 결정 행의 세대 | 두지 않습니다. 기대 상태 버전만 둡니다. |
| 5 | 부하 핫스팟 | 그룹 2 P0 작업 완료 후 측정 하네스와 함께 검증합니다. |
| 6 | INHIBITED 때 작업 번호 쓰기 | 쓰기 전에 보류합니다(D 단계 시점). |

### 2.2 앞서 정해진 것

- picasso ADR 51: 세 가지 권위 경계(임무 실행, 로봇 제어, 공유 자원), 리스의 세 가지 의미, 네 가지 값, 단일 적용자 기반 단일 활성 원칙, 소유 이전 규약(획득 -> 옛 경로 차단 -> 재대조 -> 발행 재개), 수신 측 차단, 미들웨어 발행 관문 하나 및 입력 둘, 기종 분류별 자동 이양 규약.
- 기 구현 항목: picasso `PhysicalState.occupiesRobot` 및 `pumps` 속성(picasso #91, `79e074d`). 실행 호스트 `judge` 가 `occupiesRobot` 상태인 실행을 판정(`MissionHost.kt`). 운영자 실행 취소와 잔여 파지 표시는 실행 호스트 운영 정책으로 확정되어 있습니다(picasso-ops #29, `283af4e`, `guarantees.md`). 표시는 mission DB(`V5__execution_cancel_residual_hold.sql`)에 영속되고 재기동 시 다시 읽습니다. 취소 및 해소 승인자는 사람만 가능하도록 DB `CHECK` 제약으로 강제합니다.

### 2.3 이 문서가 정하는 것

이 문서는 다음 절에서 picasso-ops 고유의 다중 인스턴스 규칙을 정의합니다.

- §3 역할별 권위 단위
- §4 리스 행 규격
- §5 세션 advisory 잠금 불채택
- §6 펜싱 적용표
- §7 인수 순서
- §8 단계 0 최소 자리
- §9 DB failover
- §10 부하 핫스팟

## 3. 역할별 권위 단위

### 3.1 단계별 권위 단위 비교

| 역할 | 단계 0 (현재: 단일 활성) | 단계 1 (활성·대기) | 단계 2 (분할) |
|---|---|---|---|
| 운영 서비스 스테이션 조정 | 프로세스 하나 | 운영 서비스 리더 하나 | 스테이션(경합 자원군) claim 단위. 행에 관리자 세대 포함 |
| 유휴 로봇 배정 | 실행 호스트 프로세스 | 실행 호스트 리더가 배정 담당 | 열린 선택(하단 상술) |
| 실행 호스트 | 프로세스 하나 | 전체 리더 하나 | 기체 점유 및 구역 판정을 조정자로 이전한 후 실행자 분할 |
| `adapter-host` | 기체별 프로세스 (복수 호스트의 중복 담당 차단 장치 없음) | 기체별 리스 | 기체별 또는 상호 배타적인 플릿 제어 도메인별 |
| 결과 수집·콜백 전달 | 리더 없음 | 리더 없음 (조건부 성립) | 리더 없음 (조건부 성립) |

### 3.2 세부 제약과 분할 조건

스테이션 권위는 `StationCoordinator` 의 `tick` 에만 국한되지 않습니다. 동일한 상태를 변경하는 모든 경로가 하나의 권위 경계로 묶입니다.
- `tick` 경로
- `rework` 경로
- 재평가 경로(`observe` 내부의 `RETRYING` claim)
- 수동 해제 경로
- 설비 쓰기 경로

현재 운영 서비스의 분할을 가로막는 요소는 두 가지입니다.
1. «남은 상태 = 죽은 프로세스» 로 단정하는 복구 판정(`StationCoordinator.kt`).
2. `rework` 에 걸려 있는 JVM 모니터(`@Synchronized`).
이 둘은 반드시 인스턴스 식별자와 세대 기반 확인으로 전환해야 분할이 가능합니다.

실행 호스트가 활성·대기(단계 1)에서 단일 전체 리더를 유지해야 하는 이유는 명확합니다. 재기동 복원(`restore()`)이 미결 일지 행 전체를 인스턴스 소유 조건 없이 읽어 들이기 때문입니다. `adapter-host` 가 기체별 권위를 갖는 이유는 벤더 측 제어 인터페이스가 기체 단위로 배타적 제어를 요구하기 때문입니다.

### 3.3 분할 단계의 열린 선택

유휴 로봇 배정 방식은 단계 2 분할 시점에 다음 두 가지 안 중 하나를 선택합니다. 활성·대기(단계 1)에서는 두 방식의 결과가 같습니다.
- 선택 (가) (비관적 접근): 배정 도메인마다 리더가 전체 뷰를 기반으로 배정 대상을 단독 결정합니다.
- 선택 (나) (낙관적 접근): 각 실행자가 배정을 제안하고, 제어 도메인 claim 을 통해 최종 확정을 직렬화하며, 충돌 시 재시도합니다. 이 방식은 별도의 네 번째 조정 서비스 프로세스를 요구하지 않습니다.

선택을 확정하기 위한 기준 조건은 다음과 같습니다.
- 배정 도메인이 둘 이상으로 나뉘는 시점인지 여부
- 실제 하네스에서 측정한 claim 충돌률 및 재시도 비용
- 전역 뷰 부재 시 특정 작업 요청의 기아(starvation) 발생 여부

공유 자원 조정 역시 단계 2 에서 열린 선택입니다. 고정 순서 행 잠금으로 리더 없이 직렬화할 것인지, 자원군별 권위자를 둘 것인지 결정해야 합니다. 단계 1 에서는 단일 리더를 쓰므로 차이가 없습니다.

### 3.4 결과 수집과 콜백 전달이 리더 없이 동작하기 위한 전제

결과 수집 및 콜백 전달은 리더 선출 없이 동작할 수 있으나, 다음 전제 조건을 만족해야 합니다.
- 결과 수집 커서 CAS(`WorkRequests.kt` 의 `ops.result_cursor` 단일 행을 `FOR UPDATE` 로 읽고 갱신)는 단일 실행 호스트 피드(`result_producer`)를 전제로 성립합니다. producer 가 여럿으로 분할되면 이 단일 커서 모델은 보장을 제공하지 못합니다.
- 콜백 claim token(`WorkResultDelivery.kt` 의 `FOR UPDATE SKIP LOCKED` 및 30초 임대, claim 대조)은 늦게 도착한 발신자의 DB 갱신만 방어합니다. 이미 발송된 HTTP 요청의 중복이나 네트워크 역전은 막지 못합니다. 이는 수신 측이 멱등 키(`receipt_id`, 버전)로 흡수해야 합니다. 새로운 리더가 선출되더라도 이전 세대에서 완료된 불변 결과(식별자, 버전, 해시 기반)를 폐기해서는 안 됩니다.
- `sweepStale`(`WorkRequests.kt`) 동작은 아직 대조하지 않았습니다.
- 실행 호스트의 결과 생성 순번은 단일 행 `FOR UPDATE` 로 직렬화됩니다(`HostRecords.appendResult()`).

## 4. 리스 행 규격

### 4.1 리스 저장소와 기본 원칙

프로세스 권위 리스는 분산 합의 알고리즘을 자체 구현하는 대신, 원자적 쓰기를 직렬화할 수 있는 중앙 저장소(PostgreSQL)를 권위의 근거로 사용합니다. 범용 리스 프레임워크는 작성하지 않으며(YAGNI), 필요한 최소 규격만 정의합니다.

`TestRequestService` 의 registry 시험 요청 claim 방식(`SKIP LOCKED` + 만료 + `claimed_by`·`claimed_at`)은 만료 이후라도 다른 프로세스가 재claim 하기 전까지 이전 프로세스의 결과 제출을 수락합니다. 이러한 방식은 상호 배타적 명령 권한을 보장해야 하는 프로세스 권위 리스로 사용해서는 안 됩니다.

### 4.2 리스 테이블 구조

열의 정확한 물리 이름은 구현 시점에 확정하며, 필수 논리 구성은 다음과 같습니다.

| 논리 항목 | 설명 |
|---|---|
| 역할 | 권위 단위를 식별하는 키 (예: 스테이션군, 호스트 전체 리더) |
| 보유자 | 현재 리스를 획득한 인스턴스 고유 식별자 |
| 세대 | 리스를 획득하거나 승격할 때마다 1씩 증가하는 정수 |
| 만료 시각 | 리스의 유효 기간 만료 시각 (DB 시계 기준) |

### 4.3 시계 기준과 만료 검증

만료 시각 판정에는 애플리케이션 시계를 일절 사용하지 않고 데이터베이스 시계만 사용합니다. 현재 코드베이스에는 시계가 혼재되어 있습니다.
- 애플리케이션 시계 사용: 스테이션 만료 및 `phase_at`(`StationCoordinator.kt` 의 `clock.instant()`), registry 시험 요청 claim(`TestRequestService.kt` 의 `now()`).
- DB 시계 사용: 콜백 전달 및 작업 요청 갱신(`WorkResultDelivery.kt`, `StationCoordinator.kt` 의 `clock_timestamp()`).

데이터베이스 시계 역시 시간 점프가 발생할 수 있고, DB failover 전후로 편차가 생길 수 있습니다. 따라서 리스 획득 및 갱신 판정은 잠금 대기를 마친 시점의 DB 시각(`clock_timestamp()`)으로 평가합니다.

### 4.4 획득 및 갱신 규칙

1. 리스 획득: 단일 SQL 문장으로 원자적으로 수행합니다. 세대는 같은 트랜잭션에서 올립니다.
   ```sql
   UPDATE … WHERE expires_at < clock_timestamp() OR holder = :me RETURNING …
   ```
   획득 시도 중 네트워크 오류 등으로 응답이 불분명하면, 즉시 새 세대를 만들어 재시도하지 않고 조회를 통해 직전 시도의 성공 여부를 확인합니다.
2. 리스 갱신: 보유자, 세대, 만료 여부를 동시에 검사합니다.
   - 만료 시각이 이미 지나버린 옛 보유자가 뒤늦게 보낸 갱신 요청으로 권위가 부활하는 상황을 원천 차단합니다.
   - 갱신 전용 연결 풀을 별도로 분리합니다. 갱신용 DB 커넥션을 제때 얻지 못하는 상황 자체를 권위 상실 징후로 취급합니다.
3. 쓰기 직전 로컬 검증: 외부 명령을 발행하거나 DB 에 쓰기 전에, 애플리케이션 내부의 단조 시계(monotonic clock)를 확인하여 리스 잔여 시간이 남아 있는지 먼저 검증합니다.

### 4.5 만료 시간 산정 기준

리스 만료 시간은 다음 계산식을 절대적인 **하한선**으로 둡니다.

`만료 시간 하한 = (3 * 심장박동 주기) + 최대 GC 정지 시간 + DB 왕복 지연 시간`

특정 배수를 곱하는 것만으로는 안전을 수학적으로 증명할 수 없습니다. 따라서 실제 네트워크 지연, 커넥션 풀 대기 시간, GC 정지, 스케줄러 지연을 측정한 실측값과 시스템 목표 복구 시간(RTO)을 종합하여 최종 만료 길이를 확정합니다.

## 5. 세션 advisory 잠금을 쓰지 않는 이유

### 5.1 불채택 사유

PostgreSQL 세션 레벨 advisory 잠금(`pg_advisory_lock`)을 장시간 프로세스 권위 리스로 채택하지 않는 이유는 단순히 «해제 감지가 늦다» 는 점 때문이 아닙니다. 본질적인 문제는 다음과 같습니다.

| 비교 항목 | 세션 advisory 잠금의 문제 | §4 리스 행 방식 |
|---|---|---|
| 커넥션 풀 간섭 | 일반 연결 풀과 커넥션을 공유하면 반납·재사용 시점에 잠금 유지가 깨집니다 | 일반 연결과 독립적으로 상태가 테이블에 보존됩니다 |
| 세대 단조 증가 | 잠금 자체에 증가하는 세대 번호를 실을 수 없습니다 | 획득 시 세대 번호를 1씩 올려 원자적으로 기록합니다 |
| 외부 관측성 | 어느 인스턴스가 잠금을 쥐고 있는지 외부에서 명확히 조회하기 어렵습니다 | 테이블 조회를 통해 보유자와 만료 시각을 즉시 식별합니다 |

전용 커넥션을 생성하여 프로세스 수명 동안 끝까지 쥐고 있는 방식도 대안으로 검토할 수 있으나, Postgres 와 연결 풀의 세부 동작을 확인하지 않았으므로 채택하지 않은 대안으로 남깁니다.

### 5.2 트랜잭션 범위 advisory 잠금의 유지

트랜잭션 범위 advisory 잠금(`pg_advisory_xact_lock`)은 장시간 권위를 유지하는 용도에는 부합하지 않습니다. 그러나 현재 picasso-ops 가 임무 등록과 재평가 충돌을 방지하기 위해 사용하는 임무 잠금(`MissionResources.kt` 의 `pg_advisory_xact_lock(hashtext(:wm))`)은 짧은 트랜잭션 동안의 등록·재평가 직렬화가 목적이므로 변경 없이 그대로 유지합니다(`guarantees.md`).

프로세스 권위 관리는 §4 에서 정의한 리스 행을 사용하는 것으로 확정하며, 전용 커넥션을 상시 점유하는 advisory 잠금 방식은 채택하지 않은 대안으로 남깁니다.

## 6. 펜싱 적용표

| 지점 | 차단 방법 | 지금 |
|---|---|---|
| DB 상태 전이 | 확인과 쓰기를 한 문장으로 합칩니다: `… WHERE owner_epoch = :e` 를 상태 전이 조건에 더합니다. 운영 서비스 리더 세대는 `work_request`·`station_run` 전이 문장에 넣습니다. | 조건부 상태 전이는 있습니다(`StationCoordinator.kt` 의 `WHERE … AND state IN`). 세대 조건은 없습니다. |
| `adapter-host` | 받는 쪽이 발신자 세대를 대조하고 낮은 값을 거부합니다. 계약 칸은 picasso ADR 51(`picasso/docs/adr/0051-three-authority-boundaries.md`)의 조건(ADR 9 소비자 = 이 구현, ADR 36 어휘)에서 들어갑니다. | 계약 헤더에 칸이 없습니다. 조작은 태스크 id 만 맞으면 받습니다(picasso `contract.md` §7.4). |
| 벤더로 나가는 마지막 경로 | 하나로 모읍니다. `adapter-host` 둘이 각각 통과시킨 명령이 같은 기체로 가면 입구 차단이 무력합니다. | 두 `adapter-host` 가 같은 기체를 맡는 것을 막는 장치가 없습니다. |
| 설비 쓰기(작업 번호, 그리고 작동·해제·리셋) | 쓰기 직전 리스 유효 확인을 거치고 쓴 뒤 에코를 대조합니다. | 아래 `numbered()` 설명을 따릅니다. |
| 상위 콜백 | 옛 발행 경로 차단(펜싱)이 아니라 멱등 키(`receipt_id`, `version`)로 막습니다. | claim token 은 늦은 DB 갱신만 막습니다. |

`numbered()` 는 결함이 아닙니다. 사전 확인 뒤 잠금 밖에서 쓰고 다시 확인합니다.
- 순서: 잠금 안에서 사전 확인(`tick` 의 `WAITING_READY` 분기, 준비 신호·격리·만료, `StationCoordinator.kt`)을 거칩니다. 그 뒤 잠금 밖에서 작업 번호를 쓰고(`port.write`), 다시 잠금 안에서 재확인(상태·revision·소유자·격리)한 뒤 `DISPATCHING` 으로 전이합니다. 클래스 주석의 «Database locks cover decisions, never network calls» 방침을 따릅니다.
- 남는 창은 확인 커밋과 쓰기 사이이며 순서만으로는 닫지 못합니다. 쓰기 직전 프로세스 권위 리스 유효 확인과 세대로 이 창을 줄입니다. 여기서 막지 못한 늦은 쓰기는 에코 불일치가 `REVIEW_REQUIRED` 로 잡습니다(`ECHO_MISMATCH`). 같은 실행의 늦은 쓰기는 같은 토큰이므로 무해합니다. 단 같은 토큰을 다시 쓰는 것은 설비가 멱등일 때만 무해하므로 `docs/station-equipment-requirements.md` 의 요구 사양에 더할 항목입니다. 해당 문서는 이번에 고치지 않고 §11 에 남깁니다.
- 작업 번호 토큰은 완료 귀속의 run 단위 펜스이며, 쓰기 행위 자체를 막지는 못합니다. 둘 다 참입니다.
- 셀 신호 수동 쓰기(`CellSignalOperations.write`)는 쓰고 되읽어 대조합니다(`recheck`). 활성·대기 구조에서는 여기에도 쓰기 직전 리스 확인이 붙습니다.
- 토큰을 받지 못하는 설비의 대안은 셋입니다: 쓰기 직전 리스 재확인, 쓰고 되읽어 대조, 격리입니다.
- `INHIBITED` 상태일 때 작업 번호 쓰기는 쓰기 전에 `WAITING_READY` 에 사유를 적고 보류합니다. 써 놓고 막히면 기한 초과로 엉뚱한 사유가 남기 때문입니다.
- 예약 허가는 PLC 인터록을 대체하지 않습니다.

## 7. 인수 순서와 리더 상태

리더 상태는 `STANDBY` → `RECONCILING` → `ISSUING` → `LOST` 로 전이합니다. 리스 획득 성공은 `ISSUING` 이 아니라 `RECONCILING` 진입을 뜻합니다.

인수 순서는 단계 1 기준으로 다음 절차를 밟습니다:
1. 리스 획득과 세대 증가를 같은 트랜잭션에서 처리합니다.
2. 소유 행(스테이션 소유자 등)의 관리자 세대를 갱신합니다. 기체 점유는 풀지 않습니다.
3. 그 뒤에만 남은 `RETRYING`·`REWORKING` 상태를 보고 앞 프로세스가 죽었다고 판단합니다. 이때 판단 조건으로 «행 세대 < 내 세대» 를 둡니다. 지금 코드는 조건 없이 판단합니다(`StationCoordinator.kt`). 현재 두 조정기 동시 처리 시험은 `{RUNNING, REVIEW_REQUIRED}` 둘 다 받아들입니다(`WorkRequestsTest` 의 `조정기 둘이 동시에 공통 접수를 처리해도 호스트 전송은 한 번이다`).
4. 결정적 태스크 id 로 `WatchTask` 를 다시 붙입니다.
5. 발행을 재개합니다(`ISSUING`).

세 역할 사이에 원자 트랜잭션이 없으므로 인수 뒤 재대조 절차가 필요합니다.
- 대기자는 일지를 미리 읽어 둡니다. 인수 공백은 리스 만료와 상태 재구성 시간의 합입니다. 실행 호스트는 `restore()` 의 기체 스냅숏을 씁니다.
- 리스를 잃으면 `LOST` 로 전이합니다: 발행을 멈추고 벤더 연결을 닫고 자기 차단 기록(`FENCED`)을 남깁니다. 이 기록이 picasso ADR 51(`picasso/docs/adr/0051-three-authority-boundaries.md`)의 G1 류 이양 증거 ①입니다.
- 기종별 인수 정책은 picasso ADR 51 결정 7을 따릅니다: 벤더 리스가 옛 경로를 거부하는 기종은 자동으로 처리합니다. 인수가 리셋인 기종은 인수 전에 태스크를 정리합니다. 강제 수단이 없는 기종은 증거가 없으면 제어자 불명으로 보아 신규 발행을 보류하고 관측을 계속하며 사람 확인으로 해제합니다.
- `restore()` 범위는 단계 0 에서는 «내 인스턴스 행 + 심장박동이 끊긴 인스턴스 행» 으로 좁힐 자리만 두고, 단계 1 에서 «내 세대 행 + 만료 행» 으로 좁힙니다.

## 8. 단계 0 최소 자리 (선출 코드는 넣지 않음)

| 자리 | 판단 | 대가·조건 |
|---|---|---|
| 단위마다 로봇 묶기(실행의 `robotId` 는 단위 기본값) | 세 검토 찬성합니다. | 복원이 단위마다 스냅숏 N 개를 읽어야 하므로, 하나만 못 읽어도 DEFERRED 가 됩니다. 되돌릴 조건은 복원 DEFERRED 비율이 정한 값을 넘을 때입니다. picasso Core 변경이 먼저 들어가야 합니다. |
| 판단 기록 영속화(picasso 한계 §15.213) | 세 검토 찬성하며, 소유 이전의 전제입니다. | 지금 판단은 사본과 조작 기록에만 남고 자동으로 다시 적용되지 않습니다(S4b T8). |
| 실행 호스트 일지·운영 서비스 스테이션 행의 인스턴스 id + 심장박동 | Fable 제안을 따르며, 단계 0 는 인스턴스 id 와 심장박동 기준만 둡니다. | 일지에는 `instance_id` 가 이미 있습니다(값은 미들웨어 `instanceId` 이며 재기동마다 바뀝니다). 스테이션 행(`ops.station_run`·`ops.rf_station`)에는 없습니다. 심장박동은 양쪽 모두 없습니다. |
| `restore()` 와 남은 상태 조건 | 단계 0 에서는 인스턴스 id 와 심장박동으로 좁히고, 단계 1 에서는 세대를 비교합니다. | 세대가 상수 1 이면 «행 세대 < 내 것» 조건이 영영 거짓이 됩니다. 또한 `restore()` 를 만료 행으로 좁힐 만료 개념도 아직 없습니다. |
| 실행 상태 버전 | Codex 후보입니다. | 확정 후보입니다. 칸 이름과 자리는 아직 정하지 않았습니다. |
| 하위 계약 발신자 세대 칸 | `adapter-host` 옛 발행 경로 차단(펜싱) 구현 때 넣습니다(picasso ADR 51). | 지금은 넣지 않습니다. |
| 구간 예약 포트 구현 | 모양만 둡니다(picasso 한계 §15.162). | 소비자와 같은 PR 에서 다룹니다. |
| robot → 제어 도메인 해석 | 보류합니다. | YAGNI 원칙을 따릅니다. |

운영 서비스는 모든 상태 변경 경로를 한 권위 아래로 묶고, `adapter-host` 는 기체에 닿는 모든 명령 경로를 식별하며, 실행 호스트는 실행 상태 변경·작업 수락·복원 경계를 명시합니다.

## 9. DB failover 정책

소유자 결정(§2.1 결정 3)에 따른 방침입니다.
- 위험: 비동기 복제 failover 로 리스와 세대가 되돌아가 두 리더가 같은 번호를 가질 수 있습니다. 결과 수집 커서와 outbox 도 같이 되돌아갑니다.
- 기본 방침: 발행 중지와 전체 재대조입니다.
- 코드 감지: 각 인스턴스가 관측한 최대 세대를 들고 있다가, DB 의 세대가 그보다 작으면 후퇴로 판단하여 `RECONCILING` 으로 전이합니다.
- 현장 요구 사양: 자동 failover 를 원하는 현장은 승격 절차에서 generation 을 올려야 합니다(DB 밖에 보존하는 통제된 승격). 이를 제공하지 못하는 현장은 자동 failover 를 지원하지 않으며 수동 복구로 처리합니다. 운영 모호성을 없애기 위해 요구 사양과 대체 경로 형식을 함께 둡니다.
- 고르지 않은 대안: 리스 트랜잭션만 동기 커밋하는 방안은 발행 의도·결과·커서 손실이 남으므로 채택하지 않습니다. 관측한 최대 세대에 1 을 더하는 단독 방식은 관측하지 못한 수신자가 더 높은 값을 기억할 수 있어 제외합니다. generation 지정 단독 방식은 사람 수칙에 의존하여 코드가 집행하지 못하므로 고르지 않습니다.
- Postgres 를 유지하며 DB 고가용성(HA) 구성은 외부 전제로 둡니다.

## 10. 분할 전에 고치고 잴 부하 핫스팟

이 작업은 그룹 2 P0 뒤에 측정 하네스와 함께 진행합니다.
- 스테이션 `tick`(2초 주기, `StationController.kt` 의 `ops.stations.poll-ms:2000` 설정): 스테이션마다 전체 스테이션 목록을 다시 읽어 O(스테이션²) 부하가 생깁니다(`StationCoordinator.kt` 의 `stations().single{…}`). 활성 스테이션마다 호스트를 조회하는 부하도 있습니다.
- 콜백 전달(2초 주기, `WorkResultDelivery.kt`): 결과 전체를 대상으로 `INSERT…SELECT` 를 수행합니다.
- 실행 호스트 pump(250ms 주기, `MissionHost.kt` 의 `PUMP_PERIOD`): 기동 뒤 인시던트 전체와 실행 전체를 훑습니다.
- 미들웨어 아웃박스 누적: `ack` 를 받은 응답도 들고 있어 계속 자랍니다(`MissionHost.kt` KDoc, S3a 스펙 §12 한계).
- `work_request` 인덱스 부하: 인덱스가 `(received_at DESC, receipt_id)` 하나뿐이며 EXPLAIN 분석은 아직 하지 않았습니다.
- 순서: 이들 핫스팟을 먼저 고친 뒤 로봇 수를 늘려 가며 측정합니다. 단일 활성으로 버티지 못하는 수치가 나올 때 단계 2 분할을 엽니다.

## 11. 지금 하지 않는 것

- 리더 선출 코드, 리스 행, 세대 열, 심장박동 구현은 하지 않습니다(이 문서는 설계 기록입니다).
- 분할 단계의 배정 권위와 자원 조정 방식 선택은 하지 않습니다(§3 열린 선택 항목).
- 세션 advisory 잠금은 도입하지 않습니다(§5).
- 범용 리스 프레임워크, 샤딩, 합의 클러스터는 만들지 않습니다(YAGNI).
- 결정 행의 세대 칸은 두지 않습니다.
- 다중 사이트(picasso 한계 §15.9), 전역 배차 및 다수 로봇 경합(picasso 한계 §15.126)은 기존대로 범위 밖으로 둡니다.
- `docs/station-equipment-requirements.md` 에 설비 멱등 요구 사양을 더하는 작업은 이번에 하지 않습니다(§6 관련 후보 항목).

## 12. 참조와 보장 문서와의 관계

- picasso ADR 51(`picasso/docs/adr/0051-three-authority-boundaries.md`): 경계, 용어, 자동 이양 규칙의 원본입니다. 이 문서는 그 내용을 배치 관점으로 옮긴 것이며, picasso 쪽은 이 문서를 가리키지 않습니다.
- `docs/guarantees.md`: «배포 전제» 의 «운영 서비스 한 프로세스» 와 «여러 인스턴스» 는 단계 0 의 사실이며 이 문서가 바꾸지 않습니다. «부분 완료·잔여 파지 기체의 배정 제외» 및 «잔여 파지 표시의 범위» 는 기체 점유와 잔여 파지 표시의 지금 동작입니다. 해당 표시는 실행 호스트 운영 정책이며 picasso 의 보장이 아닙니다(picasso 설계 문서 §15.146). 소유 이전 과정에서 표시는 보존되는 기록입니다(기체 점유와 물품 책임은 관리자 세대만 바뀝니다).
- 잔여 파지 표시의 지금 한계 중 이 문서와 닿는 점: 운영자 취소를 기록한 뒤 다음 pump 전에 재기동하면 다시 지은 실행에 취소를 다시 걸지 않습니다(`guarantees.md`). 소유 이전에서도 이는 같은 빈자리로 남습니다.
- S4b 스펙: A=B 재기동 복원의 원본입니다. 이 문서에서 다루는 `restore()` 범위 변경은 S4b T3 의 «정착도 포기도 없는 일지 행 전부» 를 조건에 맞게 좁히는 것입니다.
