# picasso-ops S4a: 장애 주입, 인시던트 화면, 운영자 보류 해소 설계

- 문서 상태: 설계 초안 (2026-10-09). 결정은 2026-10-09 사용자 결정(§2). 검토 1차(코드 대조) 반영
- 범위: picasso-ops 의 S4a. picasso 변경 없음
- 요청·응답 JSON 의 정확한 모양과 스파이크가 정한 세부: S4a JSON 계약 `docs/superpowers/specs/2026-10-09-s4a-json-contract.md`(스파이크에서 정함)
- 근거 문서: picasso 운영 관리 화면 설계 제안 `picasso/docs/superpowers/specs/2026-10-07-ops-console-lifecycle-design.md`(서브모듈) §4·§8.4·§9·§10, S3a·S3b·S3c 스펙, picasso ADR 43·ADR 47, picasso-ops `e482c33`, picasso `195c1ee`

## 1. 목적과 범위

운영 관리 화면 설계 제안 §10 의 입증 항목 5 는 지연, 단절, 묵은 값, 재시작을 넣으면 인시던트와 사람의 판단으로 이어지고, 재시작 뒤 중복 명령과 중복 작업 응답을 막는다는 것입니다. 제안 §4 는 운영자가 인시던트 승인과 재작업 판단을 한다고 적었고, §8.4 는 막힌 단계가 종류와 후속 행동(부족한 조건, 관측값과 기대값, 마지막 확인 시각, 근거 버전, 해결 담당, 바로 갈 작업)으로 보여야 한다고 적었습니다. §9 는 관측됨과 사람이 보증함을 다르게 표시하고 사람이 보증한 것에는 서명자와 시각을 남기라고 적었습니다. S4a 는 이 가운데 장애를 넣는 손, 인시던트를 읽는 눈, 보류를 푸는 판단까지를 picasso-ops 에서 입증합니다.

입증하는 흐름은 다음과 같습니다. 엔지니어가 화면의 현장·자원 영역에서 기체 하나를 골라 장애를 넣습니다. 그 요청은 운영 서비스와 실행 호스트를 거쳐 site 에 닿고, site 가 같은 프로세스 안의 mimic 엔진을 엔진 잠금 아래에서 직접 불러 결함이나 연결 상태를 바꿉니다. 미들웨어가 그 결과를 단위 실패와 인시던트, 또는 `IN_DOUBT` 와 오래됨으로 드러내면 운영 영역의 인시던트 구역이 설정 버전과 임무 버전, 근거 윈도우와 함께 보입니다. 설비 대기 기한을 넘겨 운영자 보류가 서면 운영자가 같은 화면에서 사유를 적고 완료 확인 또는 재작업을 판단하며, 그 판단은 picasso 인시던트의 `resolution` 과 운영 서비스의 조작 기록 양쪽에 남습니다.

앞 문서와 달리 정한 것이 둘 있습니다. 제안 §10 항목 5 의 «지연» 은 mimic 의 전송 지연이 발행 축에만 걸려 미들웨어의 gRPC 실행에는 보이지 않으므로, 연결 상태를 바꿔 생존 보고가 멈춘 묵은 값(`REPORT_STALE`)으로 보입니다. 항목 5 의 «재시작» 은 S4b 로 넘깁니다. S3a 결정 6 이 S4 로 넘긴 «셀 대역을 틀리게 하는 조작» 은 S3b 가 이미 화면에서 셀 대역 신호를 켜고 끄게 했으므로, S4a 에서는 기체 장애 주입으로 대신합니다.

S4a 가 입증하지 않는 것은 아래 표와 같습니다.

| 입증하지 않는 것 | 자리 |
|---|---|
| 호스트 재기동 뒤 실행 복원, 중복 명령·중복 작업 응답 막기 | S4b |
| 지울 때까지 유지되는 결함과 전송 장애의 주입 | T2. picasso mimic 에 결함 지우기가 생기면 넣습니다 |
| 실행 수준 보류 풀이(`release`)와 실행 중단(`cancel`)의 화면 조작 | T4 |
| 판단 뒤 작업 응답 갱신 | T10 |
| 인시던트의 내보내기와 narrator 연결 | 이번 범위 밖 |

### 2.3 기술 결정 (이 문서가 정함)

| 번호 | 주제 | 결정 | 이유 |
|---|---|---|---|
| T1 | 주입 경로 | 화면에서 운영 서비스, 실행 호스트를 거쳐 site 로 갑니다. site 는 mimic 제어 채널을 열지 않고 좁은 루프백 엔드포인트 하나(`POST /faults`)에서 엔진 객체를 엔진 잠금 아래에서 직접 부릅니다. 시계 RPC 는 노출하지 않습니다 | 제어 채널을 통째로 열면 시계 밀기·시계 모드·시드 RPC 가 함께 열려 site 의 1:1 실제 시간 시계를 깨뜨릴 수 있습니다. S3b 의 신호 중계 `POST /host/cell/signals/{name}` 과 같은 길입니다 |
| T2 | 주입 종류 | 둘입니다. (가) 진행 중 스킬 실패: `humanoid-01` 의 RUNNING `pick_place` 태스크에 `SKILL_EXECUTION_FAILED`. site 가 그 기체의 진행 중 태스크를 스스로 찾고 없으면 거부합니다. (나) 연결 상태: `OFFLINE`·`CONNECTION_BROKEN` 으로 바꾸고 `ONLINE` 으로 복구합니다. 지울 때까지 유지되는 결함(적재물 상실, 위치 상실, 제어권 상실)과 전송 장애는 넣지 않습니다. 정확한 이름은 JSON 계약에 둡니다 | 지울 수 없는 결함은 picasso 에 지우는 호출이 없어 site 재기동 없이는 그 기체가 영영 막힙니다. 전송 장애는 실행에 보이지 않습니다. 지연은 연결 상태의 묵은 값으로 보입니다 |
| T3 | 결정적 보류 | 실행 호스트 템플릿에 `ARRIVAL_WAIT_HOLD`(기한 뒤 `OPERATOR_HOLD`)를 더합니다. 기한은 20초입니다. 엔지니어가 S3b 흐름으로 활성화하면 기한을 넘긴 설비 대기 단위가 운영자 보류가 됩니다 | 제어 채널 없이 결정적으로 만들 수 있는 단위 수준 보류는 설비 대기 기한뿐입니다. Playwright 는 1:1 실시간 런처이고 시계 RPC 를 열지 않으므로(T1) 시간을 밀 수단이 없어, 기한이 짧아야 실시간으로 기다릴 수 있습니다 |
| T4 | 판단 종류와 승인자 | picasso 의 둘(완료 확인 `CONFIRM_DONE`, 재작업 `REWORK`)을 씁니다. 승인자는 운영 서비스 행위자 `X-Ops-User` 로 `Approver(id, PERSON)` 을 만듭니다. 운영자 모드만 허용합니다. 사유는 필수이며 조작 기록에만 남습니다. 실행 수준 보류 풀이(`release`)와 실행 중단(`cancel`)은 이번에 화면에 두지 않습니다 | picasso 인시던트에는 사유 칸이 없습니다. ADR 43 에 따라 승인자 기본값을 두지 않으므로 행위자 헤더에서 받습니다. T2 의 주입으로는 실행 수준 보류가 생기지 않습니다 |
| T5 | 호스트 인시던트 조회 | 목록 `GET /host/incidents` 의 칸을 늘리고(`unresolved`, `resolution`, `fault` 요약, 보류 중인 단위 여부) 단건 상세 `GET /host/incidents/{id}` 를 더합니다. 상세에는 근거 윈도우 이벤트, 단계 위치, 필요·도달 근거 등급, 확인 결과, `blockedBy`, 의도 전체가 실립니다. 모두 호스트 잠금 아래에서 읽습니다 | 현재 목록 14칸에는 fault·blockedBy·근거 윈도우·unresolved·resolution 이 없고 단건 조회가 없어 제안 §8.4 의 항목을 화면이 보일 수 없습니다 |
| T6 | 호스트 판단 | `POST /host/executions/{executionId}/units/{unitId}/resolve`(본문 decision, approverId, requestId)를 더합니다. picasso 의 Resolved·NotHeld·Refused 를 그대로 결과 이름으로 씁니다. 호스트 잠금 아래에서 부릅니다. 운영 서비스가 응답 없음 뒤 재조회할 때는 같은 실행 id·단위 id 의 인시던트 가운데 하나라도 판단자가 행위자이고 결정이 같으며 판단의 실제 시각(`wallClockAt`)이 요청 직전의 실제 시각 이후이면 반영으로 대조합니다(호스트는 requestId 를 저장하지 않고 응답에 돌려주기만 합니다). | 실행 호스트에 판단 엔드포인트가 없습니다. 결과 이름을 바꾸지 않아야 화면과 조작 기록이 picasso 의 셋과 일치합니다 |
| T7 | 운영 서비스 | `GET /api/incidents`, `GET /api/incidents/{id}` 는 호스트를 그대로 중계하고 호스트 불통이면 503 입니다. `POST /api/faults` 는 엔지니어 모드, op `INJECT_FAULT`. 판단은 `POST /api/incidents/resolve` 또는 실행·단위 경로로 운영자 모드, 사유 없으면 400 `REASON_REQUIRED`, op `RESOLVE_OPERATOR_HOLD`, 조작 기록에 승인자·결정·사유. 조작 기록의 결과는 판단의 Resolved 를 SUCCEEDED, NotHeld·Refused 를 REJECTED 로 기록하고 본문에 원래 결과 이름을 남깁니다. 장애 주입은 재조회하지 않습니다. 정확한 경로는 JSON 계약에 둡니다 | 운영 서비스는 picasso 코드를 쓰지 못하므로(`checkNoPicassoOnMain`) 호스트 응답을 picasso 타입 없이 중계하고, 조작 기록의 결과만 S3a 작업 지시의 UNASSIGNED 선례대로 매깁니다. 기존 op 이름(`WRITE_CELL_SIGNAL`, `SUBMIT_JOB_ORDER`, `CHANGE_SITE_SETTINGS`)과 같은 꼴입니다 |
| T8 | 화면 | 현장·자원 영역에 장애 주입 패널(엔지니어 모드만 조작, 기체·종류 선택, 사유 필수, 결과 알림)을 둡니다. 운영 영역에 인시던트 구역(목록 최신부터, 보류 중 강조, 상세 패널에 설정 버전·임무 버전·근거 윈도우·필요/도달 근거·확인 결과·판단 기록)을 둡니다. 보류 단위에 운영자 판단 버튼 둘과 사유 입력(운영자 모드만)을 둡니다. 판단된 인시던트는 «사람이 판단함: <판단자>, <시각>» 으로 관측과 다르게 표시합니다 | 사용자 결정 1·2 와 제안 §9 를 따릅니다 |
| T9 | 자연 실패 | 시나리오가 자연 실패 추첨(rate 0.05·0.01, 시드 0)에 흔들리지 않게 하는 방법은 스파이크에서 정합니다. 시드 0 에서 시나리오 순서를 확인하는 S3a·S3b 와 같은 방식입니다 | 통합 시험 스택의 추첨은 시드가 고정되어 있어 순서를 확인하면 재현됩니다 |
| T10 | 판단 뒤 작업 응답 | `resolve` 가 작업 응답 갱신(`notify`)을 부르지 않는 것은 picasso 의 일이므로 S4a 는 바꾸지 않고 한계로 적습니다. 실행 목록과 인시던트는 판단을 바로 보입니다 | 범위가 picasso 변경 없음입니다 |

## 3. 단계와 완료 기준

통합 시험 `FaultIncidentTest` 는 새 스택에서 순서를 두고 돕니다. 셀 대역 슬롯은 비우지 않으므로 같은 슬롯이 근거 윈도우 앞 폭 안에 채워진 적이 있으면 스킬 실패가 FAILED 가 아니라 운영자 보류가 될 수 있어, 새 스택에서 단계 1 을 먼저 합니다. 단계 1 앞에 엔지니어가 `DATA_V1` 을 활성화합니다. 그래야 인시던트에 임무 버전이 실리며, 코드 정의면 임무 버전은 비어 있습니다. 세부는 스파이크에서 정합니다.

| 단계 | 행위자 | 완료 기준 |
|---|---|---|
| 1 | 엔지니어, 운영자 | 엔지니어가 `DATA_V1` 을 활성화한 뒤, 운영자 작업 지시(PrepareSequencedRack, humanoid-01)가 `pick_place` 를 도는 중 엔지니어가 스킬 실패를 주입하면 그 단위가 FAILED 가 되고, 인시던트(GRASP_FAILED)가 현장 설정 버전·임무 버전과 함께 목록과 상세에 보입니다. 이 인시던트의 확인 결과는 NOT_REQUESTED 로 남지만 설비 확인은 실제로 한 것입니다. 조작 기록에 `INJECT_FAULT` 가 남습니다 |
| 2a | 운영자, 엔지니어 | 운영자가 작업 지시를 내고 로봇 단위가 도는 중 엔지니어가 humanoid-01 연결을 OFFLINE 으로 바꾸면, 시계를 밀지 않은 채 실행이 IN_DOUBT 로 보이고, ONLINE 으로 복구하면 RUNNING 으로 돌아옵니다. 실행이 IN_DOUBT 인 것은 로봇 단위가 RUNNING 인 동안뿐이고, 시계를 밀면 OFFLINE 동안에도 mimic 태스크가 계속 돌아 끝나므로 이 단계는 시계를 밀지 않습니다 |
| 2b | 엔지니어 | 실행이 끝난 뒤 엔지니어가 유휴 humanoid-01 에 OFFLINE 을 넣고 현장 설정의 연결 기준 시간을 하한인 60초로 바꾼 뒤 그동안 시계를 계속 밀면, quadruped-01 은 신선함으로 대조되고 humanoid-01 에는 `REPORT_STALE` 막힘(배정 불가)이 보입니다. ONLINE 으로 복구하면 신선으로 돌아옵니다. 오래됨은 운영 서비스가 registry 의 실제 시각으로 판정하므로 실제 시간 약 60~90초(그동안 quadruped-01 이 신선하도록 보고 주기 30초를 넘겨 가상 시계를 31초씩 거듭 밀며, 선례는 공용 시운전 픽스처의 보고 간격)가 듭니다 |
| 3 | 엔지니어, 운영자 | 엔지니어가 `ARRIVAL_WAIT_HOLD` 버전을 활성화하고 운영자가 작업 지시를 낸 뒤 신호를 켜지 않고 기한 20초를 넘기면 설비 대기 단위가 운영자 보류가 되고 인시던트가 미해결·보류 중으로 보입니다 |
| 4 | 운영자 | 사유를 적어 재작업을 판단하면 대기가 새로 시작되고, 신호를 켜면 실행이 끝납니다. 인시던트에 판단자와 판단이 보이고 조작 기록에 `RESOLVE_OPERATOR_HOLD`(승인자·결정·사유)가 남습니다 |
| 5 | 운영자 | `rack_present` 를 false 로 되돌린 뒤(단계 4 에서 켠 값이 남아 있으면 다음 대기가 곧바로 끝납니다) 또 하나의 보류에서 완료 확인을 판단하면 단위가 근거 없이 완료로 기록되고 «설비 근거 없이 완료 확인» 이 표시됩니다 |
| 6 | 엔지니어, 운영자, 호스트 | 엔지니어 모드의 판단은 403, 사유 없는 판단은 400, 보류가 아닌 단위의 판단은 REJECTED(본문 NotHeld)로 기록, 운영자 모드의 장애 주입은 403, 진행 중 태스크가 없는 기체의 스킬 실패 주입은 거부입니다 |

Playwright 시험은 둘입니다. 엔지니어 모드로 스킬 실패를 주입하고 인시던트가 보이는 단계, 그리고 보류 버전 활성화 뒤 운영자 모드로 재작업을 판단하는 단계입니다. Playwright 는 1:1 실시간 런처이고 시계 RPC 를 열지 않으므로(T1) 시간을 밀 수단이 없어, `ARRIVAL_WAIT_HOLD` 의 기한 20초를 실시간으로 기다립니다. 활성화한 보류 버전은 DB 에 남으므로 보류 단계는 뒤쪽, 작업 지시가 registry 를 거쳐야 해서 registry 를 멈추는 단계 바로 앞에 둡니다. 앞 단계가 `rack_present` 를 켜 두므로 보류 단계는 신호를 먼저 끕니다. 재작업 뒤 대기는 실시간 20초로 새로 시작되고 화면 폴링이 5초라, Playwright 는 재작업 뒤 대기가 다시 시작된 것을 확인한 즉시 신호를 켭니다(늦으면 두 번째 보류가 섭니다).

## 4. 확인한 사실

picasso-ops `e482c33`, picasso `195c1ee` 에서 확인했습니다.

| 항목 | 확인한 사실 |
|---|---|
| mimic 제어 채널 | `ControlServer`(`control.proto` 의 `ControlService`)는 picasso-ops 어디에서도 기동되지 않습니다. site 는 `MimicCli().start(...)` 로 계약 서비스만 엽니다. 제어 채널을 통째로 열면 시계 밀기·시계 모드·시드 RPC 가 함께 열려 site 의 1:1 실제 시간 시계를 깨뜨릴 수 있습니다 |
| 엔진 객체 | `RobotInstance` 의 `tasks.forceFault`, `events.setConnection` 등은 public 이라 site 가 같은 프로세스 안에서 직접 부를 수 있습니다. 엔진 잠금 `MimicServer.exclusive` 아래에서 불러야 합니다. 부른 뒤 따로 밀지 않고 다음 시계 진행의 정착(런처는 1초 주기, 통합 시험은 시계 밀기)에 맡깁니다 |
| 현장 기체 `humanoid-01` | 프로파일 humanoid-a. 실패 모드 둘이 모두 `pick_place` 스킬 수준입니다. `SKILL_EXECUTION_FAILED`(GRASP_FAILED)는 스스로 재시도 가능하고 새 태스크까지 유지됩니다. `PAYLOAD_LOST` 는 개입이 필요하고 지울 때까지 유지됩니다 |
| 현장 기체 `quadruped-01` | 실패 모드 `LOCALIZATION_LOST` 는 로봇 수준이고 지울 때까지 유지됩니다. pick_place 가 없고, 실제 명부에서는 명칭 미티칭이라 시운전이 막혀 있습니다. 통합 시험의 공용 시운전 픽스처(`Commissioned.complete`)는 선언 전에 명칭을 티칭해 두 기체를 모두 시운전 완료로 만듭니다 |
| 스킬 수준 고장 강제 | 그 태스크 id 가 있어야 하고 태스크가 RUNNING·PAUSED·CANCELLING 이어야 합니다 |
| 제어권 상실 강제 | 배타 제어 기종(humanoid)만 됩니다 |
| 지울 때까지 유지되는 결함 | PAYLOAD_LOST, LOCALIZATION_LOST, 제어권 상실은 picasso 에 지우는 호출이 없어 site 를 재기동해야 사라집니다. 그런 결함이 서면 그 기체의 새 실행마다 첫 단위가 막히고(실행 수준 보류 `blockedBy`, 풀이는 `release` 이며 승인자를 받지 않음), 호스트·운영 서비스의 배정 판정은 결함을 보지 않습니다 |
| 연결 상태 강제 | `ONLINE`·`OFFLINE`·`HIBERNATING`·`CONNECTION_BROKEN`. OFFLINE·BROKEN 이면 도는 로봇 단위의 실행이 `IN_DOUBT` 로 보이고(인시던트 없음) 복귀하면 RUNNING 으로 돌아옵니다. 실행이 `IN_DOUBT` 인 것은 로봇 단위가 RUNNING 인 동안뿐이며, 시계를 밀면 OFFLINE 동안에도 mimic 태스크가 계속 돌아 끝납니다. 주입하는 순간 연결 메시지가 registry 에 가서 마지막 보고 시각이 갱신되고 그 뒤 보고가 멈추므로 오래됨은 주입 시점부터 셉니다. 오래됨(`REPORT_STALE`)은 운영 서비스가 registry 의 실제 시각으로 판정하므로 실제 시간에서만 생기고, 연결 기준 시간의 하한은 60초입니다. 오래됨이 되면 기체가 배정 불가가 됩니다 |
| 전송 장애 | DISCONNECT·DELAY·EVENT_LOSS·DUPLICATE·REORDER 는 발행 축(registry HTTP 보고)에만 걸리고 미들웨어의 gRPC 에는 영향이 없습니다 |
| 스킬 실패 강제의 결과 | `pick_place` 진행 중 `SKILL_EXECUTION_FAILED` 를 강제하면 mimic 의 태스크는 RETRIABLE(비종료)이고 손은 HOLDING 으로 남으며, 미들웨어가 그것을 종료로 보고 근거를 확인합니다. 셀 대역은 성공일 때만 슬롯을 채우되 슬롯을 비우지는 않으므로, 같은 슬롯이 근거 윈도우 앞 폭 안에 채워진 적이 없으면 근거 없음으로 단위 FAILED 와 인시던트(`failureClass` GRASP_FAILED)가 남고 라인은 다음 단위로 갑니다. 채워진 적이 있으면 설비 근거가 있어 운영자 보류가 될 수 있습니다. 이때 인시던트의 확인 결과는 NOT_REQUESTED 로 남지만 설비 확인은 실제로 한 것입니다 |
| 운영자 보류(단위 수준)로 가는 길 | `IN_DOUBT` 가 유예를 넘김(제어 채널로 재현 불가), 하위가 전제 조건 미충족으로 거부, 설비 대기 기한에서 `onDeadline=OPERATOR_HOLD`, 실패 보고인데 설비 근거가 있음. 결정적으로 재현할 수 있는 것은 설비 대기 기한입니다. 실행 호스트 템플릿 `ARRIVAL_WAIT` 는 기한 120초 뒤 ABORTED 입니다 |
| `Middleware.resolve` | 서명은 `resolve(executionId, unitId, OperatorDecision{CONFIRM_DONE, REWORK}, Approver)` 입니다. 에이전트는 Refused, 보류 단위가 없으면 NotHeld. 판단을 그 단위의 가장 최근 미해결 인시던트에 `resolution`(decision, at, decidedBy)으로 붙이며 사유 칸과 note 는 없습니다. CONFIRM_DONE 은 설비 근거가 있었으면 E2, 없으면 근거 등급을 올리지 않습니다. 설비 근거 없이 완료 확인한 것은 판단이 CONFIRM_DONE 이고 봉인 때 확인 결과(`verification`)가 MATCHED 가 아닌 것으로 미들웨어의 판단 규칙과 같습니다. `unresolved` 는 봉인할 때 한 번 정해지고 판단 뒤에도 그대로입니다. REWORK 는 그 단위를 새 정체성(새 task id)으로 다시 계획하고 실행이 이어갑니다. 아무도 판단하지 않으면 실행은 정착하지 않고 그 기체는 배정 불가로 남습니다. `resolve` 뒤 작업 응답 갱신(`notify`)은 부르지 않습니다 |
| 실행 호스트 인시던트 | 목록 `GET /host/incidents`(S3c, 14칸: 설정 버전·시간값·임무 버전 포함)에 fault·blockedBy·근거 윈도우·unresolved·resolution 이 없습니다. 단건 조회와 판단 엔드포인트가 없습니다. 잠금 하나와 250ms pump 입니다. 신호 중계 `POST /host/cell/signals/{name}` 이 잠금 밖에서 site 로 넘기고 site 가 응답하지 않으면 503 `CELL_SILENT` 를 내는 선례입니다 |
| 운영 서비스 | 행위자 헤더 `X-Ops-Mode`(engineer 또는 operator)·`X-Ops-User`. 없으면 400 `ACTOR_REQUIRED`, 모드가 맞지 않으면 403. 조작 기록 실행기 `HostOperationRunner` 는 NO_RESPONSE 뒤 재조회합니다. 기존 op 이름은 `WRITE_CELL_SIGNAL`, `SUBMIT_JOB_ORDER`, `CHANGE_SITE_SETTINGS`. S3a 작업 지시는 호스트 결과 UNASSIGNED 를 조작 기록에 REJECTED 로 기록하고 본문에 원래 이름을 남깁니다. 운영 서비스는 picasso 코드를 쓰지 못합니다(`checkNoPicassoOnMain`) |
| 화면 | 운영 영역(작업 지시, 배정 가능, 실행, 셀 대역, 5초 폴링)과 현장·자원 영역(현장 설정, 엔지니어만 편집)입니다 |
| 통합 시험 | 한 JVM 스택(Postgres·site·호스트·운영 서비스). 시간은 site 가상 시계를 밀어서 갑니다. 시계를 밀지 않으면 모든 기체의 보고가 멈춥니다. 오래됨(`REPORT_STALE`)은 registry 의 실제 시각으로 판정하므로 실제 시간이 따로 듭니다. 자연 실패 추첨(rate 0.05·0.01, 시드 0)이 시나리오에 섞일 수 있습니다 |

## 5. site: 장애 주입 엔드포인트

site 는 루프백 엔드포인트 `POST /faults` 하나를 엽니다. mimic 제어 채널은 열지 않으며 시계 밀기·시계 모드·시드는 어느 경로로도 노출하지 않습니다(T1).

| 항목 | 설계 |
|---|---|
| 자리 | 셀 대역을 여는 JDK `HttpServer`(셀 포트)에 `/faults` 를 붙입니다. 호스트는 셀 기준 주소를 재사용합니다 |
| 호출 주체 | 실행 호스트만 부릅니다. 운영 서비스와 화면은 직접 부르지 않습니다 |
| 본문 | 기체 id, 주입 종류, 종류별 값(연결 상태일 때 목표 상태). 정확한 모양은 JSON 계약에 둡니다 |
| 스킬 실패 | site 가 그 기체의 진행 중(RUNNING·PAUSED·CANCELLING) 태스크를 스스로 찾아 `tasks.forceFault` 로 `SKILL_EXECUTION_FAILED` 를 강제합니다. 호출자는 태스크 id 를 알 필요가 없습니다. 진행 중 태스크가 없으면 거부하고 그 이유를 응답에 적습니다 |
| 연결 상태 | `events.setConnection` 으로 `OFFLINE`·`CONNECTION_BROKEN`·`ONLINE` 가운데 하나로 바꿉니다. `HIBERNATING` 은 이번에 쓰지 않습니다(스파이크에서 정함) |
| 잠금과 밀기 | 모든 엔진 호출은 `MimicServer.exclusive` 아래에서 합니다. 엔진을 부른 뒤 따로 밀지 않고 다음 시계 진행의 정착(런처는 1초 주기, 통합 시험은 시계 밀기)에 맡깁니다 |
| 허용하지 않는 것 | `PAYLOAD_LOST`, `LOCALIZATION_LOST`, 제어권 상실, 전송 장애(DISCONNECT·DELAY·EVENT_LOSS·DUPLICATE·REORDER)는 종류 목록에 두지 않습니다. 보내면 거부합니다 |
| 응답 | 받아들임, 거부(이유 코드), 알 수 없는 기체. 정확한 코드는 JSON 계약에 둡니다 |

S3b 의 셀 대역 신호 중계와 같은 꼴이므로, site 의 기동 코드는 셀 대역을 여는 JDK `HttpServer` 에 `/faults` 핸들러를 하나 더 붙이는 것으로 끝납니다. 기체 둘 가운데 스킬 실패 주입이 뜻을 갖는 것은 `humanoid-01` 뿐이며, `quadruped-01` 은 pick_place 가 없어 연결 상태 주입만 받습니다.

## 6. 실행 호스트: 장애 중계, 인시던트 상세, 운영자 판단

실행 호스트는 셋을 더합니다. 장애 중계는 신호 중계처럼 호스트 잠금 밖에서 site 로 넘기고, 호스트 잠금은 인시던트 조회와 판단에만 씁니다.

| 엔드포인트 | 역할 | 설계 |
|---|---|---|
| `POST /host/faults` | 장애 중계 | 본문을 셀 기준 주소의 site `POST /faults` 로 그대로 넘기고 site 의 응답을 돌려줍니다. 호스트는 종류를 해석하지 않으며 잠금을 잡지 않습니다. site 가 응답하지 않으면 신호 중계와 같은 이름으로 503 `CELL_SILENT` 를 냅니다 |
| `GET /host/incidents` | 목록 확장 | S3c 의 14칸에 `unresolved`, `resolution`(decision, at, decidedBy), `fault` 요약(failureClass 등), 보류 중인 단위 여부를 더합니다. `unresolved` 는 봉인할 때 한 번 정해진 값이며 판단 뒤에도 그대로입니다. 보류 중인 단위 여부는 그 단위의 지금 상태가 OPERATOR_HOLD 이고 그 인시던트가 그 단위의 가장 최근 미해결 인시던트일 때만 참입니다. 최신부터 정렬합니다 |
| `GET /host/incidents/{id}` | 단건 상세 | 근거 윈도우 이벤트, 단계 위치(실행 id, 단위 id, 템플릿 단계), 필요 근거 등급과 도달 근거 등급, 확인 결과, `blockedBy`, 의도 전체(설정 버전·시간값·임무 버전 포함)를 실습니다 |
| `POST /host/executions/{executionId}/units/{unitId}/resolve` | 운영자 판단 | 본문 decision(`CONFIRM_DONE` 또는 `REWORK`), approverId, requestId. `Approver(approverId, PERSON)` 으로 `Middleware.resolve` 를 부르고 Resolved·NotHeld·Refused 를 결과 이름으로 그대로 돌려줍니다. 운영 서비스가 응답 없음 뒤 재조회할 때는 같은 실행 id·단위 id 의 인시던트 가운데 하나라도 판단자가 행위자이고 결정이 같으며 판단의 실제 시각(`wallClockAt`)이 요청 직전의 실제 시각 이후이면 반영으로 대조합니다(호스트는 requestId 를 저장하지 않고 응답에 돌려주기만 합니다). |

실행 호스트 템플릿에 `ARRIVAL_WAIT_HOLD` 를 더합니다. 기존 `ARRIVAL_WAIT` 와 같은 설비 대기 단위이되 `onDeadline=OPERATOR_HOLD` 이고 기한은 20초입니다(T3). 엔지니어가 S3b 의 임무 버전 활성화 흐름으로 이 템플릿을 고르면, 신호가 켜지지 않은 채 기한을 넘긴 단위가 운영자 보류가 되고 인시던트가 미해결로 남습니다.

호스트 인시던트는 메모리에만 있습니다. 재기동하면 사라지며, 이것은 S4b 의 자리입니다.

## 7. 운영 서비스

운영 서비스는 picasso 코드를 쓰지 못하므로(`checkNoPicassoOnMain`) 호스트 응답을 picasso 타입 없이 중계합니다. 행위자 검사와 조작 기록만 더하며, 조작 기록의 결과는 판단의 Resolved 를 SUCCEEDED, NotHeld·Refused 를 REJECTED 로 기록하고 본문에 원래 결과 이름을 남깁니다(S3a 작업 지시의 UNASSIGNED 선례).

| 엔드포인트 | 모드 | op 이름 | 설계 |
|---|---|---|---|
| `GET /api/incidents` | 둘 다 | 없음 | 호스트 목록을 그대로 중계합니다. 호스트 불통이면 503 입니다 |
| `GET /api/incidents/{id}` | 둘 다 | 없음 | 호스트 단건 상세를 그대로 중계합니다. 호스트 불통이면 503 입니다 |
| `POST /api/faults` | engineer | `INJECT_FAULT` | 기체 id, 종류, 값, 사유를 받습니다. 재조회하지 않으므로 조작 실행기는 재조회 지연 없이 씁니다. 사유 없으면 400 `REASON_REQUIRED`. `HostOperationRunner` 로 호스트 `POST /host/faults` 를 부르고 조작 기록에 행위자·기체·종류·사유·결과를 남깁니다. site 가 응답하지 않아 호스트가 503 `CELL_SILENT` 를 내면 응답 없음(NO_RESPONSE)으로 기록합니다. 장애 주입은 확인할 칸이 없으므로 재조회하지 않습니다 |
| 판단 경로(`POST /api/incidents/resolve` 또는 실행·단위 경로, JSON 계약에서 정함) | operator | `RESOLVE_OPERATOR_HOLD` | 실행 id, 단위 id, 결정, 사유를 받습니다. 사유 없으면 400 `REASON_REQUIRED`. 승인자 id 는 `X-Ops-User` 에서 가져옵니다. 호스트 결과(Resolved·NotHeld·Refused)를 그대로 돌려주고 조작 기록에 승인자·결정·사유·결과를 남깁니다. 결과는 Resolved 이면 SUCCEEDED, NotHeld·Refused 이면 REJECTED 이고 본문에 원래 결과 이름을 남깁니다. 응답 없음 뒤 재조회는 같은 실행 id·단위 id 의 인시던트 가운데 하나라도 판단자가 행위자이고 결정이 같으며 판단의 실제 시각(`wallClockAt`)이 요청 직전의 실제 시각 이후이면 반영으로 대조합니다(같은 사람이 같은 단위를 앞서 판단한 기록과 섞이지 않게. 재작업 뒤 두 번째 보류가 서도 반영된 판단을 놓치지 않게 «가장 최근» 과 «보류가 아님» 조건은 두지 않고, 판단 시각 `at` 은 가상 시각이라 쓰지 않습니다). 대조할 값은 요청을 보낼 때 정해 둡니다 |

행위자 헤더가 없으면 400 `ACTOR_REQUIRED`, 모드가 맞지 않으면 403 인 것은 기존과 같습니다. 판단 사유는 picasso 인시던트에 실리지 않으므로 조작 기록이 사유의 유일한 자리입니다. NotHeld 와 Refused 는 조작 기록에 REJECTED 로 남고 본문에 원래 이름이 있습니다.

## 8. 화면

### 8.1 장애 주입 패널

현장·자원 영역에 둡니다. 엔지니어 모드에서만 조작할 수 있고 운영자 모드에서는 읽기만 됩니다.

| 요소 | 설계 |
|---|---|
| 기체 선택 | 현장 기체 목록에서 하나를 고릅니다 |
| 종류 선택 | 스킬 실패(진행 중 태스크), 연결 상태(OFFLINE, CONNECTION_BROKEN, ONLINE 복구). 정확한 표시 문구는 JSON 계약의 이름을 따릅니다 |
| 사유 입력 | 필수입니다. 비어 있으면 보내지 않습니다 |
| 결과 알림 | 받아들임, 거부(이유), 응답 없음을 알림으로 보입니다. 운영 서비스의 조작 실행기는 5xx 본문을 넘기지 않으므로 site 불통(`CELL_SILENT`)과 호스트 불통은 화면에서 «응답 없음» 하나로 보이고, `CELL_SILENT` 는 조작 기록의 응답 칸에만 남습니다. 거부 이유에는 «진행 중 태스크 없음» 같은 site 의 응답 코드를 풀어 적습니다 |
| 기록 | 조작 기록 목록에 `INJECT_FAULT` 항목으로 보입니다 |

### 8.2 인시던트 목록과 상세

운영 영역에 인시던트 구역을 둡니다. 5초 폴링은 기존 운영 영역과 같습니다.

| 요소 | 설계 |
|---|---|
| 목록 | 최신부터 보입니다. 각 줄에 발생 시각, 실행 id, 단위 id, 기체, 실패 종류(`failureClass`), 미해결 여부, 보류 중 여부, 현장 설정 버전, 임무 버전을 보입니다. «미해결» 은 `unresolved` 이고 판단(`resolution`)이 없을 때입니다. «보류 중» 강조는 그 단위의 지금 상태가 OPERATOR_HOLD 이고 그 인시던트가 그 단위의 가장 최근 미해결 인시던트일 때만입니다(재작업 뒤 두 줄이 강조되지 않게) |
| 상세 패널 | 줄을 고르면 단건 상세를 보입니다. 설정 버전과 시간값, 임무 버전, 근거 윈도우 이벤트, 단계 위치, 필요 근거 등급과 도달 근거 등급, 확인 결과, `blockedBy`, 판단 기록. 확인 결과 NOT_REQUESTED 는 설비 확인을 하지 않았다는 뜻이 아니므로(단계 1 인시던트가 그렇습니다) «설비 확인 안 함» 으로 풀지 않고 코드 이름 그대로 보입니다 |
| 관측과 판단의 구분 | 판단되지 않은 인시던트는 관측값으로만 보입니다. 판단된 인시던트는 «사람이 판단함: <판단자>, <시각>» 과 결정을 함께 보여 관측과 다르게 표시합니다(제안 §9) |
| 근거 없는 완료 | 판단이 CONFIRM_DONE 이고 봉인 때 확인 결과(`verification`)가 MATCHED 가 아니면 «설비 근거 없이 완료 확인» 으로 표시합니다(미들웨어의 판단 규칙과 같음). picasso 인시던트에 note 가 없으므로 화면이 이 둘로 판정합니다 |

### 8.3 운영자 판단

보류 중인 단위의 인시던트 상세에만 보입니다. 운영자 모드에서만 조작할 수 있습니다.

| 요소 | 설계 |
|---|---|
| 버튼 둘 | 완료 확인(`CONFIRM_DONE`), 재작업(`REWORK`) |
| 사유 입력 | 필수입니다. 비어 있으면 보내지 않습니다 |
| 결과 | Resolved 이면 상세를 다시 읽어 판단 기록을 보입니다. NotHeld 이면 «보류 단위가 아닙니다» 를 알립니다. Refused 이면 «에이전트 판단은 거부됩니다» 를 알립니다. 운영 서비스가 403 을 돌려주면 모드가 맞지 않음을 알립니다 |
| 기록 | 조작 기록 목록에 `RESOLVE_OPERATOR_HOLD` 항목으로 승인자·결정·사유·결과(SUCCEEDED 또는 REJECTED, 본문에 원래 결과 이름)가 보입니다 |
| 두지 않는 것 | 실행 수준 보류 풀이(`release`)와 실행 중단(`cancel`) 버튼은 두지 않습니다(T4) |

## 9. 오류 처리

| 상황 | 처리 |
|---|---|
| 운영자 모드로 장애 주입 | 운영 서비스가 403. 화면은 패널을 조작 불가로 보입니다 |
| 엔지니어 모드로 운영자 판단 | 운영 서비스가 403. 화면은 버튼을 조작 불가로 보입니다 |
| 행위자 헤더 없음 | 400 `ACTOR_REQUIRED` |
| 사유 없음(주입, 판단) | 400 `REASON_REQUIRED`. 화면은 보내기 전에 막습니다 |
| 진행 중 태스크가 없는 기체에 스킬 실패 주입 | site 가 거부하고 호스트·운영 서비스가 그대로 중계합니다. 조작 기록에 거부 결과가 남습니다 |
| 허용하지 않는 종류(지울 수 없는 결함, 전송 장애) | site 가 거부합니다. 화면은 애초에 종류 목록에 두지 않습니다 |
| 알 수 없는 기체 | site 가 거부합니다 |
| 보류가 아닌 단위에 판단 | 호스트가 NotHeld 를 돌려주고 조작 기록에 REJECTED(본문 NotHeld)로 남깁니다 |
| 에이전트 승인자 | 호스트는 `PERSON` 만 만들므로 발생하지 않습니다. picasso 가 Refused 를 돌려주면 그대로 중계하고 조작 기록에 REJECTED(본문 Refused)로 남깁니다 |
| 호스트 불통 | 읽기(인시던트 목록·상세)는 운영 서비스가 503 `HOST_SILENT`, 쓰기(장애 주입·판단)는 200 에 결과 NO_RESPONSE. 판단은 `HostOperationRunner` 가 NO_RESPONSE 뒤 재조회로 결과를 맞추고, 장애 주입은 확인할 칸이 없으므로 재조회하지 않습니다 |
| site 불통 | 호스트가 503 `CELL_SILENT`(신호 중계와 같은 이름)를 내고 운영 서비스는 응답 없음(NO_RESPONSE)으로 기록합니다 |
| 같은 requestId 로 판단 재요청 | 같은 실행 id·단위 id 의 인시던트 가운데 하나라도 판단자가 행위자이고 결정이 같으며 판단의 실제 시각이 요청 직전 실제 시각 이후이면 반영된 것으로 대조합니다. 호스트는 requestId 를 저장하지 않고 응답에 돌려주기만 합니다 |
| 자연 실패 추첨이 시나리오에 섞임 | T9. 시드 0 에서 순서를 확인하는 방법을 스파이크에서 정합니다 |

## 10. 시험

| 시험 | 자리 | 결함 주입 |
|---|---|---|
| site `POST /faults` 가 진행 중 태스크를 찾아 스킬 실패를 강제함 | site 단위 시험 | 태스크 찾기를 빼면 거부가 나야 합니다 |
| site 가 허용하지 않는 종류를 거부함 | site 단위 시험 | 종류 목록에 `PAYLOAD_LOST` 를 넣으면 시험이 빨개져야 합니다 |
| site 가 엔진 잠금 아래에서 부름 | site 단위 시험 | 잠금을 빼면 동시 호출 시험이 빨개져야 합니다(방법은 스파이크에서 정함) |
| 호스트 인시던트 목록의 새 칸 | 호스트 시험 | `unresolved` 를 봉인 값 대신 판단 뒤 뒤집히게 하면 빨개져야 합니다. 보류 중 여부를 그 단위의 가장 최근 미해결 인시던트로 한정하지 않으면 재작업 뒤 두 줄이 참이 되어 빨개져야 합니다 |
| 호스트 단건 상세의 근거 윈도우·`blockedBy`·의도 전체 | 호스트 시험 | 칸 하나를 비우면 빨개져야 합니다 |
| 호스트 `resolve` 가 Resolved·NotHeld·Refused 를 그대로 돌려줌 | 호스트 시험 | 결과 이름을 바꾸면 빨개져야 합니다 |
| `ARRIVAL_WAIT_HOLD` 가 기한 20초 뒤 운영자 보류가 됨 | 호스트 시험 | `onDeadline` 을 ABORTED 로 바꾸면 빨개져야 합니다 |
| 운영 서비스 모드 검사(주입은 엔지니어, 판단은 운영자) | 운영 서비스 시험 | 모드 검사를 빼면 403 시험이 빨개져야 합니다 |
| 운영 서비스 사유 필수 | 운영 서비스 시험 | 검사를 빼면 400 시험이 빨개져야 합니다 |
| 조작 기록에 `INJECT_FAULT`·`RESOLVE_OPERATOR_HOLD` 가 승인자·결정·사유와 남음 | 운영 서비스 시험 | 사유를 기록에서 빼면 빨개져야 합니다. NotHeld 를 SUCCEEDED 로 기록하면 빨개져야 합니다 |
| `FaultIncidentTest` 단계 1~6 | 통합 시험(새 스택) | 단계마다 하나씩, 세부는 스파이크에서 정합니다 |
| 화면 Playwright 둘 | 화면 시험 | 판단 버튼을 운영자 모드 밖에서도 보이게 하면 빨개져야 합니다 |

통합 시험의 시간은 site 가상 시계를 밀어서 갑니다. 설비 대기 기한 20초는 시계 밀기로 넘깁니다. 오래됨(`REPORT_STALE`)만은 운영 서비스가 registry 의 실제 시각으로 판정하므로, 단계 2b 는 연결 기준 시간을 60초로 두고 실제 시간 약 60~90초를 기다리며 그동안 시계를 계속 밀어 quadruped-01 의 보고가 멈추지 않게 합니다. 단계 2a 는 시계를 밀지 않습니다.

## 11. 한계와 다음 단계

- 지울 수 없는 결함(`PAYLOAD_LOST`, `LOCALIZATION_LOST`, 제어권 상실)이 picasso mimic 에 남아 있어 그 결함은 주입하지 않습니다. picasso 에 지우는 제어가 생기면 종류 목록에 넣습니다.
- 호스트가 잠금을 기다리다 늦게 반영한 판단은 1초 뒤 재조회에서 반영 안 됨으로 남을 수 있습니다. 호스트가 requestId 를 저장하지 않아 처리 중을 구분하지 못합니다. 재조회의 실제 시각 비교는 운영 서비스와 호스트가 같은 기계에 있다는 전제입니다.
- 판단 사유는 picasso 인시던트에 실리지 않고 운영 서비스 조작 기록에만 있습니다.
- 호스트 인시던트는 메모리에만 있어 재기동하면 사라집니다. S4b 의 자리입니다.
- 판단 뒤 작업 응답이 바로 갱신되지 않습니다(T10). picasso 의 `resolve` 가 `notify` 를 부르지 않기 때문이며 S4a 는 바꾸지 않습니다.
- 전송 장애는 실행에 보이지 않아 주입하지 않습니다. 지연은 연결 상태의 묵은 값으로만 보입니다.
- 오래됨(`REPORT_STALE`)은 registry 의 실제 시각으로 판정하므로 통합 시험의 단계 2b 는 실제 시간 약 60~90초가 듭니다.
- 셀 대역 슬롯은 비우지 않으므로 같은 슬롯이 근거 윈도우 앞 폭 안에 채워진 적이 있으면 스킬 실패가 FAILED 가 아니라 운영자 보류가 될 수 있습니다. 통합 시험은 새 스택에서 단계 1 을 먼저 합니다.
- `quadruped-01` 은 pick_place 가 없어 연결 상태 주입만 받습니다.
- 실행 수준 보류 풀이(`release`)와 실행 중단(`cancel`)은 화면에 두지 않습니다.
- picasso 한계 레지스터 §15.202(판단자 `decidedBy` 는 내보내기에 실리지 않음, 소비자 대기)의 소비자가 S4a 화면이라는 메모를 picasso 쪽에 handoff 로 넘깁니다.
- 다음은 S4b(호스트 재기동 뒤 실행 복원, 중복 명령·중복 작업 응답 막기, 필요하면 picasso 선행 PR)이고, 그 뒤 운반 임무(AMR 플릿 연동)가 후보입니다.
