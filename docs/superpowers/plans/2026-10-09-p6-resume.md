# P6 재기동 뒤 다시 짓기 입구 resume Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking. 단, 이 계획은 묶음 하나(Task 1·2·3)를 구현자 하나가 하고, 검토는 묶음이 끝난 뒤 컨트롤러가 기계 대조와 시험으로 한다.

**Goal:** 담는 쪽(실행 호스트)이 재기동한 뒤 자기 기록으로 넘긴 작업 지시, 기체, 임무 정의와 버전으로 같은 정체성의 실행을 다시 짓는 입구 `Middleware.resume` 을 더한다. 넘겨받은 정의로 계획하고 배정 관문을 다시 걸지 않으며, 기체 스냅숏의 태스크 id 접미사에서 로봇 단위의 재작업 횟수를 되찾는다. 스냅숏에 태스크가 있는 마지막 로봇 단위 앞의 설비 대기는 근거 등급 E0 인 채 끝난 것으로 두고, 그 앞의 로봇 단위는 다시 관측한 성공에 설비 근거를 다시 묻지 않고 E0 으로 닫는다. 스냅숏을 못 읽으면 실행을 만들지 않는다. 계약과 내보내기 형식은 그대로다.

**Architecture:** `submit` 의 판정 뒤 실행 생성부(실행 id, `revision = order.version`, `approvedBy`, `ACCEPTED`, 표 등록)를 private `create(order, robotId, active, planned, approvedBy)` 로 떼어 낸다(Task 1, 동작 무변경). `resume(order, robotId, mission: ActiveMission): Submission` 은 같은 작업 지시 id 의 실행이 있으면 `revise` 로 가고, 없으면 WorkMaster 대조, 스냅숏 한 번 읽기, `evidenceRefusal`, `mission.capability.plan(order)`, `create(..., approvedBy = null)`, private `rebuildFrom(execution, snapshot)` 차례로 돈다. `rebuildFrom` 이 로봇 단위의 `attempt`, 앞선 `SIGNAL` 단위의 `DONE`, 앞선 로봇 단위의 표시(`Execution.resumedPrior`)를 정하고 실행 자취에 `RESUME_ATTEMPT`·`RESUME_SIGNAL_PASSED`·`RESUME_PRIOR_ROBOT` 줄을 남긴다. `beginVerify` 는 새 인자 `prior` 가 참이면 설비를 다시 묻지 않고 하류 등급(E0) 그대로 닫는다. 공개 상수 넷은 `Middleware.Companion` 에 둔다. 로봇 단위 상태는 첫 pump 가 같은 태스크 id·리비전으로 `StartTask` 를 다시 보내 기체의 기존 핸들에서 다시 관측한다.

**Tech Stack:** Kotlin, JUnit5 + kotlin.test, 각본 더블(`ResumeTest` 안의 `RobotPort` 더블 `Robot`, 설비 대기와 로봇 단위가 번갈아 서는 정의 `Interleaved`), picasso 게이트(`DocumentClaimsTest`, `GroundTruthTest`), `tools/stamp.py`.

**근거 스펙:** picasso-ops `docs/superpowers/specs/2026-10-09-s4b-restart-recovery-design.md` §5(스펙 검토 2회), 기술 결정 T1, §3 의 P6 완료 기준. P6 은 S4b 앞의 picasso PR 하나다(스펙 §3).

**스펙이 계획에 맡긴 것과 이 계획이 정한 것(스파이크에서 정함):**
- 시그니처: `fun resume(order: JobOrder, robotId: String, mission: ActiveMission): Middleware.Submission`, `submit` 의 private 오버로드 바로 뒤. 실행을 세우는 부분은 `submit` 과 함께 쓰는 private `create` 로 먼저 옮긴다(Task 1, picasso 시험 369 무수정 통과).
- 전제: 넘기는 작업 지시는 이전 인스턴스가 받은 마지막 버전이다(KDoc). 리비전이 단위의 `revision` 이 되고 태스크의 멱등은 같은 `task_id`·`revision` 에만 서므로, 낮은 버전이면 기체가 기존 태스크에 붙여 주지 않는다.
- 공개 상수 넷(`Middleware.Companion`): `RESUME_SNAPSHOT_UNREADABLE = "기체 스냅숏을 못 읽어 다시 짓지 않는다"`(거부 사유의 앞머리, 담는 쪽이 DEFERRED 를 가른다), `RESUME_ATTEMPT`, `RESUME_SIGNAL_PASSED`, `RESUME_PRIOR_ROBOT`(실행 자취의 종류). 접미사 정규식 `RETRY_SUFFIX = Regex("""@r([1-9]\d*)""")` 는 private 이고 `startUnit` 이 붙이는 접미사와 맞는다(앞자리 0 과 `@r0` 은 받지 않는다). 접미사는 `matchEntire` 로 보므로 다른 단위 id 가 앞머리인 단위의 태스크를 제 것으로 읽지 않는다.
- WorkMaster 대조: 스펙 §5 에 없던 거부. 넘겨받은 정의의 `workMasterId` 가 작업 지시와 다르면 `Rejected("넘겨받은 임무 정의의 WorkMaster 가 작업 지시와 다르다: 정의=…, 작업 지시=…")`, 실행 없음.
- 검사 순서: 기존 실행(`revise`) → WorkMaster 대조 → 스냅숏 한 번 → 근거 등급(`evidenceRefusal`, `submit` 과 같은 문장) → 계획과 생성 → 다시 짓기. WorkMaster 대조가 스냅숏 앞이라 정의가 틀린 행은 기체 스냅숏을 못 읽을 때도 DEFERRED 가 아니라 그 밖의 거부(GAVE_UP)로 간다. 배정 관문(`admits`)은 부르지 않는다. `Rejected` 의 `remedy`·`alternativeLocations` 는 null, `remedySearches()` 에 남는 것 없음.
- 스냅숏 거부 사유: `기체 스냅숏을 못 읽어 다시 짓지 않는다: robot=<robotId>, 재작업 횟수와 지난 설비 대기를 정할 근거가 없다`.
- 재작업 횟수: `Route.ROBOT` 단위마다 스냅숏 `tasks` 키 가운데 `jobOrderId#unitId`(0) 이거나 `jobOrderId#unitId@rN` 인 것의 가장 큰 N(수로 견줌). 계약 스냅숏의 태스크 `attempt` 칸은 읽지 않는다(picasso `RobotSnapshot.tasks` 는 `Map<String, TaskState>` 다). 플릿 단위는 되찾지 않는다.
- 마지막 로봇 단위: 스냅숏에 태스크가 있는 마지막 `Route.ROBOT` 단위(계획 순서, 플릿 단위는 세지 않음). 기체에 그 작업 지시의 태스크가 없으면 아래 두 규칙 모두 쓰지 않는다.
- 설비 대기: 마지막 로봇 단위보다 앞선 `SIGNAL` 단위만 `state = DONE`, 나머지 칸은 생성 때 값(근거 등급 E0). 그 뒤 대기는 `PENDING` 이라 다시 기다리고, 재기동 사이에 바뀐 신호로 곧바로 보류나 중단이 날 수 있다.
- 앞선 로봇 단위(`RESUME_PRIOR_ROBOT` 규칙): 마지막 로봇 단위보다 앞선 로봇 단위는 `PENDING` 으로 서고, pump 가 다시 관측한 `SUCCEEDED` 에 설비 근거를 다시 묻지 않고 `DONE`, 근거 등급 E0, `verification = NOT_REQUESTED` 로 닫는다. 실패로 다시 관측되면 보통의 실패 경로를 탄다. 마지막 로봇 단위는 보통대로 확인한다. 이전 인스턴스의 근거 확인 결과는 넘어오지 않는다.
- 자취 줄: `ObservedEvent(sequence = 그 기체 뷰의 커서, 없으면 0, occurredAt = now(), local = true)`. `RESUME_ATTEMPT` 는 태스크가 있는 로봇 단위마다(N 이 0 이어도) `"<unitId>: attempt=<N> (스냅숏 태스크 <taskId>)"`, `RESUME_SIGNAL_PASSED` 는 통과로 둔 대기마다 `"<unitId>: 뒤 로봇 단위 <마지막 로봇 단위 id> 의 태스크가 기체에 있어 통과한 것으로 둔다, 이 인스턴스가 관측하지 않아 근거 등급 E0"`, `RESUME_PRIOR_ROBOT` 은 앞선 로봇 단위마다 `"<unitId>: 뒤 로봇 단위 <마지막 로봇 단위 id> 보다 앞서 성공을 다시 관측해도 설비 근거를 다시 묻지 않는다, 근거 등급 E0"`. 순서는 `RESUME_ATTEMPT` 전부(단위 순서), `RESUME_SIGNAL_PASSED` 전부, `RESUME_PRIOR_ROBOT` 전부. 단위 메모(`unit.note`)에는 안 적으므로 작업 응답의 미완 단위 값은 그대로다.
- 시험: `ResumeTest` 17개(계획 1, 관문·탐색 기록 1, WorkMaster 1, 근거 등급 1, 재작업 횟수·접미사 4, 앞선 로봇 단위 2, 설비 대기 경계 3, 통과 대기 뒤 시작과 도달 근거 등급 E0 1, 스냅숏 거부 1, 멱등 1, 리비전 경로 1). 더블은 시험 파일 안의 각본 `RobotPort`(`Robot`): 재기동 전 태스크를 들고 같은 태스크 id 에 기존 핸들을 돌려주며 `created` 로 새 태스크 수를, `unreadable` 로 스냅숏 null 을 만든다. 재작업 접미사 태스크를 재기동 전 상태로 바로 세우려고 mimic 을 안 쓴다. 기존 시험은 고치지 않는다.
