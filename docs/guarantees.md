## 배포 전제

이 문서에서 설명하는 보장은 다음 배포 전제에서만 유효합니다.

- 운영 서비스 한 프로세스: 같은 DB 에 활성 운영 서비스는 하나여야 합니다. 스테이션 조정기의 `tick` 과 `rework` 는 JVM 의 `@Synchronized` 와 DB 행 잠금·advisory 잠금으로 직렬화됩니다. 운영 서비스 프로세스마다 인스턴스 id(`ops-<UUID>`, 프로세스마다 새로)가 있고, 기동 때 `ops.service_instance` 에 자기 행을 넣어 주기마다 DB 시각으로 심장박동을 고치며, 정상 종료 때 멈춤(`stopped_at`)을 적습니다. 스테이션 작업 상태를 쓰는 모든 문장이 `ops.station_run.instance_id` 에 그 프로세스의 인스턴스 id 를 적습니다. `tick` 이 남은 `RETRYING`·`REWORKING` 을 만나면 이 인스턴스가 남긴 것이면 «정리 실패» 사유(예: «재평가 뒤 상태 정리 실패; 실행 관측과 현장 확인 필요»)로 `REVIEW_REQUIRED` 로 넘깁니다. 다른 인스턴스가 남긴 것이면 그 인스턴스의 심장박동이 만료됐거나 그 인스턴스가 멈춤을 적었을 때만 «프로세스 중단» 사유(예: «재평가 중 프로세스 중단; 실행 관측과 현장 확인 필요»)로 넘기고, 살아 있으면 건드리지 않습니다. 그래서 같은 DB 에 둘째 프로세스가 떠도 살아 있는 첫째의 점유를 빼앗지 않습니다. 그래도 대기열 점유(`owner`), `DISPATCHING` 재조회, 설비 쓰기에는 인스턴스 조건이 없고, 리스·세대·펜싱이 없어 같은 DB 에 운영 서비스 둘 이상을 띄우는 구성은 여전히 지원하지 않고 검증하지도 않았습니다. (코드: `ops-service/src/main/kotlin/dev/picasso/ops/service/stations/StationCoordinator.kt` 의 `tick`, `leftover`, `ops-service/src/main/kotlin/dev/picasso/ops/service/instance/OpsInstance.kt`, `ops-service/src/main/resources/db/ops/V21__service_instance_heartbeat.sql`)
- 실행 호스트 한 프로세스: 같은 DB 에 활성 실행 호스트는 하나여야 합니다. 실행 호스트도 인스턴스(미들웨어 `instanceId`)마다 `mission.host_instance` 에 같은 방식으로 심장박동을 적습니다. 기동 복원은 행을 든 인스턴스(그 작업 지시의 마지막 `RESTORED` 이벤트의 인스턴스, 없으면 받은 인스턴스)가 자기이거나 그 심장박동이 끊긴 행만 리빌드합니다. 살아 있는 다른 인스턴스가 든 행은 `DEFERRED`(사유 `살아 있는 다른 인스턴스가 든 실행이라 리빌드하지 않는다: instance=<id>`)로 미루고 그 기체를 판정에서 뺍니다. 그 인스턴스가 만료되면 pump 가 리빌드합니다. 이것은 둘째 호스트가 첫째의 실행을 빼앗지 않게 할 뿐입니다. 둘째 호스트의 새 제출·판정·pump 는 막지 않습니다(유휴 판정은 자기 메모리의 실행만 봅니다). 같은 DB 에 둘을 띄우는 구성은 지원하지 않고 검증하지 않았습니다. (코드: `mission-host/src/main/kotlin/dev/picasso/ops/host/MissionHost.kt` 의 `restoreRow`, `retryDeferred`, `mission-host/src/main/kotlin/dev/picasso/ops/host/store/HostRecords.kt` 의 `beat`, `stopInstance`, `instanceLive`, `mission-host/src/main/resources/db/mission/V7__host_instance_heartbeat.sql`)
- 비정상 종료 뒤 재기동: 정상 종료(Spring 컨텍스트 닫힘)는 멈춤(`stopped_at`)을 적어 다음 기동이 곧바로 이어 받습니다. 비정상 종료(SIGKILL, 전원 차단)는 멈춤을 못 적습니다. 다음 기동은 앞 인스턴스가 든 행을 심장박동 만료까지(기본 30초) `DEFERRED` 로 두고 그동안 그 기체를 배정에서 뺍니다. 운영 서비스가 남긴 `RETRYING`·`REWORKING` 점유도 만료까지 그대로입니다. 만료 폭(주기 5초, 만료 30초)은 실측 없이 잡은 값이고 리스가 아닙니다. 만료 뒤 깨어난 프로세스(긴 GC 정지 등)를 막지 않습니다. 비정상 종료 자체를 재는 시험은 없습니다(Playwright `lifecycle.spec.ts` 14단계의 SIGKILL 재기동은 종결한 실행만 있어 미룸이 드러나지 않습니다).
- 격리된 PoC 망: 운영 서비스, 실행 호스트, registry, 셀 대역은 `127.0.0.1` 에만 바인딩되고 mimic gRPC 는 모든 인터페이스에 열립니다. 실행 호스트 REST 와 셀 대역에는 인증이 없습니다. «이 기계 밖에서 쓰지 않는다»는 `.env` 첫 줄 주석의 전제를 따릅니다.
- 모드 헤더는 인증이 아님: 화면 API 의 `X-Ops-Mode`·`X-Ops-User` 헤더는 역할과 사용자 이름을 고르는 값입니다. API 에 닿을 수 있는 사람은 누구나 이 헤더를 붙일 수 있습니다.
- 외부 주문 토큰 하나: 외부 주문 API 는 공유 Bearer 토큰 하나(`PICASSO_INTEGRATION_TOKEN`)와 설정 출처 하나로 상위 시스템을 식별합니다. 테넌트별 권한 체계(IAM)가 아닙니다. 토큰이 비면 API 가 꺼집니다.
- 콜백 재시도에 끝이 없음: 결과 콜백 전달은 시도 수 상한이나 영구 실패 분류 없이 계속 다시 보냅니다. 다음 시도까지의 대기는 2의 min(시도 수, 8)제곱 초라 최대 256초입니다(코드에는 300초 상한이 있지만 닿지 않음). 4xx 응답도 다시 보냅니다. 콜백 주소는 루프백 IP 리터럴 http 만 받습니다. (코드: `ops-service/src/main/kotlin/dev/picasso/ops/service/requests/WorkResultDelivery.kt`)

## 보장하는 것

아래 보장은 «배포 전제»를 만족할 때만 성립하며, 시험 메서드 이름은 그 보장을 지키는 단언이 있는 곳입니다. 코드 경로 접두 `ops-service/src/main/kotlin/dev/picasso/ops/service/`는 여기서 밝히고 아래 코드 항목에서는 `requests/WorkRequests.kt`처럼 줄여 씁니다. 시험 위치는 운영 서비스 시험이 `ops-service/src/test/kotlin/dev/picasso/ops/service/`, 통합 시험이 `e2e/src/test/kotlin/dev/picasso/ops/e2e/`, 화면 시험이 `ui/e2e/`입니다.

### 작업 요청 선행 저장

- 동작: 외부 주문, 호출 계약 호출, 화면 요청은 실행 호스트를 부르기 전에 `ops.work_request` 행을 독립 트랜잭션으로 커밋합니다. `(source_system_id, external_order_id)` 가 유일하고, 같은 키에 같은 본문(키 정렬 JSON 의 SHA-256)이면 기존 작업 요청을 돌려주며 다시 제출하지 않고, 다른 본문이면 409 `ORDER_CONFLICT` 입니다.
- 코드: `requests/WorkRequests.kt` 의 `receivePrepared`, `ops-service/src/main/resources/db/ops/V6__work_requests.sql` 의 유일 제약

### 공유 스테이션 해제 조건

### 부분 완료·잔여 파지 기체의 배정 제외

- 동작: 실행 호스트 판정의 진행 중인 실행은 picasso `PhysicalState.occupiesRobot` 이라 부분 완료(`PARTIAL`) 실행의 기체에 새 작업 지시를 배정하지 않지만, 해당 실행의 리비전은 제 실행을 진행 중인 실행으로 세지 않아 그 기체에서 개정합니다. 다만 그 기체가 잔여 파지 표시나 다른 실행 점유 등으로 호스트 판정에서 제외되면 `UNASSIGNED` 가 됩니다. 부분 완료는 운영자 실행 취소로 닫으며, 취소 행을 먼저 적고 미들웨어를 부르고 다음 pump 가 `ABORTED` 로 종결시킵니다. 종결할 때 마지막 로봇 단위(계획 순서)의 파지 관측이 `HOLDING` 이면 같은 트랜잭션에서 잔여 파지 표시를 적고, 사람이 빈손을 확인해 해소할 때까지 그 기체를 뺍니다. 표시는 재기동 뒤에도 DB 에서 다시 읽습니다. 그 작업 지시에 운영자 취소가 적혀 있으면(예: 취소를 적은 뒤 다음 pump 가 `ABORTED` 로 종결시키기 전에 실행 호스트가 재기동한 경우) 기동 복원이 리빌드한 실행에 그 취소를 한 번 다시 걸며, 취소 행은 새로 적지 않고 리빌드한 실행의 `cancel` 칸에는 그 작업 지시의 처음 취소 행이 실립니다. 기동 복원 시 실행 호스트는 리빌드한 실행에 기록된 운영자 취소를 곧바로 다시 겁니다. 첫 pump는 `StartTask`를 다시 보내지 않고 기체 스냅숏에서 찾은 태스크에 붙어 취소를 보내며 하위가 끝난 뒤 종결합니다(태스크가 이미 끝났으면 취소 없이 그 종료로 판정하고, 기체 스냅숏을 못 읽으면 `CANCELING`에서 대기합니다). 리빌드한 실행에 운영자 취소를 다시 내면 `NOT_CANCELABLE`(«이미 취소를 건 실행이다»)입니다. 취소와 해소의 승인자는 사람뿐입니다(DB `CHECK`). 이 표시는 실행 호스트의 운영 정책(ADR 41)이고 picasso 보장이 아닙니다(picasso 는 종결한 실행의 파지를 판단이 아니라 정보로 둡니다, §15.146). 건너뛴 대상이 있는 부분 완료는 운영자의 건너뛴 대상 재작업으로도 이어갈 수 있으며, 이때 실행은 다시 `RUNNING`으로 돌아가고 실행 호스트에서 `PARTIAL` 실행은 종결로 기록되지 않아 `REOPENED` 이벤트가 남지 않지만 `FAILED` 실행은 `REOPENED`를 기록합니다.

### 작업 허가로 새 로봇 명령 보류

- 동작: 작업 허가는 현장 안전 신호를 기체 집합마다 비춘 정보 투영입니다(picasso ADR 52). 안전 기능이 아니며 기체를 세우는 것은 안전 계통이고, picasso 는 이 값으로 새 로봇 명령만 내지 않습니다(단위 출발, 개정 갱신, 미확정 조회). 이미 나간 명령, 취소, 관측은 막지 않습니다. 실행 호스트 설정 `host.work-permit.mapping`(작업 디렉터리 기준 JSON 파일 경로, `mission-host.properties` 기본값 빈 문자열)이 비면 선언하지 않은 현장이고 미들웨어에 허가 포트를 붙이지 않아 발행 거동이 오늘 그대로입니다. 경로가 있는데 파일을 못 읽거나 모양이 틀리면 기동이 실패합니다. 대응의 신호 하나가 원천 하나(`cell/<신호>`)이며, 값이 허가 값과 같으면 `PERMITTED`, 다르면 `INHIBITED`(막는 주체 `신호=값`, 풀릴 근거 «안전 계통이 <신호> 을 <허가 값> 으로 되돌릴 때»)입니다. 신호가 셀 대역에 없음, 신호 목록 없음, 안전 신호가 아님, 한 번도 못 읽음이면 `UNKNOWN`(까닭 `REPORTED`)입니다. 대응에 없는 기체는 `NOT_COVERED` 모름이라 새 명령이 막히므로 선언한 현장은 명부의 기체를 빠짐없이 넣어야 합니다. 막힌 실행의 단위는 `PENDING`이고 물리 상태는 운영자 보류로 바뀌지 않으며 인시던트와 작업 응답 없이 실행 목록 칸 `permitBlock` 에 보입니다. 운영자 `release`·보류 판단으로 풀리지 않으며 허가가 돌아오는 pump 에 명령을 냅니다. 내기 전에 막힌 실행의 운영자 취소는 허가를 기다리지 않고 `ABORTED` 로 끝납니다. 현장이 대응을 선언하면 `WAITING_READY` 에서 작업 번호를 쓰기 전에(작업 번호 쌍이 없는 스테이션은 작업 요청 제출 전에) 대응이 맡은 기체 전부의 허가를 봅니다(격리 확인 다음, 기한 확인 앞). 하나라도 `PERMITTED` 가 아니거나 허가를 못 읽으면 쓰지 않고 `WAITING_READY` 에 사유를 남기며 설비 준비 기한은 멈춥니다(격리와 같음). 허가가 돌아오면 «작업 허가 복귀; 설비 준비 기한을 다시 셉니다» 로 `WAITING_READY` 에 다시 들어가 기한을 다시 셉니다. 작업 허가 대응을 선언하지 않은 현장을 포함한 모든 현장에서 실행 호스트가 응답하지 않는 경우에는 작업 허가 대기가 아니라 «실행 호스트 응답 없음; 작업 번호를 쓰지 않고 작업 요청을 내지 않습니다: <원인>» 사유를 남기며 설비 준비 기한은 멈춥니다. 실행 호스트가 다시 응답하면 «실행 호스트 응답 복귀; 설비 준비 기한을 다시 셉니다»로 `WAITING_READY` 에 다시 들어가 기한을 다시 셉니다. 스테이션이 보는 기체는 대응이 맡은 기체 전부입니다(어느 기체에 보낼지는 제출 때 정해지므로). 해당 작업의 로봇 실행에 작업 허가 차단이 걸려 있는 동안에는 스테이션 작업의 `RUNNING` 실행 기한도 일시 정지됩니다. 차단이 해제되어 작업 허가가 복귀하면 실행 기한은 그 복귀 시점부터 다시 계산합니다.

### 판단 기록으로 재기동 넘기기

- 동작: 끝나 이빅션한 작업 지시는 재기동 전후 모두 같은 작업 지시 id 로 재실행하지 않습니다. 같은 id 로 다시 내면 버전과 무관하게 REJECTED 입니다. 실행 호스트는 종결을 기록하고(종결 이벤트 커밋) 작업 응답 ack 뒤에 picasso `Middleware.forget` 으로 끝난 실행을 메모리에서 이빅션합니다. `PHYSICALLY_DONE`·`ABORTED` 는 곧 이빅션하고, `FAILED`·`UNVERIFIED` 는 `host.settled.revisable-retention`(기본 `PT5M`) 동안 둡니다. 두는 동안에는 같은 버전 재제출이 IDEMPOTENT, 높은 버전은 개정으로 ACCEPTED 입니다. 이빅션한 뒤 같은 인스턴스 안에서는 picasso 가 툼스톤으로 거부합니다(사유 `FORGOTTEN_JOB_ORDER` 로 시작). 재기동 뒤에는 picasso 툼스톤이 사라지므로 실행 호스트가 막습니다. 미들웨어에 그 작업 지시의 실행이 없고 실행 일지에 그 작업 지시가 있으면 `assign` 을 부르지 않고 REJECTED 입니다. 가르는 기준은 그 작업 지시의 종결(`SETTLED`)·다시 실행(`REOPENED`)·포기(`GAVE_UP`)·운영자 종결(`CLOSED`) 이벤트 가운데 마지막 것입니다. 마지막이 종결이거나 운영자 종결이면 사유가 `FORGOTTEN_JOB_ORDER` 로 시작하고 응답 칸 `forgottenJobOrder` 가 참, 그 밖의 일지 행(종결하지 않은 행, 종결 뒤 다시 실행되었다가 미뤘거나 포기한 행)이면 사유가 `JOURNALED_JOB_ORDER` 로 시작하고 거짓입니다. 운영 서비스는 이 칸을 작업 요청의 거부(`WorkRequestRejection.forgottenJobOrder`)로 넘기고, 화면은 거부 사유에 새 작업 지시로 내라는 안내를 붙입니다. 다시 할 일은 새 작업 지시 id 로 냅니다.

### 복원 못 한 실행의 운영자 종결

- 동작: 기동 복원에서 리빌드하지 못한 포기(`GAVE_UP`) 행이나 스냅숏을 읽지 못해 미룬(`DEFERRED`, 사유가 `RESUME_SNAPSHOT_UNREADABLE`로 시작) 행을 운영자(사람)가 사유를 입력하여 종결(운영자 종결)합니다(살아 있는 다른 인스턴스가 든 실행이라 리빌드하지 않는 행은 `NOT_CLOSABLE`, 에이전트 승인자는 `REFUSED`). 실행 호스트는 해당 기체의 스냅숏을 읽고 작업 지시의 미종료 태스크(id 가 `<jobOrderId>#`로 시작하고 종료하지 않은 상태) 유무를 순서대로 확인합니다. 스냅숏을 읽을 수 있고 미종료 태스크가 없으면 `GAVE_UP` 행은 근거 `SNAPSHOT`으로 종결되고 기체 배정 제외가 해제됩니다. 스냅숏을 읽을 수 있는 `DEFERRED` 행은 다음 pump에서 리빌드되므로 `NOT_CLOSABLE`이며, 스냅숏을 읽지 못하는 동안의 증언으로만 종결할 수 있습니다. 태스크가 이동 중이거나 대기 중인 명령이 있는 등 종료하지 않은 상태(`RETRIABLE`, `NEEDS_INTERVENTION` 제외)이면 `TASK_LIVE`로 증언을 받지 않습니다. 스냅숏을 읽을 수 없거나 남은 태스크가 모두 사람을 기다리는 상태(`RETRIABLE`, `NEEDS_INTERVENTION`)일 때, 증언이 없으면 `STOP_UNCONFIRMED`를 반환하고 현장에서 로봇이 멈추었다는 운영자의 증언(`attestedStopped=true`)이 있으면 근거 `ATTESTED`로 종결됩니다(그 외 `TARGET_CHANGED`, `NOT_FOUND`, `ALREADY_CLOSED`, 살아 있는 실행이 있거나 마지막 이벤트가 `SETTLED`인 경우의 `NOT_CLOSABLE` 결과는 아무것도 기록하지 않음). 종결 시 단일 트랜잭션으로 일지 이벤트 `CLOSED`(실행 id 없음, `detail`은 근거), 덧붙이기 전용 새 표 `mission.execution_close`(V12) 1행, 처분 `SENT`인 `job_response_log` 1행, `result_outbox` 이벤트를 기록하며 커밋 후에만 메모리가 변경됩니다(기록 실패 시 500 `RECORD_WRITE_FAILED`로 아무것도 남지 않고 재시도 가능). 종결 응답은 물리 상태 `UNVERIFIED`, 비어 있는 `completedUnits`, `unverifiedUnits`, `inDoubtUnits`, 사유 코드 `UNRESTORED_CLOSED`가 부여된 `incompleteUnits`, `operatorRequired=true`, `reachedEvidence=E0`, 최상위 `closure`(`{kind:"UNRESTORED_CLOSED", basis:"SNAPSHOT"|"ATTESTED"}`)를 갖고, 인스턴스 및 실행 id는 종결된 쌍(이전 인스턴스의 실행)이며 응답 id는 `close-<event_id>`입니다(단위 id는 마지막 송신 기록에서, 없으면 작업 지시를 읽을 수 있을 때 임무 계획에서 가져오고 둘 다 없으면 비어 있으며, 로봇을 멈추지 않고 성공을 추론하지 않음). 운영 서비스는 이를 작업 요청의 다음 결과 버전으로 정상 수집하여 저장된 스냅숏에 `closure`를 유지하며(`IN_DOUBT` 작업 요청은 `ACCEPTED`로 전이, 알 수 없는 `kind`·`basis`이거나 `UNVERIFIED`가 아닌 결과의 `closure`는 그 쪽 전체를 저장하지 않음), `ATTESTED` 종결 후 해당 기체는 읽을 수 있는 스냅숏에서 미종료 태스크가 없음이 확인될 때까지 «정지 증언으로 종결하고 스냅숏 확인 전인 실행이 있다: <job order ids>» 사유로 배정에서 제외되고 재기동 때 DB에서 다시 읽습니다. 종결된 작업 지시 id는 일지의 마지막 이벤트가 `CLOSED`가 되어 재기동 전후 모두 `FORGOTTEN_JOB_ORDER`로 재제출이 거부되며 더 이상 복원 대상이나 `GAVE_UP` 행이 되지 않습니다. 상위 시스템은 `replacesExternalOrderId`로 `ACCEPTED` 상태이자 최신 결과 버전에 `closure`(`UNRESTORED_CLOSED`)가 있는 작업 요청을 대체할 수 있고 해당 결과 버전은 `ops.work_request_supersession.original_result_version`(V23)에 기록됩니다(그 외는 409 `ORIGINAL_NOT_REPLACEABLE`과 함께 «실행 없이 끝났거나 운영자가 종결한 앞선 작업 요청만 대체할 수 있습니다»를 반환). 운영 › «실행»의 «복원 못 한 실행» 구역에서는 종결하지 않은 `GAVE_UP` 행(이전 기동의 것도 재기동을 넘어 남음), 이번 기동의 `DEFERRED` 행, 스냅숏 확인 전인 `ATTESTED` 종결 행이 표시되며, 운영자는 행의 «운영자 종결» 버튼으로 연 폼에서 경고를 확인하고 종결 사유와 필요하면 현장 정지 증언을 입력해 «현장 확인 후 운영자 종결» 로 보냅니다. 심장박동가 유효한 다른 인스턴스가 든 일지 행은 미룸(`DEFERRED`) 또는 포기(`GAVE_UP`) 상태여도 심장박동가 만료될 때까지 종결할 수 없으며, 이미 종결된 행은 리빌드 대상에서 제외되고 `ALREADY_CLOSED`로 응답합니다. 운영 서비스가 무응답 후 요청 id로 종결 조회를 재시도할 때 처리 중인 요청은 409 `REQUEST_IN_PROGRESS`로 응답하여 미반영으로 처리되지 않도록 보장합니다.

지시를 못 읽어도 종결하고 단위는 마지막 송신 기록의 것이며 없으면 비고 판과 근거 등급은 그 행의 것이다`, `종결한 작업 지시를 다시 내면 FORGOTTEN_JOB_ORDER 로 거부하고 재기동 뒤에도 같다`, `종결한 행은 재기동해도 복원 대상도 포기 행도 아니고 판정 사유도 없다`, `포기 행은 두 번 재기동해도 실행 목록 unrestored 에 닫을 수 있는 행으로 남는다`, `살아 있는 태스크가 돌면 증언이 있어도 TASK_LIVE 이고 사람을 기다리는 태스크면 증언 없이는 STOP_UNCONFIRMED 증언하면 ATTESTED 로 종결하며 그 기체는 재기동을 넘어 스냅숏이 동의할 때까지 판정에서 빠진다`, `스냅숏을 못 읽어 미룬 행은 증언으로만 종결하고 종결 뒤에는 스냅숏이 읽혀도 리빌드하지 않는다`, `에이전트 승인자는 REFUSED 이고 스냅숏이 읽히는 미룬 행은 다음 pump 가 리빌드하므로 NOT_CLOSABLE 이며 둘 다 아무것도 적지 않는다`, `살아 있는 다른 인스턴스가 든 미룬 행은 NOT_CLOSABLE 이고 아무것도 적지 않는다`, `도는 실행 종결한 작업 지시 없는 작업 지시 이미 종결 본 실행이 다름 은 각각 NOT_CLOSABLE NOT_CLOSABLE NOT_FOUND ALREADY_CLOSED TARGET_CHANGED 이고 같은 requestId 는 409 REQUEST_ID_REUSED 이며 본문이 틀리면 400 JSON 이 아니면 415 다`, `종결 행을 못 적으면 500 RECORD_WRITE_FAILED 이고 이벤트 결과 송신 기록이 남지 않으며 다시 닫을 수 있다`, `종결 조회는 종결 전 404 NOT_CLOSED 종결 뒤 그 requestId 를 싣는다`, 운영 서비스 시험 `ExecutionControlsTest` 의 `복원 못 한 실행 종결은 운영자 모드만 하고 본문이 틀리면 CLOSE_BAD_REQUEST 사유가 없으면 REASON_REQUIRED 이며 호스트를 부르지 않는다`, `종결은 승인자가 행위자이고 CLOSED 는 성공 그 밖의 결과와 호스트 4xx 는 거부이며 응답이 없으면 closure 의 requestId 로 대조하고 못 읽으면 확인하지 못한다`, `HostClientTest` 의 `종결은 승인자와 사유와 본 실행과 증언과 요청 id 를 실어 보내고 종결 조회는 404 NOT_CLOSED 만 없음으로 읽는다`, `WorkRequestsTest` 의 `종결 결과 이벤트는 closure 를 결과 버전에 싣고 결과 불명 작업 요청을 수락으로 올리며 틀린 closure 는 쪽 전체를 되돌린다`, `운영자가 종결한 수락 작업 요청은 대체할 수 있고 연결에 그 결과 버전을 적으며 closure 없는 UNVERIFIED 와 열린 스테이션 작업은 대체하지 않는다`, 통합 시험 `UnrestoredCloseTest` 의 `복원 못 한 실행을 기체가 멈춘 뒤 운영자가 종결하면 상위 시스템은 UNVERIFIED 와 closure 를 받고 앞선 주문을 잇는 새 주문이 받아들여진다`, 화면 시험 `ExecutionClose.test.tsx` 여덟, `ExecutionRestore.test.tsx` 의 `이번 기동 뒤 운영자가 종결한 행은 복원 보고에 운영자 종결로 표시되고 종결하지 않은 행은 표시가 없다`

## 보장하지 않는 것

picasso-ops 가 보장하지 않는 항목은 다음과 같습니다.

### 물리적 정확히 한 번

중복 방지는 작업 요청의 중복 방지이지 로봇 동작의 중복 방지가 아닙니다. 실행 호스트 재기동 복원은 같은 태스크 id 로 다시 붙지만, 로봇 쪽 태스크 기록의 지속성은 별개라 런처와 어댑터까지 재기동한 경우 같은 태스크 id 의 중복 물리 실행을 막는다고 보장하지 않습니다. 재작업(`REWORK`)은 로봇을 다시 움직이는 판단입니다. 운영자의 현장 확인 후 해제는 물리 완료 판정이 아닙니다.

### 안전

Ops 의 보류, 재작업, 현장 확인 후 해제, 격리 해제 판단과 스테이션이 쓰는 일반 설비 신호는 인증된 안전 정지나 안전 PLC, 장비 쪽 인터록을 대신하지 않습니다. 스테이션 준비·완료 신호와 작업 번호 송신·반환 신호에는 안전 신호를 연결할 수 없고(작업 번호 신호도 안전 아닌 TEXT 신호여야 등록되고 등록 시 거부), 격리 해제 판단 역시 안전 기능이 아닙니다. 셀 대역은 안전 신호 `guard_closed` 쓰기를 거부합니다. 실행 호스트를 직접 부르는 길은 Ops 의 자원 조정을 지나지 않습니다. 작업 허가도 안전 기능이 아니며 현장 안전 신호를 기체 집합마다 비춘 정보 투영입니다(picasso ADR 52). 작업 허가가 열려 있어도 기체를 세우는 것은 안전 계통이고, 작업 허가가 닫혀도 이미 나간 명령은 안전 계통이 아니면 멈추지 않습니다. 작업 허가 값은 늦거나 틀릴 수 있습니다(관측은 250ms pump 주기, 유효 폭 `validFor`). 셀 대역의 HTTP 쓰기는 여전히 안전 신호를 거부합니다. 새 `Site.actuateSafety` 는 프로세스 안의 시험 대역용이고 HTTP 로 열지 않습니다. 근거: `site` 시험 `SiteCellTest` 의 `안전 계통 대역은 안전 신호의 값과 관측 시각을 바꾸고 일반 신호와 틀린 값은 거부하며 소프트웨어 쓰기는 여전히 403 이다`, 통합 시험 `WorkPermitTest`(소프트웨어 쓰기가 `REJECTED`·`SAFETY_SIGNAL_READ_ONLY` 임을 단언).

### 실제 하드웨어와 상용 연계

로봇은 picasso mimic(에뮬레이터), 설비는 셀 대역, 상위 시스템은 로컬 Mock MES 하나입니다. 실제 하드웨어, 실제 PLC, 상용 MES·WMS 연계는 검증하지 않았습니다.

### 여러 인스턴스

같은 DB 에 운영 서비스 여럿을 띄우는 구성도, 실행 호스트 여럿을 띄우는 구성도 지원하지 않고 검증하지 않았습니다(«배포 전제» 참고). 단계 0 자리(인스턴스 id 와 심장박동)가 생겼습니다. 그 자리가 막는 것은 둘뿐입니다: 살아 있는 다른 인스턴스가 남긴 `RETRYING`·`REWORKING` 을 앞 프로세스 중단으로 읽는 것, 살아 있는 다른 실행 호스트가 든 일지 행을 리빌드하는 것. 리더 선출·리스·세대·펜싱은 없습니다(근거: HA 설계 기록 `docs/superpowers/specs/2026-10-14-ha-authority-design.md` §8, §11). 결과 수집 커서와 콜백 전달에는 동시 실행을 견디는 장치가 일부 있지만 스테이션 조정은 프로세스 하나를 전제합니다. 콜백 주소 설정이 다른 운영 서비스가 같은 DB 에 결과 버전을 적으면, 그 결과의 전달 행은 주소를 가진 프로세스가 다시 기동해 따라잡기를 할 때까지 생기지 않습니다(전에는 2초 주기가 넣었습니다). 지금 구성은 활성 운영 서비스가 하나라 해당하지 않습니다.

### 설비 완료 신호의 인과

완료 신호는 값과 마지막으로 쓰인 시각뿐이라 어느 작업 때문에 켜졌는지 증명하지 못합니다. 외부 검토 실험 A1 에서는 스테이션 작업 X 를 보냈고 로봇이 끝나지 않아 실행 기한 초과로 `REVIEW_REQUIRED` 가 되었으며 운영자가 `CONFIRM_CLEAR` 로 해제했습니다. 이 해제는 실행 호스트에서 X 의 실행을 멈추지 않습니다. 다음 스테이션 작업 Y 를 보낸 뒤 X 쪽 설비가 늦게 완료 신호를 올리면, 고치기 전에는 Y 의 완료로 받아들였습니다. 단위 시험과 실제 스택(mimic, 셀 대역, 실행 호스트, 운영 서비스)에서 재현했습니다. 고치기 전 완료 규칙은 현장 시계의 `observedAt` 과 운영 서비스 시계의 `dispatched_at` 을 비교했습니다. 작업 번호 신호 쌍이 있는 스테이션은 반환 번호로 막습니다. 쌍이 없는 스테이션은 보낸 작업의 현장 확인 해제 때 격리로 막습니다. 다만 쌍이 없는 스테이션에서 X 가 정상 완료한 뒤 X 쪽 설비가 완료 신호를 다시 true 로 쓰면, 그 사이 실행 중인 Y 의 로봇이 물리 완료일 때 Y 의 완료로 받아들일 수 있는 한계가 남습니다. 정상 완료는 격리하지 않으므로 격리도 생기지 않습니다. 둘을 가를 수 있는 것은 작업 번호 신호 쌍뿐입니다. 시험 `정상 완료는 격리하지 않고 이전 신호가 초기화되기 전에는 다음 작업을 보내지 않는다` 가 이 한계를 단언으로 적어 둡니다. 설비 연동 요구 사양은 [공유 스테이션 설비 연동 요구 사양](station-equipment-requirements.md)을 따릅니다.

### 현장 확인 후 해제의 실행 중단 미보장

`CONFIRM_CLEAR` 은 Ops 의 스테이션 점유만 풀고 묶인 작업 요청을 닫을 뿐, 실행 호스트의 실행이나 로봇 동작을 멈추지 않고 취소를 부르지도 않습니다. 해제한 작업의 로봇과 설비는 계속 움직이거나 늦게 신호를 쓸 수 있습니다. 그래서 작업 번호 신호 쌍이 없는 스테이션은 격리하고, 운영자가 설비가 비었고 이전 로봇이 멈췄는지 현장에서 확인해야 합니다. 실행을 멈추는 길은 이제 따로 있습니다: 운영 › 실행의 운영자 실행 취소(`CANCEL_EXECUTION`, `POST /api/executions/{id}/cancel`). 두 조작은 묶여 있지 않으므로 해제한 작업의 실행을 멈추려면 사람이 따로 취소해야 합니다. 취소도 다음 pump 가 하류를 읽고 `ABORTED` 로 확정하며 로봇의 물리 정지를 보장하는 안전 기능이 아닙니다.

### 결과 콜백 순서

결과 콜백(`WorkResultDelivery.deliverOne`)은 다음 재시도 시각 순으로 개별 행 단위 전송되며, 작업 요청별 전송 순서를 보장하지 않습니다. 실패한 행만 지수 백오프로 지연되므로 버전 1이 지연되는 동안 버전 2가 먼저 도달하거나 동시 전송될 수 있습니다. 따라서 수신하는 상위 시스템은 `version` 필드와 `Idempotency-Key`(`<receiptId>/v<version>`)를 기준으로 순서를 정렬해야 합니다.

### 결과 버전의 DB 불변

`ops.work_result` 의 불변은 코드 관례이고 DB 트리거로 막지 않습니다. DB 를 직접 고치는 경로는 막지 못합니다.

### 잔여 파지 표시의 범위

- 표시는 시각 순서가 아니라 계획 순서에서 파지 관측이 있는 마지막 로봇 단위의 관측으로 정합니다. 플릿 단위는 보지 않습니다. 관측이 «든 채» 가 아니면 실제로 들고 있어도 표시가 서지 않습니다.
- 부분 완료(`PARTIAL`)는 종결로 적지 않으므로 그동안은 표시가 아니라 진행 중인 실행으로 뺍니다. 표시는 종결할 때만 섭니다.
- 이제는 작업 허가나 결함 차단과 무관하게(picasso `ResumeCancelTest` 가 허가 차단을 시험, ops 시험은 없음) 첫 pump가 기체 스냅숏에서 로봇 단위의 태스크를 찾아 붙어 취소를 보내므로, 태스크가 끝나기 전에 실행이 `ABORTED`로 종결해 기체를 배정에 다시 내주지 않습니다. 다만 플릿 운반 단위에는 취소가 다시 가지 않으며, 기체 스냅숏을 읽지 못하는 동안에는 실행이 기한 없이 `CANCELING`에서 대기합니다.
- 끝나지 않은 태스크가 없으면 곧바로 걸어 첫 pump가 새 명령 없이 `ABORTED`로 종결합니다(`cleanup = nothing_to_clean`). 그 실행은 기체의 파지를 다시 관측하지 않으므로 잔여 파지 표시가 서지 않습니다.
- 화면의 현장 확인 체크박스는 서버가 집행하지 않습니다. 빈손 확인은 사람이 현장에서 본 것을 적는 기록이고 로봇 센서로 확인하지 않습니다.
- 스킬이 취소를 받지 않으면(`CANCEL_UNSUPPORTED`) 미들웨어는 도는 단위를 끝까지 두고 다음 경계에서 멈춥니다. 호스트는 그 거부를 읽지 않아 화면에 보이지 않습니다.

### 작업 허가의 범위

- 대응에 없는 기체는 `NOT_COVERED` 모름이라 새 명령이 막힙니다(시험: `CellWorkPermitsTest` 의 `대응에 없는 기체는 NOT_COVERED UNKNOWN 이다`).
- 세션은 실행 호스트가 정한 것이고 현장 재기동은 셀 대역 끊김으로만 알며, 끊김 없이(250ms 안에) 다시 뜬 현장은 같은 세션으로 읽힙니다(시험: `CellWorkPermitsTest` 의 `셀 대역을 못 읽으면 세션이 바뀌어 앞 세션의 PERMITTED 가 SESSION_CHANGED UNKNOWN 이 되고 다시 읽으면 새 세션으로 허가한다`).
- 스테이션의 허가 확인과 작업 번호 쓰기 사이에 허가가 바뀌면 번호는 써지고 로봇 명령은 발행 게이트가 막습니다(같은 판독을 두 번 읽지 않음).
- 스테이션은 대응이 맡은 기체 전부로 판단합니다(한 기체만 막혀도 그 현장의 모든 스테이션이 기다림).
- 허가 차단은 작업 응답, 결과 버전, 상위 결과(콜백)에 실리지 않습니다.
- 플릿 경로 위임은 발행 게이트를 지나지 않고, 재기동 뒤 리빌드의 재부착도 허가에 막히며, 막힌 미확정 단위의 취소는 허가가 돌아올 때까지 하위로 나가지 않습니다. 셋 다 picasso 한계 §15.219 그대로입니다.
- 배정 판정은 허가를 보지 않습니다(막힌 기체에도 배정되고 실행이 `PENDING` 으로 기다립니다).

### 판단 기록의 범위

- 운영자 판단이나 결함 수용 직후 기록 쓰기가 실패하면 경고 로그만 남기고 다음 pump 뒤 기록이 다시 적습니다. 그 pump 기록이 성공하기 전에 프로세스가 죽으면 그 판단이나 수용 열쇠는 넘어오지 않습니다. 수용 행은 남아 실행 목록의 `releases`에서 보입니다.
- 이 실행 호스트는 여전히 조치 승인(`approveRemedy`)을 부르지 않으므로(REST 없음) 이 호스트가 만든 실행에서는 기록의 `approval` 칸이 늘 비어 있습니다. 기록에 있으면 넘깁니다. picasso는 게이트 연쇄 검사(`AdmissionGate.chainOf`)에서 기체 스냅숏이나 종료한 단위 대신 종결하지 않은 실행의 도는 단위 파지 관측(`liveHold`)으로만 조치 제안을 계산하지만, 실행 호스트가 실행 중인 기체를 새 배정에서 제외하므로(`occupiesRobot`, «진행 중인 실행이 있다») 파지 관측이 있는 기체에는 새 작업 지시가 전달되지 않습니다. 기존 실행의 리비전 경로 역시 조치 제안을 기록하지 않고 picasso `commit` 이 기존 실행에 조치를 붙이는 승인을 거부하므로, 현재 흐름에서는 승인 대상인 조치 제안이 형성되지 않습니다. 부품을 파지한 채 완료된 기체는 같은 문서의 «부분 완료·잔여 파지 기체의 배정 제외» 항목대로 잔여 파지 표시와 사람의 빈손 확인으로 다룹니다.
- 수용은 결함을 지우지 않습니다(같은 결함은 다시 막지 않지만 새 결함은 다시 막습니다). 작업 허가 차단은 수용으로 풀리지 않습니다.
- 다시 연 인시던트는 결함 원문·파지 관측이 비어 있습니다(새 인스턴스가 관측하지 않았습니다). 현장 상태는 사람이 직접 봅니다.
- 판단 기록 표(V6) 이전에 받은 일지 행(기록 없음)은 옛 거동으로 리빌드합니다: 앞선 단위는 근거 등급 E0, 설비 대기 기한은 재기동 때부터 다시 잽니다.
- 인시던트 사본의 판단 행은 여전히 pump 뒤에 적습니다. 판단 자체는 판단 기록으로 넘어옵니다.

### 종결한 실행 이빅션의 범위

- 종결 뒤 다시 실행된 실행의 기록(받은 리비전 행, 일지 이벤트 `REOPENED`, 판단 기록)을 적지 못하면 그 기록이 커밋될 때까지 모든 실행의 pump와 신규 제출, 배정이 막히며 리비전 제출의 응답은 500입니다. 막힌 실행은 일지 쓰기 실패와 같은 칸 `journalBlockedExecutionIds`에 보이고 다음 pump가 다시 적으면 풀립니다.
- 리빌드는 받은 리비전 가운데 가장 높은 버전의 작업 지시를 쓰지만 기체와 임무 버전은 일지 행의 것을 씁니다. 리비전은 실행이 쥔 임무 정의로 계획하고 이 실행 호스트는 재할당을 부르지 않기 때문입니다.
- 이빅션한 작업 지시에 대한 picasso의 툼스톤은 메모리에만 유지되며 지우는 입구나 상한이 없습니다(picasso 한계 «§15.224 · 이빅션한 작업 지시 툼스톤»). 재기동을 넘어서 재제출을 거부하는 것은 실행 일지입니다. 운영자가 종결한 작업 지시(일지에서 마지막이 `CLOSED`) 역시 일지를 통해 재기동을 넘어서 `FORGOTTEN_JOB_ORDER`로 재제출이 거부됩니다.
- `FAILED`와 `UNVERIFIED`의 보관 기간은 호스트 시계(가상 시계 시험에서는 가상 시간)로 측정합니다. 보관 기간이 지난 뒤 도착한 리비전은 REJECTED로 거부되며 새 작업 지시 id 로 내야 합니다.
- 인시던트 번들, 조치 탐색, 승인 소모 기록은 `forget` 뒤에도 picasso 메모리에 유지됩니다(picasso 한계 §15.166 변경 없음). 실행을 이빅션해도 이 메모리는 줄어들지 않습니다.
- 보존 기간이 지나 실행이 이빅션된 뒤 건너뛴 대상의 재작업은 `detail`이 `EVICTED`인 `NotHeld`로 반환되며, 새 작업 지시가 필요합니다.

### 운영자 출구와 운영자 종결의 범위

- 결과 불명 작업 요청 (결함 16(b)): 실행 호스트에 일지 행이 없고 제출 결과를 알 수 없는 `IN_DOUBT` 작업 요청은 어떤 운영자 조치로도 끝낼 수 없습니다. `review`는 현장 관찰만 기록하고, `recover`는 디스패치 전 `UNASSIGNED` 요청만 재평가하며, `supersede`는 `IN_DOUBT`를 거부하므로 실행 호스트의 결과가 도착할 때까지 `IN_DOUBT`로 유지됩니다.
- 모든 기체가 바쁠 때: 실행 호스트의 `UNASSIGNED`(모든 기체가 바쁘거나 배정에서 제외됨)는 작업 요청을 종료시킵니다. 큐가 없으며 기체에 여유가 생겨도 자동 재시도를 하지 않습니다. 재시도는 `replacesExternalOrderId`를 사용한 상위 시스템의 재전송이나, 디스패치 전 `UNASSIGNED`에 대한 운영자의 재평가(`recover`)를 통해 이루어집니다.
- 상위 시스템 취소 없음: 연계 API에는 상위 시스템(MES) 취소가 없습니다. 실행 중인 실행은 UI의 운영자 취소로만 정지할 수 있으며 현재 실행 호스트 인스턴스의 실행에 대해서만 가능합니다. 실행 호스트가 복원하지 못한 실행은 이번 운영자 종결로만 끝낼 수 있습니다.
- 운영자 종결 자체의 한계: 운영자 종결은 결코 성공을 추론하지 않으며(`completedUnits`가 비어 있음) 로봇을 멈추지 않습니다. 증언을 동반한 종결에서 실행 호스트는 사람의 말에 의존하며, 스냅숏이 부합함을 확인할 때까지만 해당 기체를 배정에서 제외합니다. 운영자 종결 결과는 운영 배치가 쓰는 결과 피드(`GET /host/result-events`)를 통해서만 운영 서비스에 전달되며, 레거시 폴링 모드(`GET /host/executions`만을 통한 결과 수집)에서는 종결된 실행이 실행 목록에 포함되지 않아 종결 결과를 수집할 수 없으므로 작업 요청을 대체할 수 없습니다.
