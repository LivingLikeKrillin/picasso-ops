# 공유 스테이션 설비 연동 요구 사양

## 소개와 범위

이 문서는 공유 스테이션 설비(PLC 등)를 picasso-ops 에 연결하는 연동 담당자와 시운전 담당자를 위한 요구 사양서입니다. 운영 서비스가 공유 스테이션에 스테이션 작업을 하나씩 맡길 때 설비 쪽이 내야 하는 신호와 그 뜻, 지켜야 하는 순서를 규정합니다.

운영 서비스는 실행 호스트의 `GET /host/cell` 로 셀 대역(현장 신호 대역, 에뮬레이터)의 신호를 읽습니다. 읽은 신호 가운데 안전 신호가 아닌 것만 씁니다. BOOLEAN 신호는 값이 `"true"` 또는 `"false"` 이고, TEXT 신호는 문자열입니다.

스테이션 워커가 2초(`ops.stations.poll-ms` 기본 2000ms)마다 한 번 읽고, 완료 신호와 작업 번호 반환 신호는 같은 한 번의 읽기(한 스냅숏)에서 함께 판단합니다.

스테이션은 엔지니어가 `POST /api/stations` 로 등록하고, 등록 뒤에는 설정을 바꿀 수 없습니다. 단계 기한 `timeoutSeconds` 는 5~3600초입니다.

## 준비 신호와 완료 신호

준비 신호는 BOOLEAN 형식이며 등록 칸은 `readySignal` 입니다. 이 신호의 true 는 설비가 새 작업을 시작할 수 있다는 뜻입니다. 운영 서비스는 같은 읽기에서 준비 신호가 true 이고 완료 신호가 false 일 때만 로봇에 작업 요청을 보냅니다. 그 전에는 스테이션 작업이 `WAITING_READY`(설비 준비 대기)에 머뭅니다. 이때 사유는 «자원 확보; 설비 준비와 완료 신호 초기화를 기다립니다» 입니다. 설비 준비 대기가 단계 기한을 넘으면 로봇에 보내기 전에 `TIMED_OUT` 으로 점유를 풉니다.

완료 신호는 BOOLEAN 형식이며 등록 칸은 `completeSignal` 입니다. 작업이 시작될 때 완료 신호는 false 여야 합니다. true 는 이번 작업의 설비 일이 끝났다는 뜻입니다. 준비 신호와 완료 신호는 서로 다른 신호여야 하며, 같으면 등록을 거부합니다. 운영 서비스는 준비 신호와 완료 신호를 쓰지 않습니다. 앞 작업 뒤 완료 신호를 false 로 되돌리는 것은 설비(또는 현장의 사람)의 몫이고, 되돌리기 전에는 다음 스테이션 작업을 보내지 않습니다.

스테이션 작업이 `RUNNING`(로봇 실행 중)에 들어가는 길은 모두 그 직전에 완료 신호 false 를 확인합니다. 이 진입 경로는 넷입니다.

1. 처음 전송 전 준비 확인
2. 전송 전 미배정 재평가 전
3. 운영자 관측 재개(`RESUME_OBSERVATION`)
4. 재작업 반영

완료 판정(`COMPLETED`)은 다음 세 조건을 모두 요구합니다.

- (가) 로봇의 저장된 최신 결과가 `PHYSICALLY_DONE` 이고 `RUNNING` 진입 때 적은 결과 버전 기준선보다 새 것(관측 재개는 같은 실행을 다시 보므로 예외).
- (나) 완료 신호가 true.
- (다) 그 읽기를 한 시각이 이 스테이션 작업이 `RUNNING` 에 들어간 시각(`phase_at`)과 같거나 뒤.

(다)의 두 시각은 모두 운영 서비스의 시계 기준입니다. 신호의 `observedAt`(현장 시계)은 비교하지 않습니다. 완료 판정 시의 사유는 «로봇 물리 완료와 이번 작업의 설비 완료 신호 확인; 자원 해제» 입니다.

실행(`RUNNING`) 중에는 완료 근거와 판단된 결함을 작업 허가 차단, 실행 기한, 셀 신호 유예보다 먼저 판정하므로, 기한이 지난 처리 주기라도 로봇 완료와 새 완료 신호가 함께 확인되면 정상 완료 처리합니다. 로봇 실행에 작업 허가 차단이 걸리면 실행 기한이 일시 정지되며 허가가 복귀하면 그 시점부터 기한을 다시 계산합니다. 셀 신호를 읽지 못하면 최대 15초 동안 유예 상태로 관측을 유지하며, 유예가 만료되거나 선언된 필수 신호가 누락된 경우 및 실행 기한을 초과한 경우에는 점유를 유지한 채 `REVIEW_REQUIRED` 로 전환합니다. 이렇게 확인 필요가 된 작업은 자동으로 다시 실행하지 않지만, 운영자가 현장 상태를 확인하고 완료 확인(`CONFIRM_COMPLETION`)을 수행하여 `COMPLETED` 로 종결할 수 있습니다.

## 작업 번호 신호 쌍(선택)과 절차

작업 번호 신호 쌍은 선택 사양이며 두 개의 TEXT 신호로 구성됩니다. 등록 칸은 `jobSignal`(화면 라벨 «작업 번호 송신 신호»)과 `jobEchoSignal`(화면 라벨 «작업 번호 반환 신호»)입니다. 둘 다 연결하거나 둘 다 비워야 합니다. 한쪽만 채우면 «작업 번호 송신·반환 신호는 둘 다 연결하거나 둘 다 비워야 합니다.» 로 거부합니다. 두 신호는 서로 달라야 하고, 등록 시점에 현장에 선언된 안전 아닌 TEXT 신호여야 합니다. 그렇지 않으면 «현장에 선언된 TEXT 신호가 필요합니다.» 로 거부합니다. 여기서 작업 번호는 스테이션 작업 id(UUID 문자열)입니다.

### 신호 쌍이 필요한 이유(외부 검토 실험 A1)

스테이션 작업 X 를 로봇에 보냈고 로봇이 끝나지 않아 실행 기한을 넘겨 `REVIEW_REQUIRED` 가 되었을 때, 운영자가 현장 확인 후 자원 해제(`CONFIRM_CLEAR`)로 점유를 푸는 상황이 있습니다. 이 해제는 실행 호스트에서 X 의 실행을 멈추지 않습니다. 다음 스테이션 작업 Y 가 보내진 뒤 X 쪽 설비가 늦게 완료 신호를 올리면, 고치기 전 운영 서비스는 그것을 Y 의 완료로 받아들였습니다. 이 현상은 단위 시험과 실제 스택(mimic 에뮬레이터, 셀 대역, 실행 호스트, 운영 서비스)에서 재현되었습니다.

고치기 전 완료 규칙은 현장 시계의 `observedAt` 과 운영 서비스 시계의 `dispatched_at` 을 비교했습니다. 현재는 이 교차 비교를 없애고 동일 시계 규칙으로 변경했습니다. 그러나 완료 신호 자체는 값과 마지막으로 쓰인 시각뿐이라 어느 작업 때문에 켜졌는지 구별하지 못합니다. 작업 번호 반환 신호 쌍이 그 빈자리를 채웁니다.

### 신호 절차

신호 절차는 다음과 같이 진행됩니다.

현장이 작업 허가를 선언했으면 운영 서비스는 아래 1 의 번호 쓰기 전에 작업 허가를 봅니다(격리 확인 다음, 기한 확인 앞). 대응이 맡은 기체 가운데 하나라도 `PERMITTED` 가 아니거나 허가를 못 읽으면 번호를 쓰지 않고 `WAITING_READY` 에 남으며(사유 «작업 허가 대기; 작업 번호를 쓰지 않고 작업 요청을 내지 않습니다: …») 설비 준비 단계 기한은 멈춥니다. 허가가 돌아오면 «작업 허가 복귀; 설비 준비 기한을 다시 셉니다» 로 기한을 다시 셉니다. 설비 쪽 요구는 새로 없습니다(설비는 번호를 받지 못한 채 준비 상태로 기다립니다). 작업 허가 선언 여부와 관계없이 실행 호스트가 응답하지 않을 때도 마찬가지로 작업 번호를 쓰지 않으며(사유 «실행 호스트 응답 없음; 작업 번호를 쓰지 않고 작업 요청을 내지 않습니다: …»), 설비에 새로 요구되는 사항은 없습니다. 근거: `StationCoordinatorTest` 의 `작업 허가가 INHIBITED 면 작업 번호를 쓰지 않고 설비 준비 대기에 막은 기체와 주체와 풀릴 근거를 남기며 PERMITTED 가 되면 그때 쓴다`.

1. 준비 true 와 완료 false 를 읽으면 운영 서비스가 DB 잠금 밖에서 작업 번호를 `jobSignal` 에 씁니다. 쓰기 경로는 운영자의 신호 쓰기와 같아 운영 서비스 → 실행 호스트 → 현장 순서이며, 조작 기록에 `WRITE_CELL_SIGNAL` 로 남습니다(행위자는 그 스테이션 작업의 요청자). 현장이 받아들였거나, 응답이 없었더라도 다시 읽은 값이 그 번호이면 쓰기 성공으로 봅니다.
2. 쓰기에 성공한 뒤에만 `DISPATCHING` 으로 넘어가 로봇에 작업 요청을 보냅니다. 이 전이의 근거(`context`)에는 `jobSignal`, `jobToken`, `signals` 가 남습니다.
3. 쓰기에 실패하면 로봇에 보내지 않고 `WAITING_READY` 에 남으며 사유는 «작업 번호 쓰기 실패; 설비 신호 기록을 기다립니다» 입니다. 다음 처리 주기에 다시 씁니다. 단계 기한은 다시 시작하지 않으므로 실패가 이어지면 전송 전에 `TIMED_OUT` 으로 풉니다.
4. 설비는 작업을 시작할 때 `jobSignal` 의 값을 받아 그 작업이 끝날 때까지 붙들어 둬야 합니다. 그 사이 `jobSignal` 에 다른 값이 쓰여도 붙든 값은 바뀌면 안 됩니다.
5. 설비는 붙든 번호를 `jobEchoSignal` 에 먼저 쓰고, 그다음에 완료 신호를 true 로 올려야 합니다. 운영 서비스는 완료 신호와 반환 번호를 같은 읽기에서 판단하므로, 순서가 바뀌면 완료 true 와 이전 반환 번호를 함께 읽어 불일치로 판단할 수 있습니다.
6. 운영 서비스는 완료 신호 true 이고 반환 번호가 이번 작업 번호와 같고 로봇 물리 완료 조건이 맞을 때만 `COMPLETED` 로 판단합니다. 완료 신호가 true 인데 반환 번호가 다르면 로봇 결과와 상관없이 «설비 완료 신호 수신, 작업 번호 불일치; 현장 확인이 필요합니다» 사유로 `REVIEW_REQUIRED` 가 되고 스테이션 점유는 유지됩니다. 이 기록의 근거에는 `expected`(이번 번호), `echoed`(읽은 반환 번호), `signals` 가 남습니다.
7. 그 뒤 운영자는 현장을 확인하고 완료 신호를 내린 다음 관측 재개(`RESUME_OBSERVATION`)를 합니다. 설비가 이번 번호를 반환하고 완료를 올리면 작업이 완료됩니다. 로봇 물리 완료가 저장되어 있고 설비가 이번 작업 번호와 함께 완료 신호를 유지하고 있다면 운영자가 관측 재개 대신 완료 확인(`CONFIRM_COMPLETION`)을 수행할 수도 있습니다.

## 작업 번호 신호 쌍이 없을 때: 스테이션 격리

작업 번호 신호 쌍이 없는 스테이션에서 로봇에 전송되었거나 미전송으로 확인되지 않은 스테이션 작업(`dispatched_at` 이 있음, 제출 수락 및 결과 불명 포함)을 `CONFIRM_CLEAR` 로 해제하면 스테이션을 격리합니다. `rf_station.quarantined_by` 에 해제한 작업 id, `quarantined_at` 에 시각을 적습니다(V17 마이그레이션). 해제한 작업의 이력에는 «자원 해제에 따른 스테이션 격리» 가 남습니다.

`CONFIRM_CLEAR` 조작은 그 시점의 셀 신호, 해제한 작업의 작업 요청 id, 저장된 최신 물리 상태와 결과 버전, 격리 여부를 이력 근거에 남깁니다. 반면 로봇에 보내지 않은 스테이션 작업의 종료(대기 취소, 전송 전 시간 초과, 가용 기체 대기 중 시간 초과, 실행 호스트의 미배정 응답, 운영 서비스의 제출 거부)와 정상 완료는 스테이션을 격리하지 않습니다. 해제 시 작업 요청을 읽지 못하면 보내지 않았다고 단정하지 않고 스테이션을 격리합니다.

격리 중에는 다음 스테이션 작업이 점유해도 보내지 않고 `WAITING_READY` 에 두며 사유는 «스테이션 격리; 현장 확인과 격리 해제 판단을 기다립니다» 입니다. 격리 중 설비 준비 단계 기한은 멈추며, 시간 초과로 다음 작업에 넘어가지 않습니다.

운영자는 설비가 비어 있고 이전 작업의 로봇이 멈췄으며 완료 신호가 꺼져 있는지 현장에서 확인한 뒤 판단 `CONFIRM_STATION_IDLE`(본문 `expectedRevision`, `decision`, `reason`)을 냅니다. 화면 버튼은 «현장 확인 후 격리 해제» 입니다. 격리된 스테이션을 점유한 `WAITING_READY` 작업이 아니면 409, 셀 신호를 읽지 못하면 503, 완료 신호가 켜져 있으면 409 로 거부됩니다. 조건을 통과하면 격리를 풀고 설비 준비 단계 기한을 그 판단 시각부터 다시 셉니다. 이력 사유는 «현장 확인 후 격리 해제: {사유}» 꼴로 기록됩니다.

## 남는 한계

작업 번호 신호 쌍이 없는 스테이션에서 X 가 정상 완료한 뒤, X 쪽 설비가 나중에 완료 신호를 다시 true 로 쓰면, 그 사이 Y 가 실행 중이고 Y 의 로봇이 물리 완료 상태일 때 그것을 Y 의 완료로 받아들일 수 있습니다. 정상 완료는 격리 대상이 아니므로 이 경우에는 격리가 발생하지 않습니다. 이 둘을 구별할 수 있는 수단은 오직 작업 번호 신호 쌍뿐입니다. 시험 `정상 완료는 격리하지 않고 이전 신호가 초기화되기 전에는 다음 작업을 보내지 않는다` 가 이 한계를 단언으로 명시합니다.

현재까지는 셀 대역(에뮬레이터)과 시험이 설비 역할을 수행하였으며, 실제 PLC 와 실제 하드웨어에서는 확인하지 않았습니다.

## 표준 근거와 확인 수준

관련 국제 표준 및 산업 표준 명세의 확인 내용은 다음과 같습니다.

- OPC UA Job Control(OPC 10031-4 v2.00.0, 2024-01-31)과 Machinery Job Management(OPC 40001-3 v1.0.1, 2024-05-01): 작업을 맡기는 `Store` 메서드가 `ISA95JobOrderDataType` 을 넘기고 그 첫 필드가 `JobOrderID` 입니다([OPC 10031-4 §6.3.4](https://reference.opcfoundation.org/specs/OPC-10031-4/6.3.4)). 결과를 돌려주는 `JobResponse` 는 필수 `JobOrderID` 를 포함합니다([OPC 10031-4 §6.3.5](https://reference.opcfoundation.org/specs/OPC-10031-4/6.3.5)). `Start` 는 작업 주문을 ID 로 가리킵니다([OPC 10031-4 §6.2.1.5](https://reference.opcfoundation.org/specs/OPC-10031-4/6.2.1.5)). 또한 OPC 40001-3 §8.1 은 `JobOrderResponseList` 항목을 `JobOrderList` 와 짝짓습니다([OPC 40001-3 §8.1](https://reference.opcfoundation.org/specs/OPC-40001-3/8.1)). 확인 수준은 공개 명세 본문 확인입니다.
- ISA-95 Part 4(IEC 62264-4 / ANSI/ISA-95.00.04-2018): 작업 주문(Job order, §8.6)과 작업 응답(Job response, §9.5) 모델이 있습니다. B2MML 의 `JobResponseType` 에 `JobOrderID` 가 있으나 그쪽에서는 선택 항목입니다. 확인 수준은 절 번호와 B2MML 스키마 확인입니다.
- SEMI E40(처리 작업) 및 E94(제어 작업): 호스트가 ID 를 붙여 만드는 작업 모델입니다. 본문이 유료여서 일부만 확인했습니다.
- PackML: 제품 ID 만 정의되어 있고 작업 ID 는 없습니다.
- PLC 신호 수준의 작업 번호 반환 절차: 벤더나 업계 지침 문서에서 찾지 못했습니다.

정리하면, OPC UA 및 ISA-95 모델의 공통 성질은 "완료(작업 응답)는 맡길 때 받은 작업 주문 id 에 묶여 보고된다" 는 점입니다. 이 문서에서 규정하는 두 신호 절차는 해당 성질을 PLC 신호 수준으로 옮겨 반영한 이 저장소의 요구 사양입니다. PLC 신호 수준의 작업 번호 반환 절차는 벤더나 업계 지침 문서에서 찾지 못했으며, 이 저장소의 요구 사양입니다. 송신 신호는 작업 주문 id 를 전달하는 자리에 해당하고, 반환 신호는 작업 응답의 `JobOrderID` 자리에 대응합니다.

## 안전 신호를 쓸 수 없음

준비 신호, 완료 신호, 작업 번호 신호에는 안전 신호를 연결할 수 없습니다. 운영 서비스는 안전 신호를 읽기 대상에서 제외하며, 등록 시 안전 신호나 현장에 선언되지 않은 신호가 지정되면 등록을 거부합니다. 셀 대역 또한 안전 신호인 `guard_closed` 에 대한 쓰기 요청을 거부합니다. 안전 신호는 실행 호스트의 작업 허가 대응(`host.work-permit.mapping`)을 거쳐서만 새 로봇 명령 판단에 쓰이며 스테이션 신호로는 여전히 연결할 수 없습니다. 작업 허가는 안전 기능이 아니라 안전 신호를 비춘 정보 투영이고 picasso 는 그 값으로 새 로봇 명령만 내지 않습니다. 근거: `CellWorkPermitsTest` 의 `신호가 없거나 안전 신호가 아니거나 신호 목록이 없으면 원천이 말한 UNKNOWN 이다`.

이 규격의 신호들은 일반 공정 신호이며, 인증된 안전 정지, 안전 PLC, 장비 쪽 인터록을 대신할 수 없습니다.

## 이 저장소에서의 확인(셀 대역 신호와 시험)

셀 대역 표준 픽스처의 공유 검사 스테이션 신호는 다음과 같습니다.

- `inspection_ready`: BOOLEAN, 초기값 `"true"`
- `inspection_complete`: BOOLEAN, 초기값 `"false"`
- `inspection_job`, `inspection_job_done`: TEXT, 초기값 빈 문자열(이번 변경에서 추가)
- `guard_closed`: BOOLEAN 안전 신호, 초기값 `"true"`. 현장이 작업 허가 대응을 선언하면 작업 허가의 원천(`cell/guard_closed`)이 될 수 있음. 시험에서는 `Site.actuateSafety` 로 여닫음(HTTP 아님, 셀 대역의 HTTP 쓰기는 여전히 거부).
- 코드 경로: `site/src/main/kotlin/dev/picasso/ops/site/SiteCell.kt`

운영 서비스 구현 코드는 다음과 같습니다.

- `ops-service/src/main/kotlin/dev/picasso/ops/service/stations/StationCoordinator.kt`(`tick`, `numbered`, `observe`, `decide`, `permitHeld`)
- `ops-service/src/main/kotlin/dev/picasso/ops/service/stations/StationPort.kt`(`read`, `write`, `permit`, `permitOf`)
- `ops-service/src/main/resources/db/ops/V17__station_job_number_quarantine.sql`

단위 시험 `StationCoordinatorTest`(`ops-service/src/test/kotlin/dev/picasso/ops/service/`)에 포함된 대표 회귀 시험 항목은 다음과 같습니다.

- `작업 번호 반환 스테이션은 해제한 이전 작업의 늦은 완료 신호를 다음 작업의 완료로 채택하지 않고 확인 필요로 넘긴다`
- `작업 번호 반환 스테이션은 반환 번호가 이전 값이면 로봇 완료 뒤에 온 완료 신호도 채택하지 않는다`
- `작업 번호 쓰기에 실패하면 로봇을 보내지 않고 설비 준비 대기에 남아 다음 처리에서 다시 쓴다`
- `작업 번호 반환이 없는 스테이션은 보낸 작업을 해제하면 격리하고 현장 확인 후 격리 해제 전에는 다음 작업을 보내지 않는다`
- `격리 중 설비 준비 기한은 멈추고 격리 해제 판단부터 다시 센다`
- `현장 시계가 운영 시계보다 늦어도 전송 뒤 새로 켜진 완료 신호로 완료한다`

통합 시험 `StationLateCompletionTest`(`e2e/src/test/kotlin/dev/picasso/ops/e2e/`)는 실제 스택 환경에서 두 가지 변형을 검증합니다. 작업 번호 쌍이 있는 스테이션의 경우 작업 X 의 늦은 완료를 작업 Y 의 확인 필요로 넘기는 동작을 확인하고, 쌍이 없는 스테이션의 경우 격리 처리되어 격리 해제 전에는 작업 Y 를 보내지 않는 동작을 확인합니다. 이 시험에서 시험 코드가 설비 역할을 맡아 운영 서비스의 신호 쓰기 API 로 반환 번호와 완료 신호를 씁니다.

작업 허가 쪽은 `StationCoordinatorTest` 의 작업 허가 시험 셋(INHIBITED·UNKNOWN·못 읽음, 작업 번호 쌍이 없는 스테이션)이 번호를 쓰지 않고 기다리는 것을, `site` 시험 `SiteCellTest` 의 `안전 계통 대역은 안전 신호의 값과 관측 시각을 바꾸고 일반 신호와 틀린 값은 거부하며 소프트웨어 쓰기는 여전히 403 이다` 가 셀 문 대역을, `StationCoordinatorTest` 의 `실행 단위가 작업 허가로 막힌 동안 실행 기한은 멈추고 허가가 돌아오면 그때부터 다시 센다`, `작업 허가 차단이 풀려 기한을 다시 세도 차단 중 저장된 로봇 완료는 이번 실행의 완료 근거로 남는다` 가 실행 중 허가 차단 동안 실행 기한이 멈추는 것을, 통합 시험 `WorkPermitTest` 가 실제 스택에서 셀 문을 열고 닫을 때 실행이 기다렸다가 끝까지 가는 것을 확인합니다.
